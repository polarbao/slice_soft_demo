### 1.1 形状正确的部分 ✅

- **`engine` 与 `importers` 入度为 0**：纯叶子/注入点，没有人反向依赖它们。这是 base/engine 三段式（接口在 base、实现在 engine、注入在 Worker）能成立的度量证据。
- **`pipeline` 出度 15、入度 3**：依赖几乎所有模块但几乎没人依赖它——**这正是编排层应有的形状**。
- **`layout` 出度 1**（只依赖 `scene`）：最干净的模块。
- **`preview` 入度 1**：预览是终端消费者，边界清楚。

### 1.2 `(root)` 是耦合枢纽（🟠 F-28）

`(root)` 指 `src/slicer_core/` 下的 19 个扁平文件（`slicer.cpp` 5 888 + `model.cpp` 1 941 + `config.cpp` 1 485 + `rip_reader.cpp` 884 + `tiff_io` + `texture_image` + `json_value` 等，合计 13 169 行）。

它同时是**最高入度（17，即 19 个模块里有 17 个依赖它）和高出度（12）**，并与 **12 个模块**存在双向依赖：config, api, output, reports, scene, system, support, diagnostics, geometry, material, model, materials。

**含义**：`slicer.cpp` / `config.h` / `model.h` / `json_value.h` 这几个扁平头是全仓的公共依赖底座。这解释了两件之前只有定性判断的事：

1. **为什么 `api/`（base 层）会包含遗留扁平文件**——因为 `config.h`、`model.h`、`json_value.h` 就在 `(root)`，任何人要用配置或模型类型都得引它们。`04_` F-06 说的「分层靠白名单」在这里有了量化解释：`(root)` 无法被干净地划到任一侧，所以名单里 `model`、`json_value`、`texture_image`、`rip_reader`、`tiff_io` 都被逐个点名进 base。
2. **为什么 `slicer.cpp` 的拆解风险高**（`04_` F-09 / `06_` R-12）——不是文件大，是它所在的 `(root)` 是 17 个模块的上游。

**改进方向**：`06_` R-12 的拆解顺序应当**优先把类型定义搬出 `(root)`**（`config.h` 的结构体、`model.h` 的 `Vec3`/`Triangle`/`BoundingBox`），而不是只搬 `slicer.cpp` 的算法块。搬类型能直接降低 17 个模块的耦合面；搬算法块只是让 `slicer.cpp` 变短。**这是本章对 R-12 的一处修正建议。**

### 1.3 双向依赖 27 对（🟡 F-29）

除 `(root)` 的 12 对之外还有 15 对，其中值得注意的：

| 双向对 | 为什么值得看 |
|---|---|
| `api` ↔ `output`、`api` ↔ `geometry` | **Facade 层与实现目录互相依赖**。而 `api/` 整目录归 base、会被链进 DLL——这条耦合决定了 DLL 的实际体积下限 |
| `diagnostics` ↔ {`raster`, `preflight`, `geometry`, `pipeline`, `material`, `materials`} | 诊断层反向依赖 6 个模块。典型的「诊断伸手到处拿数据」形状 |
| `output` ↔ `reports`、`pipeline` ↔ `reports` | 报告与输出互相依赖 |

**必须说清的口径限制**：以上是**子目录粒度的双向依赖**，`A/x.h → B/y.h` 且 `B/z.h → A/w.h` 就会被计入，这**不等于文件级循环依赖**（后者在 `#pragma once` 下也不一定编译失败，但会造成真正的解耦困难）。**本轮没有做文件级环检测**——那需要构建完整的头文件包含图并跑 Tarjan。想要真结论的话这是一个 S 级的补充度量。

### 2.2 `(root)` 的数字必须打折看

原始统计里 `(root)` 是 13 169 行 / 69 个测试文件 / 191 LOC per file，看着不错。**这个数字是虚高的**，原因：我的正则把 `#include "slicer_core/config.h"`、`model.h`、`json_value.h` 这类扁平头引用都归到 `(root)`，而几乎每个测试都要引配置或模型类型。

**真实情况**：`slicer.cpp` 的匿名 namespace 占 `66–4117` 行（**4 051 行**），按 C++ 语言规则**外部无法直接引用**。所以那 4 051 行的直接单元测试覆盖是 **0，且是结构性的 0**，不是「还没写」。对它的验证只能整条跑 `run_slicer` 然后比对 golden 包。这与 `04_` F-09 的判断一致，本节提供的是量化确认。

### 2.3 一个命名问题（🟡 F-31）

`src/slicer_core/material/`（单数，8 文件 2 770 行）与 `src/slicer_core/materials/`（复数，68 文件 7 877 行）**并存**，且 `material → materials` 单向依赖。两个目录名只差一个 `s`，在 `#include` 里极易写错，而写错的后果是拿到另一个模块的头。改名是 S 级成本、零语义风险。

## 3. 并发模型审查

### 3.1 SPI 的承诺

`contracts/print_module_spi.h:21`：

> 6. `pm_module_t` 允许多线程并发调用；单个 `pm_job_t` 只允许由一个线程操作。

即：**宿主可以并发调用同一个模块实例上的进程内能力**（`scene.apply_operation`、`scene.get_viewdata`、`package.render_layer_preview`…）。这是一条对实现的实质约束。

### 3.2 实现侧确实上了锁 ✅

| 组件 | 同步手段 |
|---|---|
| `HandleRegistry` | `std::atomic_bool m_active`、`std::atomic_bool m_cancellationRequested`、`std::atomic<JobLifecycleState> m_lifecycleState`（`HandleRegistry.h:54,110-112`）+ 14 处 mutex/lock 引用 |
| `SceneCapabilityAdapter` | `mutable std::mutex m_mutex`（:833）保护适配器级状态，6 处 `std::scoped_lock`（:99,181,237,249,259）；**外加每个 session 一把独立锁** `std::mutex mutex`（:74）在 :579 处使用 |
| `WorkerJobService` | `std::scoped_lock lock{m_implementation->mutex}` 保护作业表；每作业一个 `std::thread` + 每 execution 一把 `execution->mutex` |
| `ModelCapabilityAdapter` | 4 处锁引用 |

**双层锁结构（适配器级 + session 级）是正确的设计方向**：全局锁只保护注册表，场景操作在 session 锁下进行，避免一个慢的 `get_viewdata` 阻塞另一个场景的操作。

### 3.3 但正确性本轮没有验 ⚠️

我能确认「有锁、且分层合理」，**不能确认「锁是正确的」**。静态阅读判不了的问题至少有四类：

1. **锁粒度是否覆盖全部共享状态**：`SceneCapabilityAdapter` 有 6 处 `scoped_lock`，但该文件 855 行、有几十个成员函数。哪些路径漏了锁，需要逐函数比对成员访问集。
2. **锁顺序是否一致**（适配器锁 vs session 锁）：两把锁若在不同路径下以不同顺序获取即有死锁风险。
3. **`atomic` 与 mutex 的混用是否存在竞态窗口**：`HandleRegistry` 用 atomic 表达生命周期状态，`WorkerJobService.cpp:695-704` 又在遍历作业表时读 `active->terminal.load(...)` 来判并发上限——「检查-然后-使用」之间状态可能变化。当前 `maxConcurrentJobs=1` 掩盖了这个窗口，**放开并发（F-13）时它会暴露**。
4. **`pm_poll` 的「廉价且 percent 单调不回退」承诺**在并发下是否成立。

**这一项需要动态验证**，静态读不出结论：建议做一个并发压力用例（多线程反复 `scene.apply_operation` + `get_viewdata` + `poll`），配 TSan（MSVC 无 TSan，可用 Application Verifier 或改用 clang-cl 构建一个纯验证目标）。

**这也修正了 `06_` R-13 的一处排序**：放开并发（F-13）的前置条件我原先写的是「等 MEMFLOW 有界窗口落地」。MEMFLOW 现已落地，**所以真正的前置条件现在变成了「先做并发正确性验证」**，而不是内存。

### 对既有路线图的两处修正

1. **R-12（`slicer.cpp` 拆解）的第一刀应当改成「把 `config.h`/`model.h` 的类型定义搬出 `(root)`」**，而不是我原先建议的「先搬 PNG/zlib 编码」。理由：搬类型直接降低 17 个模块的耦合面；搬算法块只让文件变短，不改耦合。PNG/zlib 那一刀仍然值得做（零语义风险、可验证方法论），但它是**第二刀**。
2. **R-13（放开并发）的前置条件从「等 MEMFLOW 落地」改为「先完成 F-32 并发正确性验证」**。MEMFLOW 已于 2026-09-06 之后合入，原前置已满足。

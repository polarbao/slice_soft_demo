### F-01 🔴 部署清单与运行时自述的能力集已实际漂移

**证据**

| 位置 | `provides` 含 `slice.rgbwsvt`？ | `produces` 含 `p0.rgbwsvt.1`？ |
|---|---|---|
| `src/slicer_module/ModuleInfo.cpp:41`（运行时 `pm_module_info` 返回值） | ✅ 有 | ✅ 有 |
| `src/slicer_module/module.json.in:11-31`（部署清单 `module.json`） | ❌ **无** | ❌ **无** |

`ModuleInfo.cpp:41` 的字符串里明确含 `"slice.rgbwsvt"` 与 `{"contract":"p0.rgbwsvt.1","kind":"package"}`；`module.json.in` 的 `provides` 数组停在 15 项且 `produces` 只有 `p0.rgbwsv.2`。

且 `tests/stage14c_05/ModuleInfoTests.cpp:118-125` **正面断言**运行时自述里必须有这两项——说明 C++ 侧是刻意的，落下的是清单模板。

**影响**

- 任何按 `module.json` 做能力发现的消费者（打包/分发流程、未来的 PrintApp、第三方审计）都会认为本模块**不支持 RGBWSVT**。
- `scripts/PackageSlicerModule.ps1:260-269` 会把这份不完整的 `module.json` 原样打进分发包。
- 两份清单谁是真源，代码里没有答案。

**改动空间**：把 `module.json.in` 的 `provides` 补 `slice.rgbwsvt`、`produces` 补 `p0.rgbwsvt.1`。

**成本**：S（2 行）
**风险**：**极低**。已核实 `PackageSlicerModule.ps1:260-269` 只校验 `schema` / `spi` / `dll` / `subprocess.exe` / `buildConfig` / `version` 六个字段，**不校验 `provides` 或 `produces`**，所以补齐不会触发打包门禁。

### F-02 🔴 本该拦住 F-01 的对拍测试整条空转

**证据**

`CMakeLists.txt:2350-2356` 注册测试时的完整命令行：

```cmake
add_test(NAME ...
    COMMAND ${Python3_EXECUTABLE}
        ".../tests/stage14c_05/ValidateModuleInfoContracts.py"
        --repo "${CMAKE_CURRENT_SOURCE_DIR}")
```

**没有传 `--debug-probe` / `--release-probe`。** 而脚本第 270 行：

```python
moduleInfo = RunProbe(probePath) if probePath else expectedInfo
...
if moduleInfo != expectedInfo:
    raise AssertionError(f"{buildConfig} runtime module info drifted")
```

`probePath` 为 `None` → `moduleInfo = expectedInfo` → **`moduleInfo != expectedInfo` 恒为假**，「运行时自述漂移」这条断言**永远不会触发**。

雪上加霜：即使接上探针也会立刻红灯——脚本第 19-56 行的 `EXPECTED_PROVIDES` / `EXPECTED_WORKER` 常量本身也**没有** `slice.rgbwsvt`，与真实 DLL 不符。

剩下唯一真正执行的检查是 `ValidateCrossConsistency(expectedInfo, manifest)`：拿 Python 常量比 `module.json.in`。这两份**恰好都是旧的**，所以互相对得上 —— **两份陈旧产物互相印证，真实产物在外面独自漂移**。

**影响**：这是 F-01 能存在的直接原因。更严重的是它说明「有一个绿灯的对拍测试」不等于「这条不变量被守住了」。

**改动空间**

1. CTest 注册时接上探针：需要一个 `--print-json` 的模块信息探针目标（脚本的 `RunProbe` 已经预期了这个接口），把 Debug/Release 两个产物路径传进去。
2. 同步 `EXPECTED_PROVIDES` / `EXPECTED_WORKER`（否则第 1 步一接上就红）。
3. **把「探针缺失」从静默降级改成硬失败**——这是根治点。当前 `if probePath else expectedInfo` 这个写法本身就是缺陷模式：可选参数缺失时悄悄退化成自我比较。

**成本**：S–M（主要成本在做探针目标；若已有可复用目标则是 S）
**风险**：低。修复后可能暴露其他既有漂移，那是收益不是风险。

> 此条与既有经验一致：**对拍测试全绿不等于验过；接受它作安全网前先断言被测分支确实触发。**

### F-04 🟠 宿主用裸子串判定模块能力

**证据**：`apps/slicer_ui_host_sim/HostSliceProtocolRoute.cpp:27`

```cpp
if (!moduleInfo.contains("slice.rgbwsvt"))
```

`moduleInfo` 是 `QByteArray`，装的是整份 `pm_module_info` JSON 文本。这是**对整份 JSON 做子串匹配**，不是解析 `provides` 数组。

**影响**：只要 `"slice.rgbwsvt"` 这 14 个字符出现在 JSON 的**任何位置**——未来的 `capabilities` 描述、错误示例、注释字段、甚至某个能力名的前缀——判定就会返回「支持」。反过来，如果模块把能力名换成等价的转义形式（`.` 表示点号，JSON 合法），判定会返回「不支持」。

这是典型的「用文本匹配代替结构解析」，在能力集会增长的系统里迟早出事。

**改动空间**：`QJsonDocument::fromJson(moduleInfo)` → 取 `provides` 数组 → 精确元素匹配。宿主已经在别处大量使用 `QJsonObject`，没有新依赖。

**成本**：S ｜ **风险**：极低

### F-21 🟠 一个对外错误码在契约里根本不存在

**证据**（2026-09-08 复核）

`PM-SLICER-VIEWDATA-SIMPLIFICATION` 被当作对外错误码返回，出现在至少 5 处：

```
src/slicer_core/api/viewdata/MeshSimplifier.cpp:156, 166, 304, 319
src/slicer_core/api/viewdata/SceneViewMeshBuilder.cpp:621
```

而 `contracts/slicer_error_codes.json` 里**没有声明它**（该文件共声明 19 个码，代码共使用 19 个码，恰好一进一出：多了 `VIEWDATA-SIMPLIFICATION`、少用了 `LAYOUT-0021`——后者实际在 `apps/slicer_worker/` 里使用，不是问题）。

它也**不符合** `file_contract_v1.result.schema.json:39` 的码格式：

```
^PM-SLICER-[A-Z]+-(?:[0-9]{4}|STALE|BUDGET)$
```

`SIMPLIFICATION` 既非四位数字，也非 `STALE`/`BUDGET`。

**影响**

- 宿主可以收到一个**契约里不存在的错误码**。宿主若按错误码表做分支处理（这是错误码存在的意义），这一条会落到 default 分支。
- 目前没有炸，因为 `scene.get_viewdata` 是进程内能力，不经过 `result.json`，所以格式正则管不到它。**但这是巧合而非设计**：如果将来 ViewData 相关工作被移到 Worker（并非不可想象——大场景 ViewData 生成本身就重），这条码会立刻违反结果 schema。

**改动空间**：二选一

1. 在 `slicer_error_codes.json` 声明它，并把码名改成符合正则的形式（如 `PM-SLICER-VIEWDATA-0080`）——需同步 5 处代码与相关测试。
2. 声明它并显式记录「非数字后缀码仅限进程内能力」这一例外（`BUDGET`、`STALE` 已经是这类例外，说明这个设计本来就允许语义后缀）。

倾向 **2**：`PM-SLICER-VIEWDATA-BUDGET` 已经在 DTO 里存在且同样是语义后缀，说明例外是既定风格；把 `SIMPLIFICATION` 补进去比改码名成本低、破坏面小。

**成本**：S ｜ **风险**：低
**根治办法**：这一条与 F-01/F-03/F-05 同源，应当并入 R-10 的能力/错误码单一真源，并加一条对拍——「代码里出现的每个 `PM-SLICER-*` 字面量都必须在契约中声明」。这条对拍脚本约 20 行，本轮已用一次性脚本验证过它能跑出结果。

## B 类：分层与拓扑（3 条）

### F-06 🟠 base/engine 分层靠 CMake 白名单而不是目录结构

**证据**：`cmake/SliceSoftCoreLayering.cmake` 全文。分类逻辑 = 6 条路径前缀 + 33 条精确文件名（`baseExactStems`）+ 1 条精确源文件 + 3 条反向例外（`engineExactSources`），其余归 engine。

**影响**

- 好的一面：**默认方向安全**——新文件默认落 engine，即默认不进 DLL。
- 坏的一面：把一个重计算文件放进 `src/slicer_core/api/`、`scene/`、`layout/`、`model/`、`importers/` 任一目录，它会**静默进 base 并被链进 DLL**，没有任何警告。分层保护完全依赖开发者知道这份名单存在。
- 名单本身**没有自检**：没有测试断言「`baseExactStems` 的每一条都对应真实文件」（改名/删文件后名单会静默失效），也没有断言「base 集合的包含闭包不触及 engine 目录」。
  > **2026-09-14 更正**：本条低估了既有门禁。`slicer_stage14b_layering_feasibility_test` 确实是一条分层门禁，但它检的是「`model.cpp` 是否越出冻结 base parser 依赖边界」，不检名单完整性。**且它当前是红的**——实测报 `model.cpp acquired a project dependency outside the frozen base parser boundary`，命中 `model/AssetReferencePath.h`、`ObjFaceParser.h`、`MtlMaterialParser.h`、`FrameGeometry.h`。准确说法是：分层自检存在但覆盖面不同，且这条已红的门禁无人处理。
- 现有的链接期门禁（`model_import_layering_probe`、`package_query_facade_14b02_base_link_test`）能兜住**符号越界**，但兜不住**误分类**——一个重文件被分到 base 只会让 DLL 变大变重，不会产生链接错误。

**改动空间**

- 方案 1（彻底）：把 base 文件物理搬进 `src/slicer_core/base/`，规则退化成一条前缀。代价是 400+ 文件的路径变更，会与所有在飞分支冲突。
- 方案 2（渐进，推荐）：保留当前名单，但**加一条自检测试**：断言 `baseExactStems` 每条都存在、断言 base 源集合里没有 `pipeline/` `engine/` `support/` `materials/` `raster/` 前缀。这是纯增测试，零风险。
- 方案 3：把名单从 CMake 挪到一份 JSON，CMake 与自检脚本共读，避免规则只有 CMake 能读。

**成本**：方案 2 = S ｜ 方案 3 = M ｜ 方案 1 = L（且冲突面大）
**风险**：方案 2 极低；方案 1 高（大规模路径变更）

### F-08 🟡 CLI 绕过 DLL/Worker，「生产必须经 Worker」在引擎边界不成立

**证据**

- `apps/slicer_cli/main.cpp:1-12` 直接 include `slicer_core/slicer.h`、`engine/ProductionSliceFacadeFactory.h`，链接 `slicer_core`（= engine）。

**影响**：模块边界上的三道防线（DLL 不链引擎 / `backend` 只接受 `worker` / DTO `noInProcessFallback`）都是硬的，但**引擎边界是软的**——CLI 拿一份 `production=true` 的配置就能产出标记 `admitted` 的包。`file_contract_v1.md` §1 用文字声明了「CLI 包仍是候选」，但代码里没有对应的强制。

**改动空间**

- 方案 1（记账，推荐）：在 `docs/slice` 明确写下 CLI 通道的准入语义与它与 Worker 通道的差异，把「靠共识」变成「有文档」。

**成本**：方案 1 = S ｜ **风险**：低
**判定**：CLI 是内部开发者工具，不分发给终端用户，方案 1 足够。**不建议封堵。**

### F-09 🔴 `slicer.cpp` 5 888 行是唯一的技术债主体

**证据**（2026-09-08 复核）：`wc -l src/slicer_core/slicer.cpp` = **5 888**（09-06 时为 6 071；MEMFLOW 的三次「G2 同步下沉」提交把它拉回了一部分）。结构见 `02_模块级评估.md` §5.5 的逐段拆解。要点：

- 匿名 namespace 占 66–4117 行（**4 051 行，占 69%**），内含 25 个结构体 + 数十个自由函数，**全部无法被单元测试直接触达**。
- 对外只有 2 个 `run_slicer` 重载。
- 至少 7 个不相关关注点混在一起，其中手写 CRC32/adler32/zlib/PNG 编码（约 100 行，535–655 行）**与切片语义完全无关**。
- 它是四个在飞专项（MATOPQ / MO-04 / MATVOL / TRANSFER）的共同修改点。

**影响**

- 单元测试不可达 → 验证只能靠 golden 包整体对拍 → 定位一个语义 bug 的成本极高。
- 变更热点 + 巨型文件 = 合并冲突的常驻来源。
- 编译单元巨大，任何改动触发全文件重编（`/bigobj` 已经必须开）。

**改动空间**：见 `06_` R-12。核心原则是**小步搬 + 每步 golden 对拍**，绝不一次性重构。第一刀应当切在与切片语义无关的部分（PNG/zlib 编码 → `src/slicer_core/output/png/`），因为它零语义风险且能立刻验证方法论是否成立。

**成本**：XL（整体）｜ 单步 S–M
**风险**：**高**。这是生产路径核心。任何一步都必须有 golden 零漂移证据。

### F-42 🟠 构建版本计数器让「定向构建 + 定向验证」不可用，每次验证都被迫全量重建

**证据**：本轮独立复现 **三次**，每次都表现为"看起来像真回归的红灯"。

| # | 场景 | 失败测试 | 报的原因 | 真实原因 |
| --- | --- | --- | --- | --- |
| 1 | P0-02 只重建 `slicer_module` | `stage14c05_module_info_tests`、`slicesoft_version_contract_test` | `0.2.465-dev != 0.2.467-dev` | 测试 exe 未重建 |
| 2 | P0-04 证伪时只重建探针目标 | `stage14d03_worker_contract_unit_tests` | `real worker reports the manifest-derived engine version` | 二进制时间戳 10:48 vs 13:31 |
| 3 | 产物清理后只重建三个目标 | `slicesoft_version_contract_test` | `slicer_cli --version drifted` | `slicer_cli` 未重建 |

三次全部在**全量重建后自愈**，语义无任何问题。

**机理**：`SLICESOFT_SLICER_IMPLEMENTATION_VERSION` 带自增构建计数（如 `0.2.467-dev`），被**编译进**每个链接它的二进制。任何一次部分构建都会推进计数，使已重建与未重建的产物报出不同版本，而多处契约测试正是比对这个版本串。

**影响（这才是要紧的）**

1. **定向验证事实上不可用**：改一个文件后想只跑相关测试，会随机撞上版本红灯。每次验证都被迫全量重建——本仓库 Debug 全量约 **10 分钟**，而定向构建约 1 分钟。
2. **红灯有伪装性**：报的是 `engine version`、`--version drifted` 这类像真回归的措辞，不是"你没重建"。我第一次就误判了，靠比对二进制时间戳才定责。
3. **叠加 F-41**：负载假失败 + 版本假失败两类噪音同时存在时，一次全量回归的红灯需要逐条定向复跑才能定责，排查成本显著。

**改动空间**

- 方案 A：让版本计数只在**显式发版**时推进，日常构建用稳定占位（如 `0.2.0-dev`）。根治，但要确认没有流程依赖每次构建都换号。
- 方案 B：把版本一致性检查从"逐二进制比对"改为"只校验与构建清单一致"，允许同一次构建内的产物共享版本。
- 方案 C（最低成本）：在 `AGENTS.md` 与任务卡模板里写明「**任何回归验证前必须全量重建**」，把它从隐性陷阱变成显性纪律。

**成本**：C = S ｜ B = M ｜ A = M（需确认发版流程）
**风险**：A/B 触碰版本治理（有 `DOC_DECISION_VERSION` 在管），需裁定；C 无风险。

**建议先做 C**——三次误判都源于"不知道有这条规则"，写下来即可消除大部分成本。

### F-43 配置来源面分散成五种写法，且无统一登记

`load_slice_config` 有 **38 个调用方**。喂给它的配置由五种互不相同的方式产生：

| # | 来源面 | 规模 | 本轮是否需改 |
|---|---|---|---|
| 1 | `samples/configs/**.json` | 124 份 | 是（补齐 35 份） |
| 2 | 测试源码里的 C++ 字符串字面量 | 9 处 / 7 文件 | 是 |
| 3 | 程序化构造 `Json::Object`（如 `WorkerPreflightExecutorTests::MakeProfile`） | 若干 | 否（本就声明） |
| 4 | 纯 C 宿主 `HostRequestBuilder.c`（规范形式 + 紧凑形式**双份**） | 3 个 builder | 否（本就声明） |
| 5 | 引擎侧回读调用方传入的 Profile 路径 | 5 处 | 否（契约上由调用方负责） |

**为什么这构成问题**：契约一变，五面都要跟上，而**没有任何东西告诉你共有几面**。按键名 grep 还会漏——`\"modelPath\"`（C 字符串字面量形态）只命中 10 个文件，去掉转义限定后是 41 个，差的那 31 个里就有第 3 类写法（`{"modelPath", ...}` 用的是普通引号）。

**实际代价**：P0-07 的范围判断错了三次，共四轮才收敛。

| 轮次 | 判据 | 怎么发现不够的 | 补齐 |
|---|---|---|---|
| 一 | 盘上 `.json`，要 `input.modelPath` **且** `output.packageDir` | 回归第 69 项 `experimental_config` 变红 | 34 份 |
| 二 | + 源码内字符串字面量 | 全量复核 124 份配置时发现漏网 | 9 处 |
| 三 | 放宽为只看 `input.modelPath` | 全量回归点名 5 项 | 1 份 |
| 四 | **谁写出配置文件** | —（收敛） | 5 处 |

前三轮错在同一处：盯着**谁加载**配置（`load_slice_config` 的调用方）。但测试可以造好配置
交给上层入口，由它内部加载——按调用方枚举必然漏掉这一类。正确判据是**谁写出配置**。
四轮全部靠红灯发现，没有一轮是靠事先枚举发现的。

**已落的缓解**：`slicing_mode_declared_contract_test` 覆盖第 1 面（124 份全查，含「发现数为 0 即判空转」的自检）。**第 2~5 面仍然只能靠人**。

**若要根治**：让配置只有一个生成器（或至少让每一面都有自己的门禁）。属 M 级，不在 P0 范围。

**方法论结论（须与 F-44 合看）**：第四轮时做过一次判据放宽后的静态枚举，得到 **87 个可疑文件**，
而回归实测只有 **5 个**真坏——静态枚举在错判据上欠拟合、在对判据上过拟合 17 倍，两头都不准。
**回归本身才是准确的枚举器**，唯一让它不可用的因素是 F-44 的挂死：坏 fixture 吃满超时，
且带着已知坏 fixture 跑完的失败集失去归因价值。

所以两条的正确关系是 **F-44 是 F-43 昂贵的原因**。把未捕获异常改成快速失败之后，
「改完跑一轮回归、按它点名的修、重复到收敛」就是最省的做法，不必事先把五个来源面枚举干净。
先修 F-44，F-43 的代价随之塌缩。本轮因为挂死而转向静态枚举，是被迫的、且代价高于收益。

### F-44 单测未捕获异常挂死而非快速失败

`output_resolution_config_unit_tests` 在 P0-07 首轮回归中启动后 **CPU 仅 0.078 秒却一直不退出**，卡在第 71/249 项——未捕获的 C++ 异常没有让进程快速失败，而是被 Windows 错误报告接管，停在那里等 ctest 超时。

**影响的是排期决策而非功能**：如果一次改动打坏了 N 个共享 fixture，回归不是「快速红 N 次」，而是额外 N × 超时（本仓部分项超时设到 180 秒）。这直接否定了「改完就跑全量、让回归替我找范围」这一策略——对 F-43 那种分散来源面，事先静态枚举是**必须**的而不是可选的。

**识别方法**：`Get-Process <name> | Select Name,Id,CPU,StartTime`，CPU 接近 0 而已启动数分钟即为挂住，应直接掐掉——带着已知坏 fixture 跑完的失败集没有归因价值。


### F-45 `slicer.config.1` 归一化静默丢弃白名单外的全部键

`NormalizeConfigJson` 对 `schema: "slicer.config.1"` 的配置调用 `NormalizeSlicerConfig1`
（`src/slicer_core/config/ConfigMigration.cpp:18-61`），它**按白名单逐键搬运**：顶层 11 个键、
`pipeline.slicingMode`、`geometry` 下 3 个、`materials` 下 8 个。白名单以外的一切**静默丢弃**——
不报错、不告警。`DetectConfigSchemaKind` 只校验 schema 的**名字**，全仓没有未知键拒绝。

**两条可验证的后果**：

1. **有些设置经 v1 根本无法表达。** `background`（`config.cpp:248`）与 `geometrySampling`
   （`config.cpp:676`）都从 legacy root 读取，但两者都不在白名单里。也就是说同一个功能，
   legacy 配置能配、v1 配置配了等于没配，而作者拿不到任何信号。
   `background.value` 决定空白像素取值，`geometrySampling.strategy` 是 relief 候选策略的闸门，
   都不是无关紧要的项。

2. **仓库自己的 v1 样例就踩了。** `samples/configs/schema_v1/slicer_config_v1_basic.json`
   声明了顶层 `diagnostics`、`materials.textureApplication`、`materials.varnishGeometry`，
   三块均不在白名单中，全部被丢弃。

**本轮是怎么撞上的**：P0-07 给 v1 样例补 `slicingMode` 时误加在顶层。文件里**看得见**该键、
门禁（当时只查顶层）报绿，而引擎在归一化后仍判「未声明」并拒绝——错误信息与文件内容直接矛盾。
这正是该缺陷最难查的形态：证据摆在眼前却与行为不符。

**已落的缓解**：`slicing_mode_declared_contract_test` 按 schema 分档指认正确位置，
并**反向**拒绝「v1 配置带被忽略的顶层 slicingMode」。但这只覆盖 `slicingMode` 一个键。

**建议**：先给 `NormalizeSlicerConfig1` 加未知键拒绝（S 级，把静默变成报错），
再决定要不要补全映射（M 级）。补全映射之前，未知键拒绝会让第 2 条里那三块立即变红——
那是真实债务浮出水面，不是新增回归。


### F-46 `.gitignore` 的 `tests/` 白名单漏掉 25/35 个目录，新增文件被静默忽略

`.gitignore` 第 18 行 `tests/*` 忽略 `tests/` 下一切，随后用 `!` 逐个放回：

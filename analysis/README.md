## 1. 一句话结论

**这套软件的边界设计（宿主 ↔ DLL ↔ Worker 进程）是同类项目里少见的扎实，「DLL 调用 EXE」不但合理，而且是整个架构最值得保留的部分；真正的债集中在引擎内部（`slicer.cpp` 5888 行单文件）、契约的多份手写副本（已实测漂移），以及工程验证基础设施（无 CI、无测试框架、单文件 3315 行 CMake）。**

换句话说：**架构对了，内脏和工装没跟上。**

## 2. 结论摘要（按用户三个问题回答）

### 问题 1：哪些模块与逻辑合理，哪些不合理？

**合理且应当保留（不要动）**

| 模块 | 为什么合理 |
|---|---|
| 公共 C ABI（`contracts/print_module_spi.h`，11 个 `pm_*` 导出） | 跨 DLL 边界只有 C 基本类型 + UTF-8 字符串 + 不透明句柄，缓冲区协议统一，异常不逃逸；避开了 MSVC 运行时/STL ABI 陷阱 |
| 宿主 → DLL 的加载方式 | Qt 宿主对 `src/slicer_core` **0 处 include**，运行时 `LoadLibrary` + 逐符号 `GetProcAddress`，不链导入库。边界不是靠约定，是靠构建结构 |
| DLL → Worker 的进程隔离 | `slicer_module` 只链 `slicer_base`，引擎**根本不在 DLL 里**——「进程内切片」不是被禁止，是编译期不可能；并有链接期门禁 |
| Facade + 工厂注入接缝 | `api/Facades.h` 纯抽象 + `engine/Production*FacadeFactory` 注入，是全项目最干净的接缝 |
| `file_contract_v1` 的失败关闭设计 | 版本先握手、无静默回退、取消/超时/staging 清理的所有权与顺序全部写死并有 schema |
| 流水线路由无静默回退 | `SlicePipelineRouter` 请求模式与生效模式分离、阻塞原因可审计 |

**有条件合理（设计对，实现或治理有缺口）**

| 模块 | 缺口 |
|---|---|
| 能力契约体系 | 同一份能力清单被**手写了 6 份**（`ModuleInfo.cpp` 字符串、`module.json.in`、`slicer_capability_dtos.json`、`file_contract_v1.*.schema.json`、`version-manifest.json`、测试里的 Python 常量），已实测漂移（F-01/F-03/F-05） |
| base/engine 分层 | 分层规则是 CMake 里的路径前缀 + 精确文件名白名单，不是目录结构；新文件默认落 engine，把引擎文件放进 `api/` 会静默进 base（F-06） |
| Worker 协议实现 | 管道排空、Job Object、取消都对；但日志/进度是无上限 `vector`，整个作业期堆在 DLL 内存（F-12） |

**不合理（应当改）**

| 模块 | 问题 |
|---|---|
| `src/slicer_core/slicer.cpp` | **5888 行**，50+ 结构体 + 手写 CRC32/zlib/PNG + 栅格采样 + 支撑生成 + 纹理列 + 材质策略 + 层合成全在一个匿名 namespace（66–4117 行，占 69%），对外只有 2 个 `run_slicer` 重载（F-09） |
| RIP 集成拓扑 | `print_module_spi.h` 开篇写明「切片、RIP、未来扩展**都**通过本接口接入宿主」，实际 RIP 由 Qt 宿主 `QProcess` 直拉 `rip_cli.exe`，1377 行控制器住在 UI 可执行文件里，`src/rip_integration` 直接链进宿主（F-07） |
| 模块自述的对拍测试 | `ValidateModuleInfoContracts.py` 在 CTest 里注册时**没传探针参数**，于是「运行时自述是否漂移」的断言变成 `expectedInfo != expectedInfo` —— 整条空转（F-02） |
| 工程验证基础设施 | 无 CI（无 `.github/workflows`）；242 处 `add_test` / 173 个构建目标全塞在 3315 行单文件 CMake；无测试框架，每个用例手写 `main` + 自制 `ExpectTrue`（F-16/F-17/F-18） |
| 配置面 | `config.h` 488 行 39 个结构体聚成一个 `SliceConfig`，引擎入口是 `run_slicer(config_path)`——一个 JSON 文件驱动全部行为（F-10） |

### 问题 2：改动空间与扩展预留

- **不合理项的改动空间**：36 条问题里 **5 条是 1–3 天可闭环的低风险修复**（R-01..R-05），**4 条是建立自动保护的中等改造**（R-06..R-09），**4 条是需要用户立项授权的结构性大改**（R-10..R-13）。详见 `04_` 与 `06_`。
- **合理项的扩展预留**：Facade 接缝、流水线路由、导入器目录、Worker 承载者参数化**都有预留且成本可控**；唯一没有预留的是**能力清单本身**——实测新增一个切片能力要手工同步 **17 处、跨 4 种语言**，实际只同步了 15 处，F-01 就是这么漏出来的。详见 `05_`。

### 问题 3：DLL 调用 EXE 是否合理？

**合理，且在当前约束下是最优解。** 完整论证与六方案对比见 `03_调用方式专题_DLL调用EXE.md`。要点：

1. 切片是长时（10 µm 量级作业以十分钟计）、可能断言失败的重计算——放进宿主进程，一次崩溃就带走用户整个工作区。（原先此处引用的「六通道 Dense 62.2 GB vs 物理 31.6 GB」已被 MEMFLOW 根治，是历史值，不再是现役论据——见 §1.5。）
2. 宿主 `PrintApp` 是**别人的程序**，集成点只能是 DLL；真正干活的是 EXE。所以拓扑本质是「宿主内的一段协调代码 fork 出一个计算进程」，与 Chrome / VSCode / 编译器驱动同形。
3. 隔离是**结构性**的（DLL 不链引擎），不是运行时开关，强度远高于「约定不要在进程内切片」。
4. 只有 4 个次优点（进程冷启动与模型重复解析、日志无界累积、并发写死 1、取消延迟无实测数），全部可在不推翻拓扑的前提下改。

**判定：保持当前调用方式。不建议改成进程内 DLL、线程池、gRPC 或去掉 DLL 直连 Worker。** 唯一值得未来评估的是「常驻 Worker + 命名管道」，但必须先测出进程启动与重复解析的实际占比再决定（本轮未测）。

## 4. 分析口径与免责

**证据等级**（沿用 `AGENTS.md` 的分级）：

- **A｜当前代码/配置/构建脚本**：本报告中带 `文件:行号` 的每一条结论都是 A 级，可逐条复核。
- **B｜`docs/slice` 正式文档与 `AGENTS.md` 记录**：例如「Release 基线已作废」「CTest 234 项」「6 项既有失败」——**未复测**，引用时已标注。其中「62.2 GB / 31.6 GB 内存实测」已确认过期（见 §1.5），「CTest 234 项」也已过期（静态 `add_test` 现为 242）。

## 1. 运行时拓扑

### 1.1 三进程 + 两种边界

```
┌─────────────────────────────────────────────────────────────────────┐
│ 进程 1：宿主 EXE                                                      │
│   生产形态 = 打印软件 PrintApp（外部程序，本仓库不拥有）                  │
```

### 1.2 关键结构事实

| 事实 | 证据 |
|---|---|
| DLL 只链 base，不链 engine | `CMakeLists.txt` `target_link_libraries(slicer_module PRIVATE slicer_base)` |
| 引擎在 engine 静态库，只有 Worker/CLI/基准工具链接它 | `add_library(slicer_engine STATIC ...)`；`slicer_core INTERFACE → slicer_engine` |
| Qt 宿主对引擎零依赖 | 对 `apps/slicer_ui_host_sim` 全目录 grep `slicer_core`：**0 个文件命中** |
| 宿主不链模块导入库 | `apps/slicer_ui_host_sim/ModuleClient.h` 定义 `PM_MODULE_STATIC` 只为拿类型声明；符号全部运行时解析 |
| Worker 路径由 DLL 自身位置推导 | `WorkerJobService.cpp:43-68` `GetModuleFileNameW(&__ImageBase)` → 同目录 `slicer_worker.exe` |
| 进程内切片被三重封死 | ① DLL 不链引擎（编译期）② `options.backend` 只接受 `"worker"`（`CapabilityCarrierRouter.cpp` `NormalizeWorkerOnlyBackend`）③ DTO `protocolInvariants.sliceBackend.noInProcessFallback = true` |
| 链接期分层门禁存在 | `model_import_layering_probe`、`package_query_facade_14b02_base_link_test` 都只链 `slicer_base`，若 base 侧误引入 engine 符号则链接失败 |

## 2. 一次生产切片的完整调用链

以宿主点「开始切片」为例（A 级，逐跳可查）：

| # | 位置 | 动作 | 传输形态 |
|---|---|---|---|
| 1 | 宿主 | 组装能力请求 JSON（`capability` + `scene` + `profile` + `output`） | 内存字符串 |
| 2 | 宿主 → DLL | `pm_submit(module, request_json)`，立即返回句柄 | **序列化 1**：UTF-8 JSON 字符串跨 ABI |
| 3 | DLL | `CapabilityCarrierRouter::Route` 判定承载者；`NormalizeWorkerOnlyBackend` 强制 `backend=worker` | 内存 |
| 4 | DLL | 私有作业目录 `%TEMP%/slicesoft-module/<pid>/module-<id>/job-<id>/` | 文件系统 |
| 5 | DLL | 首次访问该 Worker 身份时先跑 `slicer_worker.exe --contract-info`（5 s 超时）校验 major/minor/produces/capabilities | **额外一次进程启动** |
| 6 | DLL | `WriteJsonAtomically` 写 `request.json`（先 `request.tmp` 再 `rename`） | **序列化 2**：JSON 落盘 |
| 7 | DLL | `CreateProcessW(..., CREATE_SUSPENDED)` → `AssignProcessToJobObject` → `ResumeThread` | 进程 |
| 8 | Worker | 解析 `request.json` → `WorkerJobDispatcher` 按 capability 分发 → `WorkerSliceRequestMaterializer` 物化 effective config | **序列化 3**：再落一份配置文件 |
| 9 | Worker | `ProductionSliceFacadeFactory` → `SliceFacadeAdapter` → `ReadSceneEffectiveConfig(path)` → `MultiModelProductionService` / `run_slicer` | 文件读回 |
| 10 | Worker | 每层输出 `SLICE_PROGRESS phase=... percent=...` 到 stdout | 文本行 |
| 11 | DLL | 10 ms 轮询 `WaitForSingleObject` + `PeekNamedPipe` 排空（单次预算 256 KB） | 管道 |
| 12 | Worker | 写包到 `<packageDir>.staging.*` → 自检 → 原子发布 → 删 backup → 写 `result.json` → 退出 | 文件系统 |
| 13 | DLL | 读 `result.json`，用 `code` 作为权威稳定错误码（退出码只带分类） | JSON 读回 |
| 14 | 宿主 | `pm_poll` 拿进度快照（建议 200–500 ms），终态后 `pm_result` 取结果 | ABI 字符串 |

**要点**：`scene` 是**引用式**的（模型文件路径 + 变换 + 哈希），不是几何数据。因此 request.json 很小；代价是**模型文件被解析两次**（DLL 为 viewdata/collision 解析一次，Worker 为切片再解析一次）。

## 4. 分层规则（base vs engine）

分层不是靠目录，是靠 `cmake/SliceSoftCoreLayering.cmake` 的一段过滤函数：

```
basePrefixes（整目录归 base）：
  src/third_party/miniz/  src/slicer_core/api/  src/slicer_core/importers/
  src/slicer_core/layout/ src/slicer_core/model/ src/slicer_core/scene/

baseExactStems（逐文件点名归 base，共 33 条）：
  config/OutputResolution, diagnostics/Diagnostics, geometry/TriangleMeshData,
  output/rgbwsv/RgbwsvPackage, preview/TiffLayerSource, system/Sha256,
  rip_reader, texture_image, model, json_value, ...

engineExactSources（例外中的例外，从 base 拽回 engine，共 3 条）：
  model/ModelLoadConfigAdapter.cpp, scene/SceneEffectiveConfig.{cpp,h}

其余一切 → engine
```

**这条规则的实际含义**：

- 新增文件**默认落 engine**，即默认不会被 DLL 链接 —— 默认方向是安全的。
- 但把一个重计算文件放进 `src/slicer_core/api/` 或 `scene/`，它会**静默进 base 并被打进 DLL**，没有任何警告。分层保护依赖开发者知道这份名单存在。
- 名单本身没有自检：没有测试断言「`baseExactStems` 里每条都存在」或「base 集合的传递依赖闭包不含 engine 目录」。链接期门禁（`*_base_link_test`）能兜住符号层面的越界，但兜不住「一个重文件被误分类进 base」这种**不产生链接错误、只让 DLL 变大变重**的情况。

详见 04_ 的 F-06。

## 5. 契约清单（谁是谁的真源）

| 契约 | 文件 | 版本 | 边界 |
|---|---|---|---|
| 公共调用 ABI | `contracts/print_module_spi.h` | `PM_SPI_VERSION 1` | 宿主 ↔ DLL |
| 公共能力 DTO | `contracts/slicer_capability_dtos.{json,md}` | `contractVersion 1.14` | 宿主 ↔ DLL（请求/响应字段） |
| 三车道交互 | `contracts/slicer_three_lane_contract.{json,md}` | 1.1 | 宿主行为约束（Transient/Commit/Production） |
| 私有进程契约 | `contracts/file_contract_v1.md` + 4 个 schema | major 1 / minor 1 | DLL ↔ Worker |
| 生产包 | `p0.rgbwsv.2.schema.json`、`p0.rgbwsvt.1.schema.json` | — | 切片 → RIP |
| 模块自述 | `slicer_module_info.schema.json` + `ModuleInfo.cpp` 硬编码字符串 | `slicesoft.module_info.1` | 宿主装载判定 |
| 部署清单 | `slicer_module_manifest.schema.json` + `module.json.in` | `slicesoft.module_manifest.1` | 打包/分发 |
| 版本治理 | `version-manifest.json` | `releasePolicy: lockstep` | 全局 |
| RIP 模块 | `slicesoft.rip.module.1.schema.json` | status `LOCAL_ENGINEERING_ONLY` | 宿主 ↔ 外部 RIP |

**注意 `releasePolicy: lockstep`**：`application` 与 `slicer` 版本必须一致（`PackageSlicerModule.ps1` 会校验）。这是一条深思熟虑的治理决策，但它在事实上抵消了模块化最主要的一项收益——**模块本可以独立于宿主发版**。这不是缺陷，是取舍；只是取舍的代价应当被明确记账（详见 05_ §6）。

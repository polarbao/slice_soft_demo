## 1. 威胁模型（为什么这章有必要）

这个模块的部署形态决定了它的安全要求高于普通桌面软件：

```
slicer_module.dll 被装载进第三方打印软件 PrintApp 的进程地址空间
   ↓
DLL 内的任何崩溃 = PrintApp 崩溃 = 用户丢失打印软件里的全部未保存状态
   ↓
而 DLL 承担 13 项【进程内】能力：model.import / scene.* / geometry.collision
   / package.verify / package.render_layer_preview / package.read_report …
```

**关键推论**：`03_` 论证的进程隔离保护的是**切片**（重计算在 Worker 里，崩了不影响宿主）。但**进程内能力没有任何隔离**——它们直接在宿主地址空间里解析模型文件、解析 JSON、分配网格与预览缓冲。

> **一句话概括本章：进程隔离把最重的计算挡出去了，但把所有的输入解析留在了里面。**

### 输入面清单

| # | 输入 | 来源可信度 | 承载位置 |
|---|---|---|---|
| 1 | `pm_submit(request_json)` | 宿主构造，但内容含用户选择的路径与参数 | **DLL 进程内** |
| 2 | `pm_create(options_json)` | 宿主 | **DLL 进程内** |
| 3 | 模型文件（STL / OBJ / 3MF / MTL / 贴图） | **用户提供，完全不可信** | **DLL 进程内**（`model.import`） |
| 4 | 工艺预设 JSON（`configs/material_process/*.json`） | 部署目录，半可信（可被替换） | **DLL 进程内** |
| 5 | 切片配置 JSON（CLI 手写、effective config） | 开发者/用户手写 | Worker 进程 |
| 6 | 生产包（`package.verify` / `read_report` / `render_layer_preview`） | 可能是外部拿来的包 | **DLL 进程内** |
| 7 | `result.json` | Worker 写，DLL 读 | DLL 进程内（可信） |
| 8 | RIP 输出目录 | 外部 RIP SDK 产出 | 宿主 exe（`rip_integration`） |

**第 3、4、6 项是真正的不可信输入，而它们全部在 DLL 进程内解析。**

## 2. 已有防护（做得好的部分 ✅）

这个项目在文件系统安全上的用心程度明显高于平均水平，逐条列举：

### 2.1 递归删除前查重解析点 ✅✅

`src/slicer_core/api/artifacts/PackageArtifactSafety.cpp:64-113`：

```cpp
bool IsReparsePoint(const std::filesystem::path& path) {
    if (std::filesystem::is_symlink(std::filesystem::symlink_status(...))) return true;
#ifdef _WIN32
    const DWORD attributes = GetFileAttributesW(filesystemPath.c_str());
    return attributes != INVALID_FILE_ATTRIBUTES
        && (attributes & FILE_ATTRIBUTE_REPARSE_POINT) != 0U;   // ← 连 junction 也拦
#endif
}

bool RemoveOwnedDirectory(...) {
    ...
    if (IsReparsePoint(path)) {
        errorMessage = "owned artifact is a reparse point: " + ...;
        return false;                                            // ← 拒绝删除，不跟随
    }
    std::filesystem::remove_all(filesystemPath, error);
}
```

**这挡掉的是一类经典攻击**：把 `<packageDir>.staging.xxx` 换成指向 `C:\Windows` 的目录联接，让清理逻辑替攻击者做递归删除。Windows 上光查 `is_symlink` 是不够的（junction 不是 symlink），这里**两种都查了**。这是有人真的想过这个问题才会写出来的代码。

### 2.2 删除范围被契约限制在同级派生命名 ✅

`contracts/file_contract_v1.md` §7：

> Cleanup must be path-normalized and limited to sibling names derived from the request's exact `packageDir`. Recursive deletion outside that parent directory is forbidden.

契约级约束 + 实现级 reparse point 检查，两层。

### 2.3 包目标租约（防并发互相踩） ✅

`PackageArtifactSafety.cpp:300-325`：用 `create_directory` 的**原子性**作为锁（成功即获得租约，失败即已被占用），再写 `owner.txt` 记录持有者；写失败则回滚删除租约目录。这是 POSIX/Win32 上做跨进程互斥的正确低成本手法。

### 2.4 二进制 STL 的头部自校验 ✅

`model.cpp:709-721`：

```cpp
bool looks_like_binary_stl(const std::filesystem::path& path) {
    const std::uintmax_t size = std::filesystem::file_size(path);
    if (size < 84U) return false;
    input.seekg(80); const std::uint32_t triangle_count{read_u32_le(input)};
    return size == 84ULL + static_cast<std::uintmax_t>(triangle_count) * 50ULL;   // ← 严格等式
}
```

**这条严格等式顺带挡掉了一个分配炸弹**：一个声称有 40 亿三角形、实际只有 100 字节的 STL 头，不会通过这个判定，因此不会进入 `load_binary_stl` 去按 `triangle_count` 分配。三角数被文件实际大小硬约束住了。（不确定这是刻意的还是格式判定的副产品，但效果是真的。）

### 2.5 Worker 侧的路径与标识符校验 ✅

- `WorkerApplication.cpp:138-146`：`--spi-request` **拒绝相对路径**。
- `file_contract_v1.md` §3：模块必须拒绝相对请求路径、拒绝含路径分隔符的 `jobId`，并拒绝 `jobId`/`correlationId`/`capability` 与请求不匹配的结果。
- `request.schema.json` 的 `jobId` 用正则钉死：`^[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` —— 不含 `/`、`\`、`..`，**从 schema 层面就不可能构造穿越**。

### 2.6 篡改负例已入测试 ✅

`tests/stage14c_05/ValidateModuleInfoContracts.py:230-241` 的 `ValidateTamperCases` 明确测了：

- `absolute DLL path`（清单里写绝对路径 → 必须被 schema 拒绝）
- `Worker path traversal`（Worker 路径穿越 → 必须被拒绝）
- `legacy delayLoad field`（遗留字段 → 必须被拒绝）

另有 6 个坏 3MF 负例 fixture：`bad_3mf_missing_rels` / `texture_decode_failed` / `texture_path_missing` / `unknown_material_id` / `unsupported_compositematerials` / `unsupported_multiproperties`。

> ⚠ 但注意：**这些负例住在 `ValidateModuleInfoContracts.py` 里，而该脚本的运行时探针分支是空转的（`04_` F-02）**。篡改负例本身走的是 schema 校验路径、不依赖探针，所以这部分**仍然有效**；受影响的只是「运行时自述是否漂移」那一条。为避免误判，这里明确区分开。

### 2.7 跨代码页路径已专项处理 ✅（2026-09-08 刚落地）

`42507df` / `d85c619` / `5e06dd7` / `1a57bfe` 四个提交完成了 UNIPATH 专项：Worker 改用宽命令行，配置/预检/临时产物/材质报告/包预览路径统一显式 UTF-8↔native 转换，并补了跨代码页回归（中文资源导入 + Worker 切片）。提交信息记录「三代码页 25 层 Worker 写包、严格校验、预览通过，TIFF 摘要一致」。

**这是一类容易被忽略的健壮性问题（非 ASCII 路径在 `narrow`/`wide` 边界上静默失败），已经被当成专项处理掉了。**

## 3. 缺口

### F-33 🔴 自研 JSON 解析器无递归深度上限，且它跑在 DLL 进程内

**证据**：`src/slicer_core/json_value.cpp`（452 行，手写递归下降）：

```
:29  Json parse_value()   → :36 return parse_object();  → :72 object.emplace(key, parse_value());
                          → :39 return parse_array();   → :91 array.push_back(parse_value());
```

`parse_value` ↔ `parse_object` / `parse_array` **互相递归，没有任何深度计数或上限**。全文件搜 `depth` 只命中 `dump_impl` 的缩进参数（输出侧），解析侧无。

**后果**：形如 `[[[[[[...]]]]]]` 的深嵌套输入 → 递归深度 = 嵌套层数 → **栈溢出**。Windows 默认线程栈 1 MB，每层递归几十字节栈帧，量级上**万级嵌套即可触发**。栈溢出在 Windows 上是不可捕获的（`EXCEPTION_STACK_OVERFLOW`，`catch(...)` 接不住），所以：

> **一个几十 KB 的畸形 JSON 就能让装载了本 DLL 的打印软件进程直接消失，而且 ABI 不变量第 4 条「任何导出函数都不得让异常逃逸」在这里失效——栈溢出不是异常。**

这**直接抵消了进程隔离的目的**。输入面第 1、2、4、6 项都会走到这个解析器。

**改动空间**：给解析器加深度计数（超过阈值抛 `std::runtime_error`，被现有的 `catch` 链转成 `PM-SLICER-INPUT-0002`）。阈值取 64 或 128 就足够——真实配置的嵌套深度个位数。

**成本**：S（约 10 行）｜**风险**：极低（纯加闸；需确认现有 fixture 无超深嵌套）
**这是本轮所有新发现里最该先修的一条。**

### F-34 🟠 模型导入无规模上限，OOM 落在宿主进程

**证据**：对 `model.cpp` / `importers/` / `ModelCapabilityAdapter.cpp` 搜 `file_size|max_bytes|size_limit|too_large` —— 唯一命中是 `model.cpp:710` 的格式判定（§2.4），**没有任何规模上限**。

`SceneViewMeshBuilder` 里的 `triangleLimit` / `AllocateTriangleBudgets`（:192-206,536-547）是 **ViewData 的渲染 LOD 预算**，作用于「已经加载完的网格」之上，不是导入闸门。

**后果**：`model.import` 是 `in_process` 能力（`slicer_capability_dtos.json` carrier 声明）。一个 2 GB 的 ASCII STL 或高面数 OBJ 会在**宿主地址空间**里被解析和分配。`AGENTS.md` 已记录 `85e3fbd`「高面数导入·消除拓扑与触底哈希热点」这类性能工作，但那是快，不是**限**。

**改动空间**：三层可选，建议都做

1. `pm_create(options_json)` 支持 `maxModelBytes` / `maxTriangles` 配额（SPI 早就留了这个入口，`pm_module_info` 也已经有 `capabilities` 自述字段可以声明配额）。
2. 导入前用 `file_size` 做前置拒绝（廉价，不必读完文件）。
3. 解析中按三角数增量检查，超限抛 `PM-SLICER-RESOURCE-0041`（该码已存在）。

**成本**：M ｜**风险**：中（会拒绝一些当前能跑通的大模型，需产品定阈值）

### F-35 🟠 进程内能力整体没有资源配额概念

F-34 是它的一个实例。更一般地：`model.import`、`scene.get_viewdata`、`package.render_layer_preview`、`package.read_report` 都在宿主地址空间分配，而 SPI 与 DTO 里**没有任何 quota / 上限 / 背压机制**。

`slicer_capability_dtos.json` 里唯一相关的是 `viewDataRules.budgetExhaustion`：

> "reduce geometry or image resolution, then PM-SLICER-VIEWDATA-BUDGET; never drop"

——**只有 ViewData 一条能力有预算语义**，其余进程内能力没有。

**改动空间**：把「进程内能力的资源配额」作为一条协议不变量写进 DTO（与 `sliceBackend.noInProcessFallback` 同级），并在 `pm_create` 的 options 里给出可配置项。**属受控修订，需用户裁定。**

**成本**：M（协议）+ M（实现）｜**风险**：中

### F-36 🟡 `catch(...)` 兜不住的三类故障未被记账

ABI 不变量第 4 条要求异常不逃逸，`CapabilityCarrierRouter::Route` 等处也确实有 `catch(...)` 兜底。但 Windows 上以下三类**不是 C++ 异常**，`catch(...)` 接不住（除非开 `/EHa` 并显式处理 SEH，本项目未见）：

| 故障 | 触发面 | 后果 |
|---|---|---|
| 栈溢出 | F-33 的深嵌套 JSON；`slicer.cpp` 里若有深递归 | 进程直接消失 |
| 访问违规 | 几何算法越界（`AGENTS.md` 记录过 `ff21b0c`「定位并修复发布收尾越界」） | 同上 |
| `std::bad_alloc` 之外的 OOM | F-34 的大模型；Windows 上大分配失败可能是 `bad_alloc`（可接），但栈上或 `reserve` 失败路径不一定 | 视情况 |

**建议**：不是要去接 SEH（那会带来更多问题），而是**把这条限制明确写进 `print_module_spi.h` 的 ABI 不变量说明**——现在第 4 条读起来像是承诺「本 DLL 绝不会让宿主崩溃」，而实际保证只覆盖 C++ 异常。宿主集成方需要知道真实边界。

**成本**：S（文档）｜**风险**：极低

## 5. 本章结论

**安全面的形状很反直觉，值得单独讲一遍：**

这个项目在**文件系统安全**上做得比大多数同类项目好——reparse point 检查、租约、契约级删除范围限制、schema 级 jobId 正则、篡改负例入测试，这些都是有人认真想过才有的东西。

但在**输入解析健壮性**上有一个结构性缺口：**所有不可信输入的解析都留在了 DLL 进程内**，而进程隔离只保护了切片计算。最便宜也最该先修的是 F-33（JSON 深度上限，约 10 行），因为它把「一个畸形配置文件」变成了「打印软件崩溃」，量级上完全不成比例。

顺带一个观察：`03_` 得出的「进程隔离做得硬」的结论**仍然成立，但边界比我上一版写的要窄**——它硬在「重计算不在宿主进程」，不硬在「不可信输入不在宿主进程」。这两件事被混为一谈过。

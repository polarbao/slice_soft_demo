`03_` §2.1 用「六通道 Dense 62.2 GB vs 物理 31.6 GB」作为进程隔离的正当性论据。**这个数字现在是历史值。** 2026-09-06 之后 MEMFLOW 专项已合入产品分支（`0d6396b`、`a226553`），实测结果：

| 项 | 改前 | 改后 | 提交 |

**这也是一条方法论教训**：我上一轮把一个被引用的实测数字当成了系统的固有属性，而它其实是一个正在被主动消除的缺陷。**引用 B 级证据时必须确认它是否仍是现状。**

## 1. 核心切片算法

生产切片有两条模式（`config.h:448` `slicing_mode`）：

```
closed_mesh_scanline   ← 代码默认值。三角形-平面求交 + 扫描线奇偶填充
relief_heightfield     ← 生产实际使用（89/90 样例配置、10/10 部署工艺预设）。逐列高度场采样
```

### 1.1 `closed_mesh_scanline`：三角形-平面求交（`slicer.cpp:916-939`）

```cpp
std::vector<Segment2> slice_triangles_to_segments(const std::vector<Triangle>& triangles, double z_mm) {
    for (const Triangle& triangle : triangles) {      // ← 每层遍历全部三角形
        if (edge_intersects_plane(triangle.a, triangle.b, z_mm)) ...
        if (points.size() == 2) { /* 剔除退化后收集 */ }
    }
}
```

**数值健壮性：做得对，而且是 canonical 形式**（这几处不是随手写的）

| 处理 | 实现 | 为什么正确 |
|---|---|---|
| 边-面相交判定 | `(a.z <= z && b.z > z) \|\| (b.z <= z && a.z > z)`（:907-909） | **半开区间**。顶点恰在层面上时归下侧，不会被两条邻边各计一次，从根上避免了顶点处交点重复 |
| 插值除零 | `t = (z - a.z) / (b.z - a.z)`（:911-913），**未做零检查** | 由前置条件保证：只在 `edge_intersects_plane` 为真时调用，此时必有一端 `<=z` 另一端 `>z`，故 `b.z != a.z`。**安全，但依赖调用点纪律** |
| 退化线段 | `(dx*dx + dy*dy) > 1.0e-18` 才收（:932） | 剔除长度 <1e-9 mm 的退化交线（顶点擦过层面的情形） |
| 共面三角形 | 三点同 z 时无边跨越 → 0 交点 → 整块丢弃 | 对闭合流形是**正确选择**：轮廓由侧壁提供 |
| 三点相交 | 只接受 `points.size() == 2`，其余静默丢弃 | 半开判定下三点情形已被消除；这里是防御性冗余 |
| 重心坐标容差 | `point_in_triangle_xy` 用 `epsilon = -1.0e-9`（:1033-1034） | 略微放宽，避免边界像素在相邻三角形间双漏 |

**性能：缺一个标准加速结构（🟠 具体可改）**

- 复杂度 **O(L × T)**：每层遍历全部三角形。`grep` 确认 `slicer.cpp` **一处都没有**用到仓库里已有的 `NearestTriangleQuery` / `TriangleIntersectionQuery` / `PointInClosedMeshQuery`，也没有任何 BVH / kd-tree / 空间哈希。
- 标准做法是**按 z 区间对三角形分桶**（或排序后维护活动三角形集）：每层只访问 z 范围跨过该层面的三角形，复杂度降到 `O(T log T + Σ 活动三角形)`。对薄层高层数场景（1429 层）收益是数量级的——一个三角形平均只跨越极少数层，现在却被访问了 1429 次。
- 附带的分配开销：每层 `segments.reserve(triangles.size())` 新建一个 vector（:917-918）。T=50 万时每层预留约 16 MB，1429 层重复 1429 次。改成跨层复用缓冲即可（MEMFLOW 在别处已经这么做了，见 `5c6b8b7`「compose 缓冲跨层复用」，这一处没跟上）。

### 1.2 扫描线奇偶填充（`slicer.cpp:954-981`）

```cpp
for (int y{0}; y < grid.height_px; ++y) {        // ← 每一行
    for (const Segment2& segment : segments) {   // ← 遍历全部线段
        if (y_mm < min_y || y_mm >= max_y || std::abs(segment.y1 - segment.y0) < 1.0e-12) continue;
        intersections.push_back(...);
    }
    std::sort(intersections.begin(), intersections.end());
    if ((intersections.size() % 2U) != 0U) { ++result.odd_intersection_rows; }
    for (std::size_t i{0}; i + 1U < intersections.size(); i += 2U) { fill_span(...); }
}
```

**正确性：同样是 canonical 形式**

- y 方向也用**半开区间** `y_mm < min_y || y_mm >= max_y`，与 z 方向判定风格一致，避免线段共享端点处交点被计两次。
- 水平线段（`|y1-y0| < 1e-12`）跳过——水平边不参与奇偶计数，这是扫描线填充的必要条件。
- `fill_span`（:942-952）用 `ceil((left-origin)/px - 0.5)` 到 `floor((right-origin)/px - 0.5)`，即**填充像素中心落在 [left,right] 内的像素**。与浮雕采样路径的 `+0.5` 像素中心采样约定**一致**。像素中心约定在整个代码里统一，这在光栅化代码里是容易出错却做对了的地方。

**性能：缺活动边表（🟠 具体可改）**

- 复杂度 **O(H × S)**：每行都遍历全部线段。H ≈ 2792（7 795 500 像素/层的平方根量级），S 为该层线段数。
- 教科书优化是**活动边表（Active Edge List）**：按线段的 y 起点分桶，扫描线推进时增删活动边，复杂度降到 `O(S log S + Σ 活动边)`。**未实现。**
- 内层 `fill_span` 逐像素用 `mask.at(...)`（:950），带边界检查。MEMFLOW 的 `6102742`（MF-14a）已经在别处「去掉约 210 亿次边界检查」，**这一处还在**。

### 1.3 开放/非流形网格是 fail-soft（🟠 值得决策确认）

奇数交点行的处理（:973-979）：**只递增计数器，然后照常用成对交点填充，丢掉末尾未配对的那一个**。计数最终变成报告里的 `openSegmentWarnings` / `odd_scanline_intersections` 警告（:3727-3734）。

**含义**：一个开放或自相交网格进入栅格器，**不会失败，会静默产生部分填充的层**，只留一条警告。生产准入完全依赖上游 preflight 拦住非流形网格（`geometry.preflight.full` 走 Worker + `MeshRepairEligibilityPolicy`），栅格器自己不设闸。

这**可能是刻意的**（fail-soft + 诊断，让诊断模式能看到坏网格切出来什么样），但 `AGENTS.md` 反复强调的是「任何引擎失败均不得静默回退」。建议明确记一笔：**这里的静默降级是被授权的例外，还是一处漏网。** 我从代码读不出答案——需要产品裁定。

### 1.4 `relief_heightfield`：逐列高度场采样（生产实际路径）

`slicer.cpp:1043` 起。形状与 1.1/1.2 完全不同：

- **按三角形的 XY 包围盒展开到像素网格**，对每个候选像素做 `point_in_triangle_xy` 判定，用重心坐标插值出 z，维护逐列的 `zMin`/`zMax`（以及 MATVOL 启用时的逐材质顶面 `topTriangle`/`topBarycentric`）。
- 复杂度 **O(Σ 三角形投影面积)**，与层数**无关**——这是它能被 MEMFLOW 改成有界的根本原因：它本来就是逐列的高度场，不需要层栈。
- 采样策略可插拔（`GeometryOccupancyPolicy`）：`MakeLegacyGeometryOccupancyPolicy` / `MakeLayerSlabGeometryOccupancyPolicy` / `MakeLayerSlabSupersample2x2GeometryOccupancyPolicy`，对应 Stage 16 的 S0/S3/S4，且有 `ValidateLayerOccupancyPolicy` 校验。**这是一处设计良好的策略扩展点**（对比 `SlicePipelineRouter` 只认两个车道，这里是真正的策略对象）。
- `765aeb8`（FRAME）刚加了「跳过材质包围范围外的三角扫描」的空列剔除。

**评级：✅ 合理。** 这条路径的算法选择（高度场而非层栈）是对的，也正因为对，才能被优化到 1.14 GiB。

## 2. 数据结构：Dense 整栈的现状（🔴 最重要的一条新发现）

### 2.1 `sample_model_masks` 仍然全层物化

`slicer.cpp:984-1011`：

```cpp
std::vector<std::vector<std::uint8_t>> sample_model_masks(...) {
    masks.reserve(grid.layer_count);
    for (int layer_index{0}; layer_index < grid.layer_count; ++layer_index) {
        ...
        masks.push_back(std::move(raster.mask));   // ← 每层一份 width*height 字节
    }
}
```

内存 = **L × W × H 字节**。1429 层 × 7 795 500 像素 = **11.1 GB 一个栈**。`8290791` 的提交信息明确记录当时「七个 mask 整栈为真瓶颈」。

### 2.2 但 MEMFLOW 的有界改造只覆盖了 `relief_heightfield`

`slicer.cpp:4404-4451` 的分支结构：

```cpp
const BoundedReliefSupportEligibility boundedReliefSupport = EvaluateBoundedReliefSupportPath(config);
...
if (config.slicing_mode == "relief_heightfield") {
    // 有界路径：按列区间推导 + 稀疏活动列表 + 跨层复用缓冲
    boundedActiveColumns = BuildBoundedActiveColumns(boundedReliefSpans, grid.width_px, grid.height_px);
} else {
    model_masks = sample_model_masks(...);   // ← Dense 全栈，原样保留
}
```

**而 `slicing_mode` 的代码默认值是 `"closed_mesh_scanline"`**（`config.h:448`），走的正是 `else` 分支。

### 2.3 为什么这是个陷阱

| 事实 | 证据 |
|---|---|
| 生产实际 100% 用 `relief_heightfield` | 90 份样例配置里 89 份、10/10 部署工艺预设 |
| 代码默认值是未优化的那条 | `config.h:448` `slicing_mode{"closed_mesh_scanline"}` |
| 配置里省略 `slicingMode` 就静默落到默认 | `config.cpp:154` `root.value("slicingMode", config.slicing_mode)` |

**结论：内存根治是模式局部的，不是全局的；而默认值指向未被根治的那条路径。** 只要有人写一份省略 `slicingMode` 的配置（CLI 手写配置、新工艺预设、测试 fixture），就会拿到 2026-09-06 之前的内存画像。

**建议（三选一，都很便宜）**

1. 把默认值改成 `relief_heightfield`（如果产品语义允许）。
2. 保留默认值但**要求显式声明**：省略即校验失败（`config.cpp:710` 已经在校验取值合法性，加一条「必填」即可）。
3. 保留现状，但在 `closed_mesh_scanline` 路径入口按 `L×W×H` 做**内存预算准入**——`MF-01` 已经建了「溢出安全的 Raster 路由合同」与 `MF-07c` 峰值预估器，直接复用即可。

我倾向 **2 或 3**：改默认值会影响所有省略该字段的既有配置与 golden，属行为变更；而「显式声明」或「预算准入」都是加闸不改语义。

## 4. 六通道语义与包契约

`p0.rgbwsv.2`（RGB + White + Support + Varnish）与 `p0.rgbwsvt.1`（+ Transfer）。协议不变量（`slicer_capability_dtos.json`）：

```
bitDepth 8 ｜ polarity black_is_print ｜ printValue 0 ｜ emptyValue 255
```

**`black_is_print` 是一个容易出错的极性约定**：0 = 打印、255 = 空白，与直觉相反。代码里有 `visible_from_print_value`（:506 附近）做展示侧翻转。这个约定被写进了机器可读契约并有 schema 校验，是正确的治理方式。

**一处历史遗留风险（引自 `AGENTS.md`，B 级）**：12G-TCWS 冻结的原因正是「当前白区 `WSV=000` 是下游私有信号，与物理 `black_is_print` 通道语义冲突」。也就是说**极性约定上已经出现过一次语义碰撞**，且该专项因此被冻结。本章无法从代码判定这个冲突是否已消解——它需要外部 RIP 契约输入（`AGENTS.md` 记录为 `BLOCKED_EXTERNAL`）。

**建议**：把「通道值 0/255 的语义 + 白区特例」做成一份独立的语义对照表放进契约目录。现在这个知识散在 `12G` 的审查文档、`slicer_capability_dtos` 的不变量字段与代码里的翻转函数三处。

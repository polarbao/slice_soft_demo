# 02 模块级评估

> 评级：✅ 合理保留 ｜ 🟡 有条件合理 ｜ ❌ 不合理
> 每条判定后附证据（A 级：`文件:行号`）。

## 1. 契约层

### 1.1 公共 C ABI ─ `contracts/print_module_spi.h` ✅

**做对了什么**

- **导出面极小**：11 个函数，`slicer_module.def` 白名单导出，没有多余符号。
- **ABI 不变量写在头文件里而不是口头约定**（`print_module_spi.h:12-36`）：禁止结构体/STL/Qt/函数对象跨界；字符串一律 UTF-8；句柄不透明且创建释放必须同一 DLL；异常不得逃逸；运行时必须 MSVC x64 + `/MD`(Release) / `/MDd`(Debug)，模块自述运行时、宿主校验不一致拒装。
- **缓冲区协议统一且三态明确**（探测长度 / 缓冲足够 / 缓冲不足不做部分写），所有 `char*` 出参函数遵守同一份规则。
- **`pm_spi_version` 与 `pm_module_info` 必须在 `pm_create` 之前可调用且无副作用** —— 让宿主能在真正装载前做兼容判定。
- 运行时一致性有**编译期强制**：`ModuleInfo.cpp:5-11` 用 `#error` 在非 MSVC-x64 或非动态运行时下直接拒绝编译。

**唯一的结构性代价**：11 个函数是**冻结**的，`protocolInvariants.noNewAbiExport = true`。任何新能力只能挤进 `pm_submit` 的 JSON 里，不能新增导出。这是刻意的（避免版本地狱），但意味着 ABI 层无法表达「流式返回」「零拷贝 blob」这类需求——所有大数据（层预览、ViewData 网格）都要走「探测长度 → 分配 → 再取一次」的两趟缓冲区协议。

**判定：合理。不建议改动。**

### 1.2 `file_contract_v1` ─ DLL↔Worker 私有契约 ✅

**做对了什么**

- **协商在前，失败关闭**：首次接触某 Worker 身份必须先跑 `--contract-info`，校验 `major=1`、`minor∈{0,1}`、`produces` 含 `p0.rgbwsv.2`、`capabilities` 非空且是已知四项子集（`contracts/file_contract_v1.md` §2）。
- **能力决定最低 minor 与必需包契约，调用方不能靠传低 minor 绕过**；且明文写死「**没有从 `slice.rgbwsvt` 回退到 `slice.rgbwsv` 的路径**」。
- **可选能力不等于不合规**：只声明 `slice.rgbwsv` 的 Worker 仍是合规 Worker，只在请求 rgbwsvt 时才失败。这条让旧 Worker 与交接包继续有效——**是正确的向后兼容设计**。
- **清理顺序写死**（§7）：启动清残留 → 成功走 staging→自检→原子发布→删 backup → 失败删 staging 保留上次成功包 → 取消/超时先 Worker 后模块 → release 时幂等重清。且**递归删除被限制在从请求 `packageDir` 派生的同级命名**，禁止越出父目录。
- **`result.json` 的 `code` 是权威稳定码，退出码只带分类**（§5）。崩溃/强杀无结果文件时，从进程状态 + 退出码表推导。职责边界清晰。
- schema 里用 `if/then` 把「能力 ↔ minor ↔ 包契约」的三元约束表达成机器可校验的形式，不是靠文档口头描述。

**判定：合理。这是全项目质量最高的契约文档。**

### 1.3 能力清单的多副本 ❌

同一份「模块提供哪些能力 / 产出哪些包契约」的事实，被**手写了 5 份**（加上测试里的第 6 份）：

| # | 位置 | 形态 |
|---|---|---|
| 1 | `src/slicer_module/ModuleInfo.cpp:41` | C++ 里的一整行硬编码 JSON 字符串字面量 |
| 2 | `src/slicer_module/module.json.in:11-31` | CMake `configure_file` 模板 |
| 3 | `contracts/slicer_capability_dtos.json` | 公共 DTO（`contractVersion 1.14`） |
| 4 | `contracts/file_contract_v1.request/result.schema.json` | JSON Schema 的 `enum` |
| 5 | `version-manifest.json` `compatibility.contracts` | 版本清单 |

外加 `tests/stage14c_05/ValidateModuleInfoContracts.py:19-56` 里的第 6 份（Python 常量 `EXPECTED_PROVIDES` / `EXPECTED_SYNC` / `EXPECTED_WORKER`）。

**已实测漂移**（详见 04_ F-01/F-03/F-05）：`slice.rgbwsvt` 与 `p0.rgbwsvt.1` 存在于副本 1 与 4，**缺席于副本 2、3、5、6**。

**判定：不合理。** 不是因为「有多份」本身——不同消费者需要不同格式是正常的——而是因为**没有一份是生成出来的**，6 份全靠人手同步，而且唯一的对拍测试是空转的（F-02）。

## 2. 宿主层

### 2.1 `ModuleClient` 运行时加载器 ✅

`apps/slicer_ui_host_sim/ModuleClient.h` 的注释把意图写得很清楚：「客户端有意不依赖任何切片实现类型。11 个 `pm_*` 符号全部在运行时解析，使参考宿主无需链接模块导入库即可加载；能力 DLL 缺失时也能明确报告错误。」

**这不是口号，是可验证的事实**：对 `apps/slicer_ui_host_sim` 整个目录（130 文件）grep `slicer_core`，命中 **0 个文件**。宿主与引擎之间**没有任何编译期耦合**。

CMake 侧也一致：`target_link_libraries(slicer_ui_host_sim PRIVATE Qt5::Widgets slicesoft_rip_integration bcrypt)` —— 没有 `slicer_module`，只有 `add_dependencies` 保证构建顺序，POST_BUILD 把 DLL/EXE/manifest 拷到宿主目录（`apps/slicer_ui_host_sim/CMakeLists.txt:176-186`）。

**判定：合理。这是「边界靠结构而不是靠纪律」的教科书实现。**

### 2.2 纯 C 参考宿主 `apps/slicer_host_sim` ✅

3 155 行 C11，`/W4 /WX`。它的价值不在功能，而在**用一个不含 Qt、不含 C++ 的消费者证明 ABI 真的是 C ABI**。这类「另一种语言的最小消费者」是 ABI 冻结项目里最有效的低成本保险。

**判定：合理。应当保留并在 ABI 变更时继续维护。**

### 2.3 Qt 宿主 `apps/slicer_ui_host_sim` 🟡

26 983 行 / 140 文件。结构本身**比行数看起来健康**：

- `HostMainWindow` 头 206 行、58 个方法、21 个成员，实现拆成 11 个 `HostMainWindow*.cpp`（合计 2 097 行）——它是协调器，不是万能对象。
- 面板各自独立类（`HostSliceSettingsPanel`、`HostMaterialSettingsPanel`、`HostMatvolSettingsPanel`、`HostProfilePanel`、`HostRipSettingsPanel`、`HostPackageReviewPanel`…）。
- 渲染、相机、交互、状态各有子目录（`render/`、`camera/`、`settings/`）。
- 策略被单独提出来成类：`MoveOptimizationPolicy`、`TransformCommitPolicy`、`HostImportPlacementPolicy`、`SceneRenderPolicy`、`TopViewRenderPolicy`。这是好习惯。

**两个缺口**：

1. **RIP 控制器住在 UI 里**：`HostRipJobController.cpp` 1 373 行，是宿主第一大文件、全仓第七大文件（F-07）。
2. **能力探测用裸子串**：`HostSliceProtocolRoute.cpp:27` `if (!moduleInfo.contains("slice.rgbwsvt"))` —— 对整份模块信息 JSON 文本做子串匹配，而不是解析 `provides` 数组（F-04）。

**判定：有条件合理。** 骨架是好的，两个具体缺口可低成本修复。

## 3. 模块层（DLL）

### 3.1 `WorkerClient` / `WorkerProcessWindows` ✅

进程管理写得很扎实，逐条列举（`src/slicer_module/WorkerClient.cpp`）：

| 做法 | 位置 | 为什么重要 |
|---|---|---|
| `CREATE_SUSPENDED` 创建 → `AssignProcessToJobObject` → `ResumeThread` | :281-306 | 消除「子进程在被纳入 Job Object 之前就跑起来甚至自己 fork」的竞态。很多实现会漏这一步 |
| `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` | :245-247 | 宿主进程崩溃时 Worker 及其整棵进程树被内核回收，不留孤儿 |
| `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 只继承 2 个管道写端 | `ProcessAttributeList` | 防止把宿主的无关句柄泄漏给子进程 |
| `PeekNamedPipe` 先探再读，单次排空预算 256 KB | :37-70 | 避免匿名管道的经典死锁（子进程写满管道阻塞、父进程在 `WaitForSingleObject` 上阻塞） |
| 退出后再排空 10 轮 | :356-361 | 收尾未读完的输出，避免丢日志 |
| 参数校验拒绝非法超时与 >2000 ms 宽限期 | :226-232 | 把契约约束落成运行时断言 |
| 单客户端并发保护 `compare_exchange_strong` | :199-205 | 一个 `WorkerClient` 同时只允许一次 `Run` |

**判定：合理。这部分不需要动。**

### 3.2 `WorkerProtocol` 🟡

**做对了**：保留前缀（`SLICE_PROGRESS` / `SLICE_TIMING`）的行如果不符合语法就是**契约错误而不是普通日志**——这条「保留前缀语法失败即违约」的设计防住了「进度解析悄悄失效但作业照跑」这类静默故障。进度不变量（`0≤current≤total`、`percent∈[0,100]`、`elapsedMs` 单调、成功前必须出现 `percent=100`）都在解析器里强制。

**缺口**：`WorkerRunResult` 的 `stdoutLogLines` / `stderrLogLines` / `progressEvents` / `timingEvents` 是**四个无上限 `vector`**（`WorkerProtocol.cpp:213,280,303,306,321`），整个作业期在 DLL 内存里只增不减。对一个逐层输出进度、跑 30 分钟的作业，这是**确定会增长且没有上界**的内存（F-12）。

**判定：有条件合理。** 加一个环形缓冲上限即可，改动局部。

### 3.3 `CapabilityCarrierRouter` 🟡

**做对了**：承载者判定集中在一处；异常分三类映射到稳定错误码（`domain_error` → `PROFILE-0031`、`CapabilityRequestError` → `INPUT-0002`、其余 → `INTERNAL-0099`），并有 `catch(...)` 兜底——**保证异常不逃逸 DLL 边界**，这是 ABI 不变量 4 的实际落点。`NormalizeWorkerOnlyBackend` 把「进程内切片」在请求层再封一道。

**缺口**：路由是**字符串 if-else 链**，能力集合没有注册表。加一个能力 = 在这里加一个分支 + 在别的 6 处同步（见 05_ §2）。

**判定：有条件合理。** 现在的规模（15 个能力）还撑得住，但这是 F-01 那类漏改的结构性来源。

### 3.4 `WorkerJobService` 🟡

867 行，跨线程持有作业、进程客户端、进度与终态；`WriteJsonAtomically`（tmp + rename）保证请求文件不会被读到半截；私有作业目录按 `pid/module-id/job-id` 三级隔离，多实例并存安全。

**缺口**：`maxConcurrentJobs = 1`（`ModuleInfo.cpp:41`，超限时 `WorkerJobService.cpp:701` 报 `PM-SLICER-RESOURCE-0041 maxConcurrentJobs=1`）。**进程隔离本来能带来并行，这里主动放弃了**（F-13）。对 22 实例批量生产这类场景是硬上限。

**判定：有条件合理。** 串行是可以接受的保守起点，但应当被记为「已知不使用的能力」而不是「设计如此」。

## 4. Worker 层 ✅

`apps/slicer_worker` 4 364 行，形态非常克制：

- 命令行只有 3 个（`--help` / `--contract-info` / `--spi-request <绝对路径>`），拒绝相对路径（`WorkerApplication.cpp:130-146`）。
- `--contract-info` **独占 stdout**，只输出一个 JSON 对象——调用方不必做流式解析。
- 执行器按能力注册进 `WorkerJobDispatcher`（`WorkerApplication.cpp:139-152`），4 个能力 4 个执行器，**这是 Worker 侧唯一的扩展点，形态正确**。
- `runtime/` 把请求解析、身份、结果封装、结果写入拆成 8 组文件，职责单一。

**判定：合理。** Worker 是整个仓库中「大小与职责最匹配」的模块。

## 5. 引擎层

### 5.1 Facade + 工厂注入 ✅

`api/Facades.h` 只做一件事：聚合 6 个纯抽象 Facade 的头。`SliceFacade` / `PreflightFullFacade` / `RepairFacade` 三个接口各自只有 1 个虚方法，全部 `[[nodiscard]]` + `noexcept`，返回 `ApiResult<T>`（成功值或 `PM-SLICER-*` 错误），取消通过 `const ICancelToken&` 传入而不是全局标志。

实现侧 `src/slicer_core/engine/Production*FacadeFactory.{h,cpp}` 三个工厂 + `SliceFacadeAdapter`。**接口在 base、实现在 engine、注入在 Worker** —— 这是 base/engine 切分能成立的根本原因。

**判定：合理。这是全项目最干净的接缝，新增能力应当照抄这个形状。**

### 5.2 `pipeline/` ✅

46 个文件，按引擎车道组织：`LegacySceneLayerAdapter` / `GlobalSurfaceShell*`（4 组）/ `OpenVdbCandidate*`（2 组）/ `MultiModel*`（4 组）/ `SlicePipeline*`（路由 + 上下文 + 步骤结果）。

`SlicePipelineRouter` 值得单独表扬：**请求模式与生效模式分离**（`requested_mode` / `effective_mode` / `fallback_applied`），阻塞原因带稳定错误码与可读 detail，且 `RequireSlicePipelineRoute` 让「被阻塞」变成抛异常而不是悄悄降级。这与 `AGENTS.md` 里反复强调的「任何引擎失败均不得静默回退」一致，**且是代码强制的，不是文档承诺的**。

**判定：合理。**

### 5.3 `geometry/` ✅

43 个文件，几何查询（`NearestTriangleQuery`、`PointInClosedMeshQuery`、`TriangleIntersectionQuery`、`DistanceField2D`）、诊断（`MeshTopologyDiagnostics`、`MeshRobustnessDiagnostics`、`ContactPostureMetrics`）、OpenVDB 适配（6 组，`USE_OPENVDB` 开关下才编）、修复子目录 `repair/`。职责划分清楚，OpenVDB 依赖被隔离在可选开关后而不是散布全仓。

**判定：合理。**

### 5.4 `importers/` ✅

`obj/` `three_mf/` `mtl/` 三个子目录 + `model.cpp` 的格式分发。**目录结构本身就是扩展点**：加一个格式 = 加一个子目录 + 在分发处加一支。

**判定：合理。**

**判定：不合理。这是全项目唯一真正的技术债主体。** 但**不建议现在大改**——理由与拆解方法见 06_ R-12。

### 5.6 `config.{h,cpp}` ❌

`config.h` 488 行 **39 个结构体**（`OutputConfig`、`MaterialConfig`、`TextureConfig`、`RgbPolicyConfig`、`WhitePolicyConfig`、`VarnishPolicyConfig`、`MaterialPolicyConfig`、`ModelFillConfig`、`MaterialProcess*`×6、`MaterialRole*`×2、`MaterialVolume*`×6、`TransferChannelPolicyConfig`、`InternalVoidSupportConfig`、`UpperSupportConfig`、`SupportBaseProjectionConfig`、`SupportConfig`、`OuterVarnishShellConfig`…）全部聚合成一个 `SliceConfig`；`config.cpp` 1 485 行做加载与校验，同样带 G2 豁免。

**为什么不合理**：

- 引擎的唯一入口是 `run_slicer(config_path)` —— **一个 JSON 文件驱动全部行为**。这让「哪些配置项影响哪个车道」无法从类型上判断，只能靠文档与 `DiagnosticEffectiveConfig`（855 行）事后解释。
- 每个新专项（MATVOL / MATOPQ / TRANSFER / Stage16 采样）都往同一个 `SliceConfig` 上挂新结构体，配置面**只增不减**，且没有按车道分组的类型边界。
- 副作用：任何配置项变更都触碰 `config.cpp`，而 `config.cpp` 又被 G2 豁免——**豁免变成了常态**。

**判定：不合理，但优先级低于 `slicer.cpp`。** 配置膨胀本身不产生正确性风险，主要代价是可理解性。

### 5.7 `model.cpp` 🟡

1 941 行，STL 直接解析 + OBJ/3MF 委派给 `importers/` + 自动定向（`AutoOrientReport`）+ 外观评估（`ModelAppearanceAssessment`）+ 3MF 报告（`ThreeMfReportInfo`）。

它在 base 里，因此**被打进 DLL** —— 这是对的（宿主需要 `model.import`）。但把「自动定向策略」这类**产品语义**放在 base 的模型加载器里，与「base 只做数据与查询、engine 做策略」的分层意图有张力。

**判定：有条件合理。** 不紧急。

## 6. 工具与旁路

### 6.1 `apps/slicer_cli` 🟡

1 565 行，直接 `#include "slicer_core/slicer.h"` 并在 `main.cpp:547` 调 `run_slicer(...)`。它**链接 `slicer_core`（= engine），完全绕过 DLL 与 Worker**。

`file_contract_v1.md` §1 明确写「直接 CLI 产出的包仍为候选（candidates）」，且 `MultiModelProductionService.cpp:1019-1022` 用 effective config 的 `production` 布尔决定 `productionAcceptance` 是 `"admitted"` 还是 `"functional_fixture_admitted"`。

**所以：「生产必须经 Worker」这条不变量在模块边界（`options.backend` 只接受 `worker` + DLL 不链引擎）是硬的，在引擎边界是软的**——CLI 拿一份 `production=true` 的 effective config 就能产出标记为 `admitted` 的包（F-08）。

对内部工具而言这是可接受的（CLI 是开发者工具，不分发给终端用户），但**这条边界的软硬差异应当被写进文档，而不是靠「大家知道 CLI 不算生产」**。

**判定：有条件合理。** 建议做的是**记账**（明确写下 CLI 通道的准入语义），不是封堵。

### 6.2 RIP 集成 ❌

见 04_ F-07 完整论证。摘要：

- `print_module_spi.h` 第 4 行写明「所有预处理能力模块（**切片、RIP、未来扩展**）通过实现本接口接入宿主 PrintApp」。
- 实际实现：`HostRipJobController.cpp:865` `m_process = new QProcess(this)` 直接拉起 `rip_cli.exe`；`src/rip_integration`（1 951 行）作为静态库 `slicesoft_rip_integration` **直接链进宿主 exe**；RIP 有自己的清单 schema（`slicesoft.rip.module.1`）与打包脚本（`PackageRipModule.ps1`），但**不实现 `pm_*`**。
- 结果：仓库里存在**两种形状不同的能力集成拓扑**，宿主里有两套作业控制器、两套进度解析、两套取消逻辑、两套错误映射。

**判定：不合理。** 修复成本不低（RIP 侧是外部 SDK），但这是「架构意图与实现分叉」的典型，越晚归位越贵。

### 6.3 其余 `apps/*`（12 个演示/矩阵/基准工具，6 448 行） ✅

`geometry_kernel_demo`、`stage16_*`（4 个）、`surface_shell_*`（3 个）、`texture_fill_partition_*`（2 个）、`tiff_writer_benchmark`、`multi_model_scene_matrix`、`repaired_asset_intake`、`mesh_repair_preflight`、`rip_reader_test`、`openvdb_sdf_utility_probe`。

它们是**证据生产工具**——这个项目的验收方式是「跑矩阵、出报告、对 golden」，这些工具是那套方法论的载体。把它们和产品目标放在同一个 `apps/` 下、同一个 CMakeLists 里编，是构建规模问题（F-18）而不是设计问题。

**判定：合理保留，但应当与产品目标在构建上分组**（见 06_ R-08）。

## 7. 工程基础设施 ❌

| 项 | 现状 | 问题 |
|---|---|---|
| CI | 无 `.github/workflows`；`AGENTS.md` 记录 CI 专项由用户 2026-08-10 裁决暂缓 | 234 项回归全靠人工本机跑；`AGENTS.md` 明确警告「构建与回归必须分开判定退出码」「陈旧 `build/` 会让 ctest 对陈旧二进制报 PASS」——**这两条警告本身就是没有 CI 的症状** |
| 测试框架 | 无。每个用例手写 `main` + 自制 `ExpectTrue(cond, msg)` | 148 个可执行目标里绝大多数是测试；断言不打印实参（`AGENTS.md` 记录全仓 85 处），失败时不报原因 |
| 构建组织 | 单文件 3 315 行 CMake 承载 173 个目标 | 任何目标改动都触碰同一个文件，合并冲突面大（`AGENTS.md` 已记录 MEMFLOW 分支的 merge 冲突面「仅 `CMakeLists.txt` 与 TASKS_16 两处」——`CMakeLists.txt` 是常驻冲突点） |
| 行数门禁 | `ValidateSourceSizeGuard.py` + `SourceSizeGuardConfig.json` | **只在 CTest 里注册 `--self-test`，仓库全扫描未进 CTest**（`AGENTS.md` 明确记录），所以门禁违规是静默债不是红灯 |
| 构建目录 | 仓库根 8 个 `build*` | `build/` 已知陈旧且危险 |

**判定：不合理。** 这一层的投入回报比最高——它不改变任何产品行为，但决定了上面所有分析结论能不能被自动守住。

## 8. 评估小结

把上面的判定按「投入回报」重排：

| 优先级 | 对象 | 理由 |
|---|---|---|
| **最高** | 契约副本漂移 + 空转的对拍测试（F-01/F-02） | 已经出问题了，且修复成本 1–3 天 |
| **高** | 工程基础设施（CI / 框架 / CMake 拆分） | 不改产品行为，但守住其余一切 |
| **中** | RIP 归位 SPI（F-07） | 架构意图与实现分叉，越晚越贵 |
| **中** | base/engine 分层从白名单改目录（F-06） | 现在没出事，但保护是脆的 |
| **低（但必须做）** | `slicer.cpp` 拆解（F-09） | 唯一的债主体，但必须小步 + golden 对拍，急不得 |
| **可延后** | 配置面重组、CLI 准入记账、并发放开 | 不产生正确性风险 |

# 05 扩展性评估与预留

> 回答用户问题 2 的后半段：**「针对合理的模块是否有预留后续扩展空间」**。
> 方法：不看设计意图，看**实测数据** —— 用仓库里已经发生过的一次真实扩展（新增 `slice.rgbwsvt` 能力与 `p0.rgbwsvt.1` 包契约）作为自然实验，数它实际触碰了多少文件。

---

## 1. 自然实验：加一个新切片能力，实际要动多少处

对全仓 grep `slice.rgbwsvt`（排除 docs）：

**产品代码与契约，15 个文件：**

| # | 文件 | 承担的角色 |
|---|---|---|
| 1 | `contracts/file_contract_v1.md` | 私有契约正文（协商规则、能力↔minor↔包契约三元约束） |
| 2 | `contracts/file_contract_v1.contract_info.schema.json` | 协商响应 schema |
| 3 | `contracts/file_contract_v1.request.schema.json` | 请求 `enum` + `if/then` 分支 |
| 4 | `contracts/file_contract_v1.result.schema.json` | 结果 `enum` + `if/then` 分支 |
| 5 | `src/slicer_module/ModuleInfo.cpp` | 运行时自述字符串（硬编码 JSON） |
| 6 | `src/slicer_module/CapabilityCarrierRouter.cpp` | 承载者路由分支 + `contractMinor` 推导 |
| 7 | `src/slicer_module/WorkerContract.cpp` | 能力 → 最低 minor / 必需 produces 的映射 |
| 8 | `src/slicer_module/WorkerJobService.cpp` | 作业请求构造 |
| 9 | `apps/slicer_worker/WorkerApplication.cpp` | `--contract-info` 输出 + dispatcher 注册 |
| 10 | `apps/slicer_worker/runtime/WorkerJobDispatcher.cpp` | 分发 |
| 11 | `apps/slicer_worker/runtime/WorkerRequestParser.cpp` | 请求解析 |
| 12 | `apps/slicer_worker/slice/WorkerSliceRequestMaterializer.cpp` | effective config 物化 |
| 13 | `apps/slicer_ui_host_sim/HostSliceProtocolRoute.cpp` | 宿主协议 → 能力路由 |
| 14 | `apps/slicer_ui_host_sim/HostProfileCatalog.cpp` | Profile 目录 |
| 15 | `apps/slicer_ui_host_sim/HostMainWindowProfile.cpp` | UI 绑定 |

**加上测试与脚本：再 8 个文件。合计 23 个文件。**

**而且它还漏了 2 处**（就是 04_ 的 F-01 与 F-05）：

| 应该改但没改 | 后果 |
|---|---|
| `src/slicer_module/module.json.in` | 部署清单声称不支持这个能力（F-01） |
| `contracts/slicer_capability_dtos.json` | 公共契约完全没提这条已经在生产的路径（F-05） |

**结论：正确完成一次能力扩展需要人工同步 17 处，实际只同步了 15 处，漏了 2 处，而唯一负责发现这类漏改的测试是空转的（F-02）。**

这不是「某个人不小心」，这是**扩展成本超过人类可靠同步能力上限**的必然结果。**能力清单是这个项目唯一没有做扩展预留的关键位置。**

## 2. 逐扩展点评估

评级：🟢 预留充分 ｜ 🟡 可扩展但成本线性 ｜ 🔴 无预留

### 2.1 新增切片/几何能力 🔴

- **扩展点**：无。分散在 17 处手写副本里，靠字符串比较串联。
- **实测成本**：17 处，跨 4 种语言（C++ / JSON Schema / CMake 模板 / Python），且**没有任何机制保证同步**。
- **已发生的失败**：F-01 / F-05。
- **改进方向**：见 §5 的单一真源方案。

### 2.2 新增输出包协议（`p0.*`） 🟡

- **扩展点**：`src/slicer_core/output/` 下按协议分目录（`rgbwsv/` / `rgbwsvt/`），各自有 Writer / Reader / SchemaReader / Protocol / TiffIo。
- **已证可行**：`p0.rgbwsvt.1` 就是这么加进来的，且 `rgbwsvt/RgbwsvtPackageReader` 与 base 的分层关系被显式列进 `SliceSoftCoreLayering.cmake` 的 `baseExactStems`——**说明扩展时确实考虑了分层**。
- **成本**：一个新目录 + 一份 schema + 分层名单 + §2.1 的能力扩展成本。
- **评级**：目录结构本身是好的预留；成本主要被 §2.1 拖累。

### 2.3 新增模型格式 🟢

- **扩展点**：`src/slicer_core/importers/{obj,three_mf,mtl}/` 目录结构 + `model.cpp` 的格式分发。
- **成本**：一个新子目录 + 分发处一支 + `ModelLoadConfig` 可能的新字段。
- **预留质量**：目录即扩展点，`importers/` 整目录归 base（在 `basePrefixes` 里），新格式自动获得正确的分层归属，**不需要改 CMake 名单**。这是全项目做得最对的一处预留。
- **评级**：🟢

### 2.4 新增切片流水线/引擎车道 🟡

- **扩展点**：`SlicePipelineMode` 枚举 + `SlicePipelineConfig` + `ResolveSlicePipelineRoute` + `pipeline/` 下的一组 Adapter/Pipeline/Package。
- **做得好的**：路由决策结构化（`requested_mode` / `effective_mode` / `allowed` / `fallback_applied` / `error_code` / `detail`），**无静默回退是代码强制的**；新增车道自动获得可审计的准入语义。
- **缺口**：`ResolveSlicePipelineRoute` 目前**只认 Legacy 与 Global 两个分支**（`SlicePipelineRouter.cpp:14-42`）。Stage 16 的 S0–S4 采样策略、MATVOL、TRANSFER 走的是 `SliceConfig` 里的另一套开关，**策略选择实际分散在至少三处机制里**：流水线路由、配置开关、Profile 预设。
- **改进方向**：把「一次切片到底走哪条路」收敛成一个可审计的决策对象，而不是三套机制的交集。这与 F-10（配置面重组）是同一件事的两面。
- **评级**：🟡

### 2.5 新增 Facade（引擎能力抽象） 🟢

- **扩展点**：`api/Facades.h` 加一个纯抽象类 + `engine/Production*FacadeFactory` 加一个工厂 + Worker 侧注入。
- **预留质量**：接口在 base、实现在 engine、注入在 Worker —— **这个三段式是 base/engine 切分能成立的根本原因**，也是新能力最应该照抄的形状。所有 Facade 统一 `[[nodiscard]] noexcept` + `ApiResult<T>` + `const ICancelToken&`，签名风格一致。
- **评级**：🟢 **全项目最好的扩展点。**

### 2.6 新增能力承载者（第二个 Worker / GPU Worker / 远程 Worker） 🟢

- **扩展点**：`WorkerLaunchOptions.executablePath` 是参数；`WorkerContractNegotiator::Negotiate(workerExecutable, requirement)` 也是参数；`CapabilityRoute` 已经有 `carrier` 字段（`CapabilityCarrier::Worker` 枚举）。
- **含义**：如果将来要加一个「GPU Worker」或「不同引擎的 Worker」，进程管理与协商代码**不需要改**，只需要在路由处决定用哪个可执行文件。
- **`WorkerContract.h:67` 的注释甚至已经写明**：「`slicer_worker.exe` **或测试 Worker** 的绝对路径」——测试确实在用这个参数化能力。
- **缺口**：`ResolveWorkerExecutable()` 目前硬编码为「DLL 同目录下的 `slicer_worker.exe`」（`WorkerJobService.cpp:43-68`）。要用第二个 Worker，需要把这个解析改成从路由决策取。改动很小。
- **评级**：🟢（架构预留充分，只差一处硬编码）

### 2.7 新增宿主 UI 面板/功能 🟢

- **扩展点**：面板各自独立类（12 个 `Host*Panel`），策略独立成类（`MoveOptimizationPolicy` / `TransformCommitPolicy` / `HostImportPlacementPolicy` / `SceneRenderPolicy` / `TopViewRenderPolicy`），`HostMainWindow` 拆成 11 个分部实现文件。
- **实证**：工作树当前正在进行的 HOSTFLOW H-F-14/15（导入姿态与批次原点）改动就落在 `HostImportPlacementPolicy` / `HostModelImportWorkflow` / `HostTransformLayoutPanel` 三个文件上——**新功能确实能落在既有的策略类里，没有再往 `HostMainWindow` 里塞**。
- **评级**：🟢

### 2.8 新增第三方能力模块（RIP 之外的第四方） 🔴

- **应有的扩展点**：`print_module_spi.h` 的 11 个 `pm_*` + `slicesoft.module_manifest.1` 清单 + 宿主的 `ModuleClient`。
- **实际情况**：**先例已破**。RIP 没走这条路（F-07），它自建了 `slicesoft.rip.module.1` 清单体系 + `QProcess` 调度 + 1 373 行住在 UI 里的控制器。**且 2026-09-08..14 这一轮又往这条分叉里投了四个提交**（双墨量模式、`slicesoft.rip.settings.3` 新 schema、阶段进度显示、模块更新）——分叉在变宽，不在收敛。
- **后果**：一个新来的能力模块开发者看仓库时，会看到两种做法，且**分量更重的那一种（RIP）是不合 SPI 的那一种**。
- **评级**：🔴 **不是因为接口不好，而是因为示范作用被破坏了。**

### 2.9 新增测试 🟡

- **扩展点**：加一个目录 + 一个 `Main.cpp` + `CMakeLists.txt` 里加 `add_executable` + `target_link_libraries` + `target_compile_options` + `add_test` 五段。
- **成本**：每个新测试在 3 315 行的 CMake 里加约 10 行，且要重新手写 `ExpectTrue`。
- **评级**：🟡（能加，但每次都付固定税；见 F-17 / F-18）

## 4. 一个反直觉的观察

**这个项目的扩展性问题不在架构层，在数据层。**

- 架构接缝（Facade / 承载者 / 流水线 / 导入器）**全部有预留且质量不错**。
- 出问题的是**同一份事实被手写成多份**：能力清单 6 份、包协议 3 份、分层规则 1 份藏在 CMake 函数里、测试期望 1 份藏在 Python 常量里。
- 所有 A 类问题（F-01..F-05）都是这一个根因的不同表现。

换句话说：**代码结构是好的，元数据管理是缺的。**

这也解释了为什么项目有 1 114 份 md 文档却仍然出现契约漂移 —— **文档记录事实，但不生成事实**。契约文件之间没有生成关系，只有人工同步关系。

## 5. 唯一真正需要新建的预留：能力注册表

这是本报告在扩展性方面的**核心建议**（对应 06_ 的 R-10）。

**目标形态**：一份 `contracts/capability_registry.json`，声明每个能力的：

```
id                      slice.rgbwsvt
carrier                 worker | in_process | mode_dependent
contractMinor           1
requiredProduces        ["p0.rgbwsvt.1"]
workerExecutor          slice.rgbwsvt
requestFields / responseFields / errors
publicDto               true | false
```

**由它生成（而不是人工同步）**：

| 目标产物 | 生成方式 |
|---|---|
| `ModuleInfo.cpp` 的自述字符串 | 构建期代码生成（`configure_file` 或小脚本） |
| `module.json` 的 `provides` / `produces` | 同上（F-01 根治） |
| `file_contract_v1.*.schema.json` 的 `enum` | 生成脚本 |
| `slicer_capability_dtos.json` 的 `capabilities` 数组 | 生成脚本（F-05 根治） |
| `version-manifest.json` 的 `compatibility.contracts` | 生成脚本（F-03 根治） |
| 测试期望常量 | 直接读注册表，不再有 `EXPECTED_PROVIDES` 常量（F-02 根治） |
| `CapabilityCarrierRouter` 的路由表 | 生成一张查表，替代 if-else 链 |
| Worker dispatcher 注册 | 生成注册列表 |

**收益**：A 类 5 条问题（F-01/F-02/F-03/F-05 + F-04 的诱因）**一次性根治**，且「加一个新能力」的成本从 17 处降到 **1 处 + 1 个执行器实现**。

**代价与风险**

- 引入构建期代码生成，增加构建复杂度（但项目已经在用 `configure_file` 生成 `module.json`，不是新概念）。
- 生成的文件要不要入库？建议**入库并加 CI 校验「重新生成后无 diff」**，这样离线阅读契约仍然直接（对一个把契约当第一公民的项目很重要）。
- 冻结契约（`slicer_capability_dtos.json` 是 `contractVersion 1.14` 的受控文件）改成生成产物，**需要用户裁定并留决策文档**。
- 迁移期要保证生成结果与当前手写内容**逐字节一致**（除了本来就该补的 rgbwsvt），否则会被误判为契约变更。

**成本**：L ｜ **风险**：中 ｜ **需要用户立项授权**

## 6. 附：`lockstep` 版本策略对扩展性的影响

`version-manifest.json` 声明 `releasePolicy: "lockstep"`，且 `PackageSlicerModule.ps1:299` 强制 `application.version == slicer.version`（并在下一行要求二者等于 `module.json` 的 `version`）。

**这在事实上取消了模块化最主要的一项收益**：模块本可以独立于宿主发版。

这不是缺陷——它是一个有意的治理决策（对应 `docs/slice/DOC/DOC_DECISION_VERSION_*`），在「宿主与模块由同一团队维护、同步发布」的阶段是正确的，能避免版本矩阵爆炸。

**但代价应当被明确记账**：

- 生产形态里宿主是**第三方 PrintApp**。PrintApp 不可能与本模块 lockstep 发版。
- 所以 lockstep 实际约束的是「本仓库的参考宿主 ↔ 本仓库的模块」，而**真正的集成边界（PrintApp ↔ 模块）用的是 `pm_spi_version` + `pm_module_info` 的运行时协商**，那才是真正的版本机制。
- 因此 lockstep 是**开发期便利**，不是产品期契约。**建议在文档里把这一点写明**，否则容易被误读成「模块不能独立演进」。

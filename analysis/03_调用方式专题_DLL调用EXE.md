# 03 调用方式专题：DLL 调用 EXE 是否合理

> 这是用户问题清单里的核心问题，单独成篇。
> 结论先行：**合理，且在当前约束下是最优解。建议保持。**

---

## 1. 先把「DLL 调 EXE」这句话拆准确

直觉上「DLL 去启动一个 EXE」听着别扭，是因为它违反了「库应该是被动的」这一习惯。但这里的实际形状不是那样：

```
错误的心智模型：                        实际的形状：

  某个库 ──启动──▶ 某个程序             宿主进程（PrintApp / Qt 宿主）
  （库越权了）                            └─ 装载了一段协调代码（打包成 DLL）
                                              └─ fork 出一个计算进程（Worker）
```

**真正在跑活的是 EXE（`slicer_worker.exe`），DLL 只是宿主进程里的适配层 + 作业管理器。** 它不含引擎，不做切片，它做的事是：把宿主的 JSON 请求翻译成 Worker 请求、管进程生命周期、解析进度、映射错误码、清理产物。

这个形状有大量先例：

| 系统 | 形状 |
|---|---|
| Chrome / Electron | 浏览器进程 fork 渲染进程；每个渲染进程一个沙箱 |
| VSCode | 主进程 fork 扩展宿主进程与语言服务器进程 |
| 编译器驱动（cl.exe / clang） | 驱动进程 fork 前端/后端/链接器进程 |
| Photoshop / AE 插件 | 插件 DLL 调外部渲染引擎进程 |
| Git 的 credential helper / diff driver | 库/主程序 fork 外部程序 |

唯一「不常见」的是**协调代码被打包成 DLL 而不是 EXE**。而这一点**不是选择，是约束**：

> 宿主 `PrintApp` 是别人的打印软件，本项目不拥有它。它的集成点只能是「装载一个模块」。所以协调层**必须**是 DLL。

`print_module_spi.h` 开篇就说明了这个定位：「所有预处理能力模块（切片、RIP、未来扩展）通过实现本接口接入宿主 PrintApp。」

**所以问题不该问成「DLL 调 EXE 合不合理」，应该问成：**

> **切片计算应该跑在宿主进程内，还是跑在独立进程里？**

DLL 只是被约束条件钉死的那一层。真正需要论证的是进程隔离。

## 2. 为什么切片必须跑在独立进程里

### 2.1 资源画像

> ⚠ **2026-09-08 更正**：下表是 **2026-09-06 之前的历史值**。MEMFLOW 专项已于其后合入产品分支，
> 单模型 10 µm 峰值由 22–34 GB 降至 **1.14 GiB**，双模型由「内存不足失败（外推 270 GB）」变为
> **valid=1 / 峰值 1.91 GB**，场景峰值与层数**彻底脱钩**（提交 `6787930`、`7d7a627`、`35517d1`）。
> **因此内存不再是进程隔离的现役论据**——§2.2 表格里其余五条理由不受影响，本章结论不变。
> 详见 `07_切片域算法与数据结构评估.md` §0。下表保留作为历史记录与「为什么当初这么设计」的说明。

| 指标 | 实测值 |
|---|---|
| 单模型（`finger_suoguo/a-2/0.2.obj`，10 µm 层厚） | 1 429 层 × 7 795 500 列 = **111.4 亿 pixel-layer** |
| 六通道 Dense 内存需求 | **62.2 GB** |
| 机器物理内存 | **31.6 GB** |
| 单模型实跑 | 450/1429 层用时 593 s，全程外推 **~31 分钟** |
| 双模型 | **直接内存不足失败** |

这不是「有点重的计算」，这是**会打爆物理内存、会跑半小时**的计算。

### 2.2 如果它跑在宿主进程内会发生什么

| 事件 | 进程内 | 独立进程（当前） |
|---|---|---|
| 内存耗尽 | **宿主被杀，用户丢失整个工作区与未保存场景** | Worker 被杀，宿主收到 `RESOURCE` 分类错误码，场景完好 |
| 几何算法断言失败 / 越界 | **宿主崩溃** | Worker 退出码带分类，DLL 转成稳定 `PM-SLICER-*` 码 |
| 用户点「取消」 | 只能协作式：要在几十处循环里插检查点，任何一处漏了就取消不掉 | 协作式先试（`cancel.requested` 标记），2 000 ms 宽限后 `TerminateJobObject` **强杀兜底** |
| 内存碎片 / 堆膨胀 | 累积在长期运行的 UI 进程里，越用越慢 | 进程退出即彻底归还 |
| 第三方库（OpenVDB / libtiff / meshoptimizer）出事 | 直接污染宿主地址空间 | 隔离在 Worker |
| 宿主是**别人的程序** | **切片崩溃 = 打印软件崩溃**，责任边界无法切分 | 责任边界物理清晰 |

最后一条是决定性的：**这个模块要装进第三方打印软件里**。在别人的进程里跑一个会吃 62 GB、跑 30 分钟、可能断言失败的计算，是不可接受的集成方式。进程隔离在这里不是优化，是**准入条件**。

### 2.3 隔离是结构性的，不是约定性的

这一点值得强调，因为它是这套设计里最强的部分：

```cmake
target_link_libraries(slicer_module PRIVATE slicer_base)
#                                            ^^^^^^^^^^^
#                              不是 slicer_engine，不是 slicer_core
```

**切片引擎的目标代码根本不在 DLL 里。** 所以：

- 「进程内切片」不是被政策禁止，是**编译期不可能**——没有符号可以调用。
- 有人想「临时加个开关跑进程内试试」，会在链接期就失败，不会悄悄合进主线。
- 并且有**链接期门禁把这条守住**：`model_import_layering_probe`、`package_query_facade_14b02_base_link_test` 两个目标只链 `slicer_base`，一旦 base 侧误引入 engine 符号，这两个目标就链不过。

再叠三道运行时防线：

1. `CapabilityCarrierRouter::NormalizeWorkerOnlyBackend`：`options.backend` 缺省补 `"worker"`，显式传其他值抛 `domain_error` → `PM-SLICER-PROFILE-0031`。
2. `contracts/slicer_capability_dtos.json` `protocolInvariants.sliceBackend`：`allowed: ["worker"]`，`noInProcessFallback: true`。
3. `file_contract_v1.md` §1：「In-process slicing is not part of this contract.」

**四道防线里最重要的是第一道（链接结构），因为它不依赖任何人遵守规则。** 大多数项目的「隔离」只有第 2–4 道，那是纸面隔离。

## 3. 传输方式：为什么是文件 + stdout 而不是别的

选定了「独立进程」之后，还要选进程间怎么说话。当前选择是：

| 方向 | 载体 |
|---|---|
| 请求 | `request.json`（原子写：`request.tmp` → `rename`） |
| 结果 | `result.json`（原子写：`result.json.tmp` → `rename`） |
| 进度/计时 | stdout 的保留前缀文本行（`SLICE_PROGRESS` / `SLICE_TIMING`） |
| 日志 | stdout/stderr 普通行 |
| 终态分类 | 进程退出码（0/1/2/3..8） |
| 取消 | `cancel.requested` 零字节标记文件 + `TerminateJobObject` 兜底 |
| 产物 | 文件系统上的 package 目录（staging → 原子发布） |

**这是刻意选的最笨的方案，而这里「笨」是优点：**

1. **零依赖**：不需要引入 gRPC / protobuf / 命名管道框架 / 共享内存库。整个 IPC 层的实现是 `WorkerClient.cpp`（约 500 行）+ `WorkerProtocol.cpp`（约 330 行）。
2. **可离线复现**：作业目录里就是一份 `request.json`。开发者可以直接 `slicer_worker.exe --spi-request <path>` 单独重跑，不需要宿主、不需要 DLL、不需要 Qt。仓库里就有这条路径的工具（`scripts/Prepare14D08WorkerDebugRequest.py`）。这对一个跑 30 分钟的计算来说是**巨大的调试价值**。
3. **可 schema 校验**：请求与结果都有 JSON Schema，且用 `if/then` 表达了「能力 ↔ minor ↔ 包契约」的三元约束。二进制协议做不到这个。
4. **崩溃语义天然清晰**：没有 `result.json` = 没走到正常收尾。不需要额外的心跳/连接状态机去区分「对方死了」和「对方在想」。
5. **产物本来就是文件**：切片的输出是一个装满 TIFF 的 package 目录。既然大数据必然落盘，控制流也走文件就没有额外损失。

**代价**：三段序列化（宿主内存 → `request.json` → Worker 物化 effective config → 引擎读回），以及模型文件被 DLL 与 Worker 各解析一次。见 §5.1。

## 4. 六种方案横向对比

| # | 方案 | 故障隔离 | 传输开销 | 取消/超时 | ABI/依赖风险 | 改造成本 | 判定 |
|---|---|---|---|---|---|---|---|
| **A** | **当前：DLL + 子进程 + 文件契约** | **进程级** | 3 段序列化 + 进程启动 | **强（可强杀）** | **低** | 0（已完成） | ✅ **保持** |
| B | 引擎链进 DLL，进程内直算 | **无** | 0 | 弱（纯协作式） | 高（引擎 + OpenVDB + libtiff 符号进宿主地址空间） | 中 | ❌ 一次 OOM 带走宿主；且宿主是第三方程序 |
| C | 进程内 + 线程池 | **无** | 0 | 弱 | 高 | 中 | ❌ 同 B，且多线程共享堆让 OOM 更难定位 |
| D | 常驻 Worker + 命名管道/共享内存 | 进程级 | **低**（省进程启动与重复解析） | 强 | 低 | **高**（要做连接状态机、心跳、崩溃重连、会话隔离） | 🟡 **未来可评估，需先测量** |
| E | gRPC / 本地 socket | 进程级 | 中 | 强 | 中（引入 protobuf/gRPC 依赖树） | 高 | ❌ 本地单机 + 并发上限 1，付了分布式的价买不到分布式的收益 |
| F | 去掉 DLL，宿主直接调 Worker EXE | 进程级 | 低 | 强 | 无 | 中 | ❌ **不可行**：宿主 PrintApp 的集成点就是 DLL，这一层不能去掉 |

### 4.1 为什么 D（常驻 Worker）现在不做

它是唯一在技术上值得考虑的替代，但：

1. **收益未经测量**。省下的是「进程启动 + 模型重复解析」。对一个 30 分钟的切片作业，这部分占比大概率可以忽略；对 `geometry.preflight.full` 这类短作业占比才可能显著。**本轮没有测**，`AGENTS.md` 也没有这项测量记录。按项目已有的教训（短基准单次运行波动可达 47%），这种决策**必须先有多次取最小值的实测**。
2. **成本被低估**。常驻进程要引入：连接建立/断开状态机、心跳与死连接检测、崩溃后重连与作业重放、多会话隔离（现在靠「一个作业一个进程」天然隔离）、常驻进程的内存不归还问题（切片跑完 62 GB 的堆，进程不退出就还给不了系统）。最后一条尤其致命——**当前设计「进程退出即彻底归还内存」这个性质，在常驻方案里会消失**。
3. **它会削弱当前最强的性质**：作业失败的爆炸半径从「一个作业」扩大到「常驻进程里的所有作业」。

**结论：D 保持在候选池，开工前置条件是「测出进程启动 + 重复解析在真实作业里的占比」。**

## 5. 当前方案的四个次优点（都可在不动拓扑的前提下修）

### 5.1 进程冷启动 + 模型重复解析

**事实（已逐行确认）**：

- 每次作业新建一个进程（`WorkerJobService.cpp:686` 每次 `ResolveWorkerExecutable()`）。
- **每次作业都要额外跑一次 `--contract-info` 进程**（5 s 超时）：`WorkerJobService.cpp:465-470` 在每个作业线程里无条件构造 `WorkerContractNegotiator` 并 `Negotiate`，**没有任何缓存**。所以**一个作业 = 两次进程启动**。
  > 值得注意的是，`file_contract_v1.md` §2 的措辞是「模块必须在**向某个 Worker 身份提交第一个作业之前**执行 `--contract-info`」——契约本身就预期了「按 Worker 身份缓存」，实现比契约要求做得更频繁。这不是违约（多协商是安全的），但是契约明确留出的优化空间没有被使用。
- `request.json` 里的 `scene` 是引用式的（模型路径 + 变换 + 哈希），Worker 拿到后**重新从磁盘解析模型**。而 DLL 侧为了 `model.import` / `scene.get_viewdata` / `geometry.collision` 已经解析过一遍。

**影响**：① 每个作业多一次进程创建 + 一次 JSON 解析（对短作业如 `geometry.preflight.full` 占比可能可观，对 30 分钟的切片可忽略）。② 同一个模型在两个进程里各有一份三角网——对 `finger_suoguo` 这类大模型是实打实的重复 I/O 与重复内存。

**改动空间（不动拓扑）**：

- **低成本**：把协商结果按「Worker 可执行文件路径 + 文件 mtime + size」缓存在模块实例生命周期内，契约本身已经允许。改动局限在 `WorkerJobService`，不触碰任何契约文件。
- 中成本：DLL 侧在 `model.import` 时把解析结果落成一份中间格式（已三角化的二进制缓存）放进作业目录，Worker 直接映射。代价是磁盘占用与缓存一致性管理。
- **前置条件：先测量。** 尤其是第二项——不测就动等于凭感觉优化。第一项因为改动面极小且契约已允许，可以不等测量就做。

### 5.2 日志与进度在 DLL 内无界累积

**事实**：`WorkerRunResult` 里 `stdoutLogLines`、`stderrLogLines`、`progressEvents`、`timingEvents` 四个 `std::vector` 只增不减（`WorkerProtocol.cpp:213,280,303,306,321`），生命周期是整个作业。

**影响**：1 429 层逐层进度 = 至少 1 429 个 `WorkerProgressEvent`，加上引擎的普通日志行。单次作业不至于爆，但这是**没有上界**的结构。

**改动空间**：给四个容器加上限（环形缓冲：进度保留最近 N 条 + 首尾；日志保留最近 N KB + 溢出计数）。改动局限在 `WorkerProtocol.cpp` 与 `WorkerClient.h` 的结构定义，**不触碰契约**。成本：小。

### 5.3 并发写死 1

**事实**：`ModuleInfo.cpp:41` `"maxConcurrentJobs":1`；`WorkerJobService.cpp:701` 超限报 `PM-SLICER-RESOURCE-0041 maxConcurrentJobs=1`。

**影响**：进程隔离本来天然支持并行（每个作业一个进程、私有作业目录已经按 `pid/module-id/job-id` 三级隔离），但主动放弃了。对 22 实例批量生产这类场景是硬上限。

**改动空间**：把上限做成 `pm_create` 的 `options_json` 参数（SPI 已经预留了这个入口，且 `pm_module_info` 已经把 `maxConcurrentJobs` 声明为宿主可读的能力字段——**接口层面早就准备好了**）。风险在于 N 个并发 Worker × 62 GB 的内存画像，所以放开必须配合内存准入判断，不能无条件放开。成本：中。**建议等 MEMFLOW 有界窗口（目标 134 MB）落地后再评估。**

### 5.4 取消延迟没有实测数

**事实**：`pm_module_info` 自述 `cancelLatencyMs: 2000`；`file_contract_v1.md` §6 规定宽限期最多 2 000 ms 然后 `TerminateJobObject`。Worker 侧在「步骤边界与逐层循环内」检查 `cancel.requested`。

**问题**：2 000 ms 是**契约上限**，不是实测的取消延迟。真实延迟取决于 Worker 检查点的密度——如果某个步骤（比如一次全局距离场计算）内部没有检查点，协作式取消就会拖到宽限期结束然后被强杀。强杀本身是安全的（staging 由模块侧兜底清理），但用户体验是「点了取消要等 2 秒」。

**改动空间**：加一个测量而不是加代码——在现有取消用例里记录「发出取消 → 进程退出」的实际耗时分布，确认是否存在无检查点的长步骤。成本：小（测量）。

## 6. 关于「两条不同拓扑」的问题

这一节其实不属于「DLL 调 EXE 是否合理」，但用户问的是「当前切片软件采用的调用方式是否合理」，那么完整回答必须包括：**仓库里存在第二条形状完全不同的能力调用路径。**

```
切片：宿主 EXE ──pm_* (C ABI)──▶ slicer_module.dll ──CreateProcess + 文件契约──▶ slicer_worker.exe
RIP ：宿主 EXE ──QProcess 直调──▶ rip_cli.exe ──链接──▶ RipSlicer.dll
      + src/rip_integration（1 951 行）静态链进宿主 exe
      + HostRipJobController（1 373 行）住在 UI 可执行文件里
```

而 `print_module_spi.h` 第 5 行的原话是：「所有预处理能力模块（**切片、RIP、未来扩展**）通过实现本接口接入宿主 PrintApp。」

**这是架构意图与实现的分叉**，代价具体可数：

- 宿主里有**两套**作业控制器、两套进度解析、两套取消逻辑、两套错误码映射、两套设置持久化。
- RIP 的能力发现走 `rip_module.json`（`HostRipJobController.cpp:235`）而不是 `pm_module_info`——**两套模块清单体系**。
- 生产形态里，PrintApp 要集成 RIP 就得再实现一次 QProcess 调度，而不是复用它已经写好的 `pm_*` 装载器。
- `src/rip_integration` 链进宿主 exe，意味着 RIP 的验证逻辑（`RipOutputValidator` 820 行）**无法独立于 Qt 宿主发版**。

详细的问题登记与修复提案见 04_ F-07 与 06_ R-11。

## 7. 本章结论

| 问题 | 结论 |
|---|---|
| DLL 调 EXE 合理吗？ | **合理。** 真正的形状是「宿主内的协调层 fork 计算进程」，DLL 只是被宿主集成点钉死的那一层 |
| 切片该不该独立进程？ | **必须。** 62 GB / 30 分钟 / 可能断言失败的计算，不能跑在第三方打印软件的进程里 |
| 隔离做得够不够硬？ | **够硬，而且硬在正确的地方**：DLL 不链引擎（编译期结构保证）+ 链接期门禁，比运行时开关强一个数量级 |
| 传输用文件 + stdout 合理吗？ | **合理。** 零依赖、可离线复现、可 schema 校验、崩溃语义天然清晰；且产物本来就是文件 |
| 有没有更好的方案？ | **当前没有。** 常驻 Worker（方案 D）是唯一候选，但**必须先测量**进程启动与重复解析的实际占比，且要接受「进程退出即归还内存」这一性质的丧失 |
| 需要改什么？ | 四个次优点：进程冷启动/重复解析（先测量）、日志无界累积（小改）、并发写死 1（中改，等 MEMFLOW）、取消延迟无实测（加测量） |
| **还有别的问题吗？** | **有，且更重要**：RIP 走了另一条完全不同的拓扑，与 SPI 的声明意图分叉（F-07） |

**一句话：切片的调用方式不是这个项目需要担心的地方。需要担心的是 RIP 没走同一条路，以及引擎内部那 5 888 行。**

### 2.3 v0.1 交付物

```text
modules/slicer/
├─ slicer_module.dll          11 个 pm_* 导出，过 C-SPI-01..18（内含静态链接的 core）
├─ slicer_worker.exe          重作业承载（= 演进后的 slicer_cli，内含静态链接的 core）
├─ module.json                能力自述 + runtime/buildConfig
└─ <依赖 DLL: tiff / assimp / miniz ...>
contracts/
├─ print_module_spi.h         与打印侧同源 · 【唯一跨越边界的头文件】
├─ p0.rgbwsv.2.schema.json
├─ slicer.capabilities.json
└─ file_contract_v1.md
```

> ⚠️ **交付包中没有 `slicer_core` 的任何文件**。`slicer_core.lib` 是静态库中间产物，已被 DLL 与 Worker **各自静态链接**（见 `INT_10` §1.1）。打印软件既不 include core 头、也不链接 core 库。

**打印软件的对接方式（零编译期耦合）**：

```text
构建期：只需 contracts/print_module_spi.h（用于函数指针 typedef）
        不需要 slicer 的 include 路径，不链接任何 .lib
运行期：LoadLibraryEx(modules/slicer/slicer_module.dll, LOAD_WITH_ALTERED_SEARCH_PATH)
        → GetProcAddress 取 11 个 pm_* 符号
        → pm_spi_version() == 宿主 PM_SPI_VERSION，否则拒绝装载
        → pm_module_info() 校验 runtime / buildConfig 匹配，否则拒绝装载
        → pm_create() → 调用能力 → pm_destroy()

能力面（v0.1）：
  ✅ model.import / model.get_metadata
  ✅ geometry.preflight (fast/full)
  ✅ scene.apply_operation（Commit 车道）/ scene.get_snapshot
  ✅ geometry.collision
  ✅ slice.rgbwsv（Worker 承载）
  ✅ package.verify
  ⏸ package.get_summary/render_layer_preview → v1.0
  ⏸ scene.get_viewdata → v1.0
```

### 2.4 为什么 v0.1 不必等单体拆完（关键判断，P）

```text
薄壳（api/ + slicer_module/）是【在 slicer_core 之上加一层】，不需要先拆 slicer.cpp
→ slicer.cpp 5157 行照样能被 facade 调用
→ 拆分是为了【可测/可剖析/可增量/可取消】，不是 DLL 化的前置条件
∴ 先出 v0.1 让打印软件能用，拆分在中期并行推进
```

**唯一的例外是 `tiff_io.cpp` 缺陷**——它必须在 v0.1 之前修，因为 RIP 与 `ChannelSplitter` 用 libtiff 读我方产物，当前处于未定义行为区。这是 W1 就排它的原因。

## 7. s14 文档吸纳台账（回答第 5 问）

### 7.1 总体评价

**质量：规划级，非规格级。可选择性吸纳，不可替代我方 ABI 工作。**

可信度证据（A，我逐条核对）：s14 给出的 12 个文件行数**全部与工作树精确一致**（`slicer.cpp` 5157、`UiSmokeTestRunner.cpp` 6963、`MainWindow.cpp` 3659 等）；`slicer_module`/`slicer_worker`/`.def` 零命中，其"IMPLEMENTATION NOT STARTED"属实；63 张任务卡与 470h 算术自洽；状态纪律严格（`未执行项保持 NOT RUN`、`IMPLEMENTATION_GATE = NOT_AUTHORIZED`、`CURRENT_NEXT_TASK = 03D-01` 拒绝把自己排到队首）。**这不是幻觉产物。**

局限：**约 1400 行文档只产出 1 个 struct + 2 个 typedef，零函数签名**；PRD_14 与 DECISION_14 约 80% 重复；三点估算是 `0.75×/1.0×/1.4×` 机械缩放（40/63 任务都恰好 8h）；有一处活跃矛盾（`RgbwsvPackageWriter.cpp` 被分配给禁止改它的任务）。

### 7.2 吸纳清单（8 项，已落入文档）

| # | 吸纳内容 | 落点 | 价值 |
|---|---|---|---|
| 1 | **Transient/Commit/Production 三车道** + `operationId` 幂等 + 快照可重建 | `INT_09` G-1 | 🔴 **最有价值**。补上我方 SPI 对"60fps 拖拽"的空白 |
| 2 | **`package.*` 查询与预览能力** | `INT_09` G-2 | 🔴 防止宿主自造 TIFF 解码与材料合成 |
| 3 | **Worker 是 DLL 私有实现细节** | `INT_10` §1 | 措辞比我方精准，杜绝双 API 面 |
| 4 | **`Cancelling` ≠ `Cancelled`** | `INT_09` G-3 | 有 13F 真实 bug 佐证 |
| 5 | staging→自检→原子发布 + 崩溃后无半成品 | `INT_10` §3.2 | 与我方 `tiff_io` 缺陷形成系统级兜底 |
| 6 | 大缓冲契约 + 预览 cache key 规则 | `INT_09` G-5 / G-2 | 禁 Base64、必须从生产 TIFF 解码 |
| 7 | **拆分治理纪律**（单 Owner / characterize→wrap→move→guard→regression / 行数非 DoD）| `INT_11` §2.2 | 正是绞杀式重构需要的纪律 |
| 8 | 模块缺失时宿主仍可启动（`D14-E-03`）+ D14-C/D 负例矩阵 | `INT_10` §3.2 / 验收 | 现成的 ABI 一致性测试计划 |

### 7.3 冲突与裁定（4 项）

| # | 冲突 | 裁定 | 理由 |
|---|---|---|---|
| A | `scene.layout` 归属：s14 放模块内，我方排除 | **各对一半 → 折中**：`geometry.collision` 出真值归模块；**packing 策略留宿主** | 碰撞/越界是几何真值不可重造（s14 对）；但 layout 全部输入归宿主且是高频变更的 UX 决策（我方对）|
| B | 接缝数：s14 三个（S1/S2/S3），我方四个 | **我方胜**，保留四个 | s14 全文对 `ch7`/`printdata`/`ReadyTicket`/`CMYK`/`grayBits`/`drop` **零命中**，S2/S3 只是占位；`ReadyTicket` 是决策制品，所有权与生命周期均异于像素目录，应独立成缝 |
| C | 同步快路径：s14 要求同步轻能力，我方只有异步三件套 | **我方调和**：不加 `pm_call`，改为在 `capabilities.syncCapabilities[]` 声明，轻能力在 `pm_submit` 内同步完成 | 保持单一调用模型，同时给宿主可预期语义 |
| D | 装载机制：s14 只说"延迟加载"未言机制 | **我方胜** | s14 对 `GetProcAddress`/`DELAYLOAD`/`.def`/`__cdecl`/`/MD` **零命中**；且只有显式 `LoadLibrary`+`GetProcAddress` 才能满足其自己的 `D14-E-03` |

### 7.4 s14 缺失、我方补上的（7 项）

```text
① 全部函数签名与 ABI 机制层（11 导出/.def/__cdecl/MD/运行时装载）
② RIP 侧线格式（rip.ch7.1 / printdata.v1 / ReadyTicket）
③ 墨滴量化模型（grayBits=2 → CMYK 0-3 / White 0-6 / S,V 0-9）
④ 切片侧具体缺陷（tiff_io 字对齐 / 无 flush / manifest 重复）—— tiff_io.cpp 未出现在其拆分矩阵
⑤ 切片链路 cancel token —— 【两侧共同盲区】，我方已列为 steps/ 的 DoD
⑥ ISliceStep / steps/ / 场景优先数据模型
⑦ 全部数值预算（s14 明确声明不虚构，故一个数字都没有）
```

### 7.5 采纳 s14 的排期认知

s14 估 Stage 14 全程 **63 卡 / 470h / 约 16 个有效开发周**（单人 30h/周）。与我方 §2–§3 的 111–164 人日（v0.1 + v1.0）**量级一致**，可互为校验。但两点修正：

- `14B-07A`（`slicer.cpp` 特征测试与依赖图）**仅估 8h 严重低估**，我方按 15–25 人日估整体拆分；
- s14 把拆分全部前置到 14B（170h，占 36%），而我方主张**先出 v0.1 再拆**（§2.4），让打印软件早 3 个月拿到可用件。

### 不一致 1（🔴 我方自造）：薄壳目录命名冲突

### 8.1 新增裁定：core 的产物与交付边界（2026-08-02）

原 `INT_10` 只写了三层的"职责"，未写各层**构建产物**，容易被误解为"打印软件要面对三个东西"。已补齐并裁定：

```text
slicer_core   → slicer_core.lib（静态库）· 中间产物 · 【不进交付包】· 打印软件完全不接触
slicer_module → slicer_module.dll（内含静态链接 core）· 交付 ·【宿主唯一入口】
slicer_worker → slicer_worker.exe（内含静态链接 core）· 交付 · DLL 私有实现细节

核实：CMakeLists.txt:29 add_library(slicer_core ...) 未带 SHARED、未设 BUILD_SHARED_LIBS
      → CMake 默认 STATIC → 当前形态已正确，无需改动（A）
```

**两个接口不可混淆**：

| 接口 | 形态 | 消费者 |
|---|---|---|
| 内部 `slicer_core/api/` | C++ facade（STL 可用）| DLL / Worker / CLI / UI / 单测——**均为我方内部** |
| 外部 11 个 `pm_*` | C ABI（不透明句柄 + UTF-8 JSON）| **打印软件（唯一）** |

**为什么 core 不做成第二个 DLL**：否则链路变成"打印软件 → slicer_module.dll → slicer_core.dll"，core 的 C++ 接口（STL/异常/模板）将跨 DLL 边界，CRT 不匹配即崩，且违反"跨 ABI 只用 C 类型"红线。静态链接的代价仅为磁盘上两份 core 代码，可接受；但由此产生**同一次构建**的硬约束。

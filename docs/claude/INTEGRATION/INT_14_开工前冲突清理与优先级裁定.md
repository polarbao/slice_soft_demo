## 1. Q0：UI 模拟宿主调用——建议改方案

### 1.1 判断：要做，但不按原方案做

原 `INT_07` 提的 U0–U5（把现有 `slicer_debug_ui` 整体改走 DLL）**现在不成立**，三条理由（A）：

1. **UI 已过度膨胀**：`MainWindow.cpp` 3659 行、`UiSmokeTestRunner.cpp` 6963 行。在这两个文件上做 ABI 迁移，等于在最不稳定的地方动最敏感的改造。
2. **原方案的前提消失了**：`INT_07` 假设"等 13F-R2 拆完 UI 再迁"，但**主仓库的 `TASKS_13F` 只有 R0/R1，没有 R2**（A：状态行为 `R0 COMPLETE / R1 IN PROGRESS`）。R2 那 17 张 UI 拆分卡只存在于未合入的 s14 文档里。**没有 13F-R2，就没有"拆完再迁"这个前置。**
3. **成本不对等**：U2–U5 全量迁移估 10–15 人日，而它要验证的东西（ABI 是否够用）用更小的代价就能验。

### 1.2 改为：独立宿主模拟器

```text
新增 apps/slicer_host_sim/（约 400–600 行，不碰现有 UI）
  职责：完全按打印软件的方式调用 slicer_module.dll
    ① LoadLibraryEx(LOAD_WITH_ALTERED_SEARCH_PATH) + GetProcAddress 取 11 个符号
    ② pm_spi_version / pm_module_info 校验 runtime / buildConfig
    ③ 走三车道：本地 transient 变换 → Commit 提交（带 expectedSceneRevision）→ Production 切片
    ④ pm_poll 轮询进度、pm_cancel 取消、pm_result 取结果
    ⑤ 模块缺失/损坏/版本不符时的 fail-closed 行为演示
  形态：控制台程序 + 一个脚本化场景（无 Qt，不依赖 UI）
```

**为什么这比改 UI 好（P）**：

| 维度 | 改现有 UI（U2–U5）| 独立 host_sim |
|---|---|---|
| 成本 | 10–15 人日 | **2–3 人日** |
| 文件冲突 | 与未来 UI 拆分抢文件 | **零冲突** |
| 验证 ABI 完整性 | ✅ | ✅ **等效** |
| 可作打印侧参考实现 | ⚠️ 混在 Qt 代码里，不易抄 | ✅ **纯 C 调用，直接可抄** |
| 能进 CI 常驻 | ⚠️ 需要 Qt 环境 | ✅ 无 Qt，CI 友好 |
| 验证"手感" | ✅ 真实交互 | ❌ 脚本化 |

唯一损失是"真实拖拽手感"，但那本就该由打印软件自己验，且可用 `Host→DLL 调用次数` 这条可证伪指标替代（`INT_09` G-1）。

### 1.3 现有 UI 怎么办

**保持直连 `slicer_core` 不变**。等 Stage 14 的 DLL 稳定、且 UI 拆分专项真正立项后，再评估是否迁移。这也符合"同一文件单 Owner"纪律。

→ 已据此修订 `INT_07`（U 系列降级为"可选后置"）与 `INT_11`（Owner 表去掉悬空的 13F-R2 引用）。

### 🔴 C-2 优先级冲突：官方下一任务 vs 封装

### 🔴 C-3 `tiff_io.cpp` 字对齐缺陷仍在生产路径上

**关键事实（A）**：03D 虽已 `01..07 COMPLETE`，但判定是 **`GO_OPTIONAL`——默认 Writer 保持 handwritten**。

因此 `INT_06` §5 指出的两处缺陷（溢出区未字对齐已生效、IFD 起始偏移被偶数通道数掩盖）**依然在生产输出中**。RIP 与 `ChannelSplitter` 用 libtiff 读我方产物，仍处未定义行为区。

**但 03D 给了一个更便宜的解法（P）**：既然 LibTIFF 后端已实现并通过兼容/性能 Gate，**可以考虑直接切默认后端**，而不是去修手写 writer 的对齐逻辑。代价是需要"新 Gate + 用户单独授权"（`DOC_DECISION_12X` §8.3 明确要求）。

**两条路择一，请裁定**：

| 方案 | 成本 | 风险 |
|---|---|---|
| A 修手写 writer 的对齐 | 3–5 人日 + golden 重基线 | 低，但治标（手写 writer 长期仍是自产自销盲区）|
| B 切 LibTIFF 为默认后端 | 需新 Gate + 授权 + 性能复核 | 中，但**根治**（消除自产自销盲区，且第三方实现天然与消费方同源）|

### 🔴 C-4 RIP 白区语义冲突（12G-TCWS 已记录但冻结）

**这是与打印软件对接最深的一处语义冲突（A，`DOC_DECISION_12X` §8.1 原文）**：

```text
现有 RIP 把正常 RGB 纹理区域作为纹理，把白色区域 W/S/V=0/0/0 作为私有识别信号；
在 black_is_print 生产协议中，W/S/V=0/0/0 的物理含义是三个通道同时打印，
因此该信号不能直接视为自包含 p0.rgbwsv.2 材料语义。
```

**为什么这对集成是硬冲突（P）**：我在 `INT_03`/`INT_08` 定的 S1→S2 契约假设"切片输出的六通道语义是自包含的、RIP 按语义消费"。但现实是 **RIP 正在把某个通道组合当作带外信号（out-of-band signal）**。这意味着：

- 若我方将来在某处合法地写出 `W/S/V=0/0/0`（三通道同时打印），RIP 会误判为白区；
- 反之，RIP 依赖的这个信号**不在 `p0.rgbwsv.2` 的契约里**，属于隐式耦合。

官方已冻结 12G-TCWS 等 RIP 合同决策。**但集成不能等**——建议在 M0 契约冻结时把这一条作为显式条款处理（要么 RIP 放弃该信号，要么在 manifest 里显式声明 `ripContractId`）。

### 🟡 C-5 主状态表遗漏 03E

`REPORT_12X` v4.5 的阶段总表（§2）只有 `03D-LIBTIFF` 一行，**没有 03E**——而 `REPORT_03E_02` 的日期是同一天（2026-08-03）。§2.3 剩余任务数量也未计 03E。

### 🟡 C-6 `13F-R2` 悬空引用（我方文档缺陷，已修）

`INT_11` §3 把 `UiSmokeTestRunner.cpp` / `MainWindow.cpp` / `SceneDocument` 的 Owner 指给"13F-R2"，但主仓库 13F 只有 R0/R1。→ 已修正。

### 🟡 C-7 03E-02 的外部依赖未闭合

### 3.2 封装（Stage 14）的位置——官方序列里没有

这是需要你决策的核心。目前**封装工作没有官方优先级**，因为它还没立项（C-1）。

### 3.3 三个插入方案（请裁定）

| 方案 | 序列 | 优点 | 代价 |
|---|---|---|---|
| **甲 先收口再封装**（保守）| 09D → 12E-10 → **Stage 14** | 遵守既有序列；12E 有完整收口证据 | 打印软件拿到可用件推迟约 8–10 周 |
| **乙 并行插入**（推荐，P）| 09D 与 **Stage 14 立项+v0.1** 并行；12E-10 其后 | 打印侧不空等；封装的 v0.1 不依赖 09D/10 的结论 | 需两条线并行，单人则需交替 |
| **丙 封装优先** | **Stage 14 v0.1** → 09D → 12E-10 | 最快交付打印软件 | 12E 收口再推迟；09D 的纹理厚度语义可能反过来影响能力面 |

**我的建议是乙（P）**，理由：

1. **v0.1 的能力面与 09D/12E-10 不冲突**——v0.1 只暴露 `model.import` / `geometry.preflight` / `scene.transform` / `slice.rgbwsv` / `package.verify`，这五项的语义已被 12E-09B/09C 收口，**不依赖 09D 的纹理厚度决策**；
2. **封装的前 3 周是文档与薄壳**（立项 + `contracts/` + C ABI），与 09D 的代码改动**几乎不碰同一批文件**；
3. **打印侧已在等**——他们的 M1 门禁挂着我方 `slicer_module.dll`（`CLD_07` M1-07），空等成本高于并行成本。

但有一条硬约束：**若选乙，09D 与 Stage 14 必须严格分文件 Owner**，尤其 `config.cpp`（09D 会改配置）与未来的 `src/slicer_module/`（互不相干，可并行）。

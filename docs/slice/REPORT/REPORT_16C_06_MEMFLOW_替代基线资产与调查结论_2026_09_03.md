## 4. 基线实测（Retained Dense，A 侧）

### 4.1 采集口径

```text
二进制      build-slicesoft/main/Release/slicer_cli.exe
工艺        单材料路径（STL 不携带材质与贴图，无法用多材质工艺）
配置        matopq_baseline.json 的 DPI 635x600、层厚 0.038、MATVOL 关闭
指标        SLICE_TIMING 的 totalMs / sliceProcessingMs / peakWorkingSetBytes
测量条件    **串行、无并发**（实测并发下同一资产偏差可达 32%）
```

`peakWorkingSetBytes` 由切片进程自报，**是进程级峰值工作集**，比上游文档中
「retainedRasterBytes 下界」更接近真实占用——后者按定义只覆盖主要栅格字节，
不含模型、纹理、allocator、JSON 与 TIFF 库。

### 4.2 首个数据点

`qiegejiapian-zxl.stl`（12,084 三角，本批最小）：

```text
wall                  59 s
totalMs               57,904.7
gridSetupMs                8.98    ← 单材料不走 MATVOL 逐列求交，故极小
sliceProcessingMs     54,837.5     ← 主项
workingSetBytes        8,646,656   （进程结束时）
peakWorkingSetBytes  2,992,267,264 ← **峰值 2.99 GB**
```

**这是本专项首个真实的 Peak Working Set 实测值。** 上游文档此前只有按公式估算的
`retainedRasterBytes` 下界，无进程级实测。

peakWS **906 MB**，与上表同量级。

#### 4.6.0 比降幅更值得看的是【离散度】

这批数据最强的一条不是「降了六七成」，而是**峰值不再随资产波动**：

```text
09-03 retained   2,658 ~ 3,316 MB    极差 658 MB，相对波动 25%
09-06 bounded      953 ~ 1,006 MB    极差  53 MB，相对波动  5%
```

而同一批资产的层数是 **104~138**（相差 33%）、三角数是 **12,084~241,274**
（相差 20 倍）。峰值对这两者都几乎不敏感 ——
**这正是「峰值与层数脱钩」在真实资产上的独立复现**，
此前该结论只由 `a-2` 的 15/29/58 层同为 1.019 GB 支撑（那是同一模型改层厚）。

唯一明显偏高的 `qiegejiapian-hcc`（1,006 MB）也不是因为它三角数最多（241,274，
是次多者的 5.7 倍），而是因为它的栅格宽 118 px（5315 vs 5197）—— 即峰值跟着
**列数**走。这与 §4.4 「压力来自 pixel-layer 而非三角数」的判断一致，
也与峰值模型「O(列数)」的建模方式吻合。

#### 4.6.1 耗时【几乎没有变化】，这一点必须写明

| 资产 | wall（09-03） | totalMs（09-06） |
|---|---|---|
| `qiegejiapian-zxl` | 59 s | 61.2 s |
| `qiegejiapian-hcc` | 71 s | 73.3 s |

（其余六项本轮只采了峰值，未逐一记耗时；上面两项已足以说明趋势。）

**内存降了七成，耗时却略增 2~3%。** 不能用「专项使耗时减半」来概括这批资产
—— 报告 §5.10 那个「18.9 -> 9.44 分钟、-50%」是 `a-2/0.2.obj` @10um 的结果，
那是 **1,429 层**的场景。

**推断（未做归因实验）：层数是关键变量。** 有界路径把整栈换成按层重建，
每层多付一次重建开销、省下一次整栈分配；层数越多，省下的越占优。
这批资产只有 116~138 层，两笔基本相抵。若要坐实这条，需要固定资产、
只扫层厚做一组对照，本轮没做。

**对结论的影响：** 专项的内存收益在这批大幅面资产上**独立复现了**
（-67%/-70%，与 `a-2` 的 -97% 同向但幅度不同，因为这批本就没到换页的量级）；
而耗时收益**不是普遍的**，它随层数增长，不应写成无条件的结论。

#### 4.6.2 这三个点已固化进预估器测试

`stage16c06_slice_peak_memory_estimate_unit_tests` 现有 **8 个实测点**，
这三条是其中仅有的、来自**入库真实资产**且非合成放大的点：

```text
suoguo qiegejiapian-zxl  估 1,185 MiB / 实测 909 MiB = 1.30x
suoguo qiegejiapian-hcc  估 1,206 MiB / 实测 959 MiB = 1.26x
a-3 @0.1mm               估 1,134 MiB / 实测 864 MiB = 1.31x
```

三点全部被高估覆盖，裕度与 `a-2 @10um` 的 1.26x 一致 ——
即峰值模型在**大幅面单材料**这一档上，由三个互相独立的真实资产各自验证过一次。

### 4.4 本批数据对专项前提的独立印证

决策文的定性是「主要问题**不是三角形数量**，而是把整个 `width * height * layers`
空间多次常驻」。本批数据直接支持该判断：

```text
峰值内存 vs pixel-layer    相关系数 = +0.996      近乎完美线性
每亿 pixel-layer 的峰值     301~328 MB            八个样本高度一致

三角数最少   12,084 三角  ->  2,853 MB
三角数最多  241,274 三角  ->  3,316 MB
三角数相差 20.0 倍，峰值内存仅相差 1.16 倍
```

> **一处需要提防的假相关：** 峰值内存对三角数的相关系数是 **+0.864**，看似也高，
> 但那是因为三角数最多的样本恰好幅面也最大（225mm x 60mm x 138 层 对 220mm x 60mm x 104~125 层）。
> 单看相关系数会得出「三角数也是主因」的错误结论；正确的判据是上面
> 「20 倍 对 1.16 倍」的对照。后续引用本批数据时勿只取相关系数。

### 4.5 与文档估算的关系

上游按公式估算 `123.stl` 的 `retainedRasterBytes` 下界为 10,390,777,860（约 9.7 GiB），
而本批 pixel-layer 同量级的实测进程峰值为 2.6~3.3 GB。二者**不矛盾**：

```text
retainedRasterBytes 下界  = pixelsPerLayer * layers * 6   假设六通道全层同时常驻
实测 peakWorkingSetBytes                                  进程实际峰值
```

差异说明当前 Retained Dense 路径**并非把六通道全层同时保持在物理内存中**
（存在分阶段释放或系统分页），故上游文档「预算不是峰值承诺、不能替代独立进程
Peak Working Set」这一限定是必要且正确的。**后续 G-M7 的 A/B 必须以
`peakWorkingSetBytes` 为准，不能用 `retainedRasterBytes` 估算值代替。**

## 5.5 真实生产阻塞场景（2026-09-04 用户报告并实测确认）

本节是本报告最重要的补充：**该专项不再是预防性优化，已有真实作业被阻塞。**

### 5.5.1 用户报告

```text
资产    model/obj/reality/finger_suoguo/a-2/0.2.obj
参数    层厚 10um（0.01 mm）
现象    单模型切片耗时约 20 分钟
        0.2.obj + 0.3.obj 一起切片时内存不足，切片失败
```

### 5.5.2 实测确认（Release，2026-09-04）

```text
几何          14,593 面，autoOrient 后 bbox 60 x 220 x 14.289 mm
层数          1,429（10um）
栅格          1500 x 5197 = 7,795,500 列
pixel-layer   111.4 亿      ← 昨天那批 STL 基线是 8~11 亿，高一个数量级
六通道理论    62.2 GB
预估峰值      33.7 GB（按昨天实测 310 MB/亿 pixel-layer 折算）

实跑          450/1429 层用时 593 s → 全程外推约 31 分钟
              进程被终止后物理可用由 4.5 GB 回升至 11.4 GB
              即 450 层时已占约 7 GB，按层数线性外推 1,429 层约 22 GB
机器           物理内存 31.6 GB（页文件 84.7 GB）
```

**判定：单模型预估峰值已超过物理内存总量，靠页文件换页勉强完成，故耗时 20~31 分钟；
双模型需 124 GB+，物理内存与页文件余量均不足，因此失败。**

这不是「内存占用偏高」，而是架构性量级错配：当前 Retained Dense 的内存需求**与层数成正比**，
层厚由 38um 收到 10um，层数即翻 3.8 倍，内存同步翻 3.8 倍。

### 5.5.3 缓解方案比较（均不推荐作为最终解）

| 方案 | 预估峰值 | 代价 |
|---|---|---|
| 现状 635x600 @10um | 33.7 GB | 超物理内存 |
| DPI 降至 400x400 | 14.2 GB | XY 精度降 37%，双模型仍不足 |
| DPI 降至 300x300 | 8.0 GB | XY 精度降 53% |
| 层厚放宽至 20um | 16.9 GB | Z 精度减半，等于放弃需求 |
| **memflow 有界窗口** | **134 MB** | 需完成 MF-04/MF-07 |

降参数是拿精度换内存，且双模型场景无论怎么降都不够（两个 14.2 GB 仍超）。
**memflow 的关键性质是内存不再随层数增长**——后续若需 5um 层厚亦不受影响。

### 5.5.4 修订后的实施路径（用户 2026-09-04 授权跳过 MF-06）

> `DEV_16C_06_MEMFLOW_有界逐层流式切片设计.md` 第 12 节。**

```text
原定顺序   MF-03B4B -> MF-04 -> MF-05 -> MF-06 -> MF-07 -> MF-08
修订顺序   MF-03B4B -> MF-04 -> MF-07            （MF-06 跳过，MF-05 视需求）
```

**MF-06（Sparse Tile/Span）跳过的依据与授权：**

1. **上游设计本就留有此口子。** 任务卡 MF-07 的依赖原文为
   「MF-06 Gate 或**明确跳过 Sparse**」——跳过是设计预留的合法分叉，不是绕过 Gate。
2. **用户 2026-09-04 明确授权跳过**，并要求在文档中声明（即本节）。
3. **Dense 有界流式已足以解决 5.5.2 的场景**：有界窗口 134 MB 对 33.7 GB，
   约 250 倍收益，无需 Sparse 的额外压缩。
4. **Sparse 风险显著更高。** 决策文列其语义风险为「高」，并具体指出稀疏裁剪出错
   可能「丢失小组件、边界一像素、支撑连通或光油扩张区」；`123.stl` 的 17 个连通分量
   正是为此设的 Gate（G-M6）。以更高风险换取当前不需要的收益不合理。

**MF-05（多实例 Barrier）的处置：** 不跳过，但**降级为条件项**。
5.5.1 的双模型场景是两个实例，需要 MF-05 才能受益；单模型场景 MF-04 即可。
故顺序为「MF-04 落地并验证单模型收益 → 再依双模型实际需求决定 MF-05 的优先级」。

**跳过 MF-06 的后果须一并记录：** `G-M6`（`123.stl` 17 个连通分量不丢失）随之不再适用；
若将来重启 Sparse，该 Gate 必须重新激活，且届时 `123.stl` 已不可用（见 §2），
需以本报告 §3 的替代资产重建该 Gate 的判据。

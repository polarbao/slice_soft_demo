## 4. 基线实测（Retained Dense，A 侧）

### 4.1 采集口径

```text
二进制      build-slicesoft/main/Release/slicer_cli.exe
工艺        单材料路径（STL 不携带材质与贴图，无法用多材质工艺）
配置        matopq_baseline.json 的 DPI 635x600、层厚 0.038、MATVOL 关闭
指标        SLICE_TIMING 的 totalMs / sliceProcessingMs / peakWorkingSetBytes
测量条件    **串行、无并发**（实测并发下同一资产偏差可达 32%）
```

`peakWorkingSetBytes` 由切片进程自报，**是进程级峰值工作集**，比上游文档中
「retainedRasterBytes 下界」更接近真实占用——后者按定义只覆盖主要栅格字节，
不含模型、纹理、allocator、JSON 与 TIFF 库。

### 4.2 首个数据点

`需切割甲片-翟晓玲.stl`（12,084 三角，本批最小）：

```text
wall                  59 s
totalMs               57,904.7
gridSetupMs                8.98    ← 单材料不走 MATVOL 逐列求交，故极小
sliceProcessingMs     54,837.5     ← 主项
workingSetBytes        8,646,656   （进程结束时）
peakWorkingSetBytes  2,992,267,264 ← **峰值 2.99 GB**
```

**这是本专项首个真实的 Peak Working Set 实测值。** 上游文档此前只有按公式估算的
`retainedRasterBytes` 下界，无进程级实测。

### 4.3 全批基线（8/8 成功，串行采集）

| 模型 | 三角数 | pixel-layer | wall | totalMs | sliceProcMs | **peakWS** |
|---|---|---|---|---|---|---|
| 单缩裹-云芳 | 31,800 | 811,243,472 | 52 s | 51,290 | 47,884 | **2,658 MB** |
| 单缩裹-圣元 | 29,972 | 928,249,742 | 59 s | 57,922 | 53,929 | **2,880 MB** |
| 单缩裹-登艳 | 37,260 | 928,249,742 | 65 s | 64,389 | 59,670 | **2,911 MB** |
| 单缩裹-翟晓玲 | 41,258 | 928,249,742 | 60 s | 60,356 | 56,107 | **2,886 MB** |
| 需切割甲片-翟晓玲 | 12,084 | 904,848,488 | 59 s | 58,124 | 54,111 | **2,853 MB** |
| 单缩裹-董月云 | 31,373 | 858,045,980 | 55 s | 54,775 | 50,708 | **2,756 MB** |
| 单缩裹-黄晨晨 | 42,305 | 975,052,250 | 62 s | 61,191 | 56,653 | **2,999 MB** |
| 需切割甲片-黄晨晨 | 241,274 | 1,100,918,184 | 71 s | 69,541 | 64,220 | **3,316 MB** |

`sliceProcessingMs` 占 `totalMs` 的 92%~93%，是耗时主项；`gridSetupMs` 因单材料不走
MATVOL 逐列求交而可忽略（首个样本仅 8.98 ms）。

### 4.4 本批数据对专项前提的独立印证

决策文的定性是「主要问题**不是三角形数量**，而是把整个 `width * height * layers`
空间多次常驻」。本批数据直接支持该判断：

```text
峰值内存 vs pixel-layer    相关系数 = +0.996      近乎完美线性
每亿 pixel-layer 的峰值     301~328 MB            八个样本高度一致

三角数最少   12,084 三角  ->  2,853 MB
三角数最多  241,274 三角  ->  3,316 MB
三角数相差 20.0 倍，峰值内存仅相差 1.16 倍
```

> **一处需要提防的假相关：** 峰值内存对三角数的相关系数是 **+0.864**，看似也高，
> 但那是因为三角数最多的样本恰好幅面也最大（225mm x 60mm x 138 层 对 220mm x 60mm x 104~125 层）。
> 单看相关系数会得出「三角数也是主因」的错误结论；正确的判据是上面
> 「20 倍 对 1.16 倍」的对照。后续引用本批数据时勿只取相关系数。

### 4.5 与文档估算的关系

上游按公式估算 `123.stl` 的 `retainedRasterBytes` 下界为 10,390,777,860（约 9.7 GiB），
而本批 pixel-layer 同量级的实测进程峰值为 2.6~3.3 GB。二者**不矛盾**：

```text
retainedRasterBytes 下界  = pixelsPerLayer * layers * 6   假设六通道全层同时常驻
实测 peakWorkingSetBytes                                  进程实际峰值
```

差异说明当前 Retained Dense 路径**并非把六通道全层同时保持在物理内存中**
（存在分阶段释放或系统分页），故上游文档「预算不是峰值承诺、不能替代独立进程
Peak Working Set」这一限定是必要且正确的。**后续 G-M7 的 A/B 必须以
`peakWorkingSetBytes` 为准，不能用 `retainedRasterBytes` 估算值代替。**

## 5. 对专项现状的判定

### 5.1 完成程度（引自上游任务卡 v2.2）

```text
MF-00 .. MF-03B4A   COMPLETE（8 张卡，2026-08-18 ~ 08-21）
MF-03B4B            PREPARED / IMPLEMENTATION GO   前置已满足，尚未开工
MF-04 .. MF-07      PENDING
MF-08               PENDING / INPUT OPEN（依赖设备 SLA/内存上限）
```

**关键：生产完全未接线。** 上游反复声明「生产仍为 Retained Dense」，MF-01..03B4A
未接 `run_slicer`、Production Service、Profile、SPI、Worker、TIFF、preview、report。
故已完成的 8 张卡**对实际切片的内存占用没有任何影响**——§4 实测的 2.99 GB 峰值
正是当前生产路径的真实状态。

### 5.2 因此可做与不可做

| | 现在可做 | 需等到 |
|---|---|---|
| A 侧基线（Retained 峰值与耗时） | **可做**（本报告 §4） | — |
| B 侧对照（Bounded 峰值） | 不可做 | MF-07 生产路由接入后 |
| 同请求 A/B（G-M7 判据） | 不可做 | 同上 |
| 逐层零漂移验证 | 可做（定向测试已存在） | — |

**结论：G-M7 的「峰值内存下降」在 MF-07 之前无法验收，这不是缺陷而是设计顺序**
（决策文 M0..M4 冻结顺序明确 M4 才做自适应路由接入）。本报告的价值在于把 A 侧固定下来，
使 MF-07 落地时能立即做 A/B 而不必回头补基线。

## 6. 遗留与建议

1. **资产入库问题**：本批 STL 位于 `E:\项目资料`，不在仓库内，且属真实客户数据（文件名含人名）。
   是否入库、以何种形式入库（脱敏改名？只留最大的一个？）需用户裁定。
   在入库前，本报告记录的基线**依赖外部路径，不可复现于他人机器**。
2. **`123.stl` 的历史数字处置**：建议在上游 REPORT 中把该模型的数字标注为
   「资产已不可用，仅作容量参考」，避免后续误引为实测基线。
3. **MF-03B4B 是否立即开工**：其准备已冻结且判定为 GO，与本报告的基线工作无依赖，
   可独立进行。但它同样不接生产，完成后仍无法改善 §4 的 2.99 GB。
4. **单材料工艺的局限**：STL 无材质，故本基线走单材料路径，未覆盖 MATVOL 多材质纵深。
   多材质大幅面资产的内存基线仍缺失——现有多材质资产（gubao04 等）幅面小，
   栅格达不到本量级。

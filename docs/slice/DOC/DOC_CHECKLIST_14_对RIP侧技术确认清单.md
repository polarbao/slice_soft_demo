## 0. 为什么需要这份确认

切片软件、RIP、打印软件三方即将做模块化集成。数据链路是：

```text
切片软件 ──S1──> RIP ──S2──> 打印软件通道化 ──S3──> 打印执行
        p0.rgbwsv.2      rip.ch7.1        12 物理通道
```

**S1 已冻结**（切片输出协议），**S3 已存在**（打印软件既有实现），但 **S2 尚未确认**——即"RIP 吃什么、吐什么"这一段。下面 6 个问题就是 S2 上尚未闭合的点。

在这些问题回复之前，切片侧与打印侧都无法编写与 RIP 对接的代码（会返工）。

## 1. 背景速览（作答所需的全部事实）

### 1.1 切片侧输出：`p0.rgbwsv.2`（S1，已冻结，不可改）

```text
目录结构   <packageDir>/manifest.json + layers/layer_%06d.tiff + reports/ + preview/(可选)
通道数     6，固定顺序 R, G, B, W, S, V
位深       8 bit 无符号
存储       stripped（默认，rowsPerStrip 在 manifest 声明）或 tiled → 两者都可能出现
planar     contiguous（交错）
极性       black_is_print → printValue = 0（出墨）、emptyValue = 255（空/不出墨）
背景       模型外区域 6 通道全部 255
DPI        X 与 Y 可不相等（本项目实际使用 X=635 或 720、Y=600）
```

⚠️ **极性最容易搞反**：`0` 是"出墨"，`255` 是"不出墨"。与"值越大墨越多"的直觉相反。

⚠️ **通道语义**：`R/G/B` 是彩色，`W` 白墨，`S` 支撑材料，`V` 光油。**目前 W/S/V 只有 0 或 255 两个值（二值）**，没有中间值。

### 1.2 打印软件侧输入要求：`ChannelSplitter`（S3 上游，硬约束）

打印软件的通道化模块对输入 TIFF 有**硬校验，不满足直接报错**：

```text
samplesPerPixel  必须 ≥ 7      （切片输出只有 6 → 必须由 RIP 补齐）
bitsPerSample    必须 == 8
planarConfig     必须 contiguous（禁 planar）
存储             使用 TIFFReadScanline 逐行读 → 【禁 tiled】
逻辑通道顺序     C, M, Y, K, White, Support, Varnish（前 7 个）
尺寸             同一作业所有层宽高必须完全一致
```

### 1.3 打印软件如何解释像素值（**不对称，重点**）

```text
逻辑通道 0..3（C/M/Y/K）：按阈值映射为墨滴数
    0 → 0 滴 ； 1..119 → 1 滴 ； 120..199 → 2 滴 ； 200..255 → 3 滴

逻辑通道 4..6（White/Support/Varnish）：【取值直接作为墨滴数】，无上界检查
```

### 1.4 墨滴上限按"通道 × 位深"变化（**易错**）

上限 = 该逻辑通道映射到的物理喷头数 × 每喷头最大墨滴数，其中每喷头最大 = `grayBits==2 ? 3 : 1`。

| 逻辑通道 | 对应物理喷头 | 喷头数 | **grayBits=2（默认）上限** | grayBits=1 上限 |
|---|---|---:|---:|---:|
| Cyan / Magenta / Yellow / Black | 各 1 个 | 1 | **3** | 1 |
| **White** | White1, White2 | 2 | **6** ⚠️ | 2 |
| Support | Support1/2/3 | 3 | **9** | 3 |
| Varnish | Varnish1/2/3 | 3 | **9** | 3 |

⚠️ **White 的上限是 6，不是 9。** 若输出 7/8/9，会被下游**静默钳位到 6**，不报错，只是墨量与设计不符。

### 1.5 物理通道顺序（已冻结）

```text
Cyan, Magenta, Yellow, Black, White1, White2,
Support1, Support2, Support3, Varnish1, Varnish2, Varnish3   （共 12 个）
```

### 1.6 材料混合（RIP 需知晓，但不需实现）

打印软件通道化时，逻辑 Support 通道的墨滴会按 **6 : 1** 分配到 `{Support1,2,3}` 与 `{Varnish1,2,3}`——即**约 1/7 的支撑墨滴被路由到光油通道**。该行为默认开启，由打印软件配置控制。

## 2. 六个待确认问题

### Q1【最高优先·阻塞编码】W/S/V 的"二值 → 墨滴数"量化，是否由 RIP 承担？

**背景**：切片侧输出的 W/S/V 是二值（`0`=出墨 / `255`=空）；打印软件期望的是 `0..上限` 的墨滴数（§1.3/§1.4）。二者之间缺一步**量化**。

**若直接透传会发生什么**（两个方向都错）：

| 切片输出 | 切片语义 | 被下游解释为 | 结果 |
|---|---|---|---|
| `0` | 出墨 | 0 滴 | 🔴 **白墨完全不出** |
| `255` | 不出墨 | 255 滴 → 钳到上限 | 🔴 **变成满墨** |

即：**语义完全反转，且不会有任何报错**——打出来相当于一张"底片"。

**三个候选方案**：

| 方案 | 承担方 | 评价 |
|---|---|---|
| **A（我方推荐）** | **RIP 量化** | RIP 本就是"连续调 → 设备墨量"的转换器，语义最合理；切片与打印软件零改动 |
| B | 打印软件插一层 `DropQuantizer` | 可行，但增加宿主职责，且多一个接缝要校验 |
| C | 切片侧输出覆盖量 | ❌ 违反 `p0.rgbwsv.2` 冻结协议，本轮不考虑 |

**需要答复**：
1. 是否由 RIP 承担量化？（是 / 否）
2. 若是：量化档位如何配置？（如白墨固定 6 滴、支撑 9 滴、光油 3 滴？还是由材料 Profile 曲线决定？）
3. 是否能保证输出严格落在 §1.4 的**按通道上限**内（尤其 White ≤ 6）？

**若答"否"**：请说明原因，我方将升级为产品决策（改由打印软件插量化层）。

### Q2【高优先】固定六通道内，白区信号如何避免与真实黑色及物理材料冲突？

**背景**：目前了解到的做法是——RIP 把普通 RGB 纹理区域当作纹理，把**白色区域的 `W/S/V = 0/0/0`** 当作私有识别信号。

**问题所在**：在 `black_is_print` 极性下，`W/S/V = 0/0/0` 的**物理含义是"白墨、支撑、光油三个通道同时出墨"**。这是一个合法的材料组合值，不是保留值。所以该信号：

- 不属于 `p0.rgbwsv.2` 契约的一部分（是隐式约定）；
- 一旦切片侧在某个合法场景写出该组合，RIP 会误判为白区，且**双方都不会报错**。

**另一个曾被提出的方案仍被否决**：改用
`R/G/B/W/S/V = 0/0/0/255/255/255` 作为白区信号。完整审计表明，早期“5 份配置”只是抽样下限：

```text
109 份配置中，59 份明确允许普通模型像素产生该值；
32 份启用纹理的配置使用有效黑色 fallback；
30 个场景入口中 23 个引用上述配置；
39 张现有贴图中 15 张包含可见纯黑像素。
```

在当前协议下，该值的正常含义是“RGB 纯黑打印、W/S/V 不打印”。删除或替换配置只能减少样例，
不能阻止 OBJ 贴图、MTL、3MF ColorGroup/Texture2D 或未来用户输入产生合法纯黑。详细清单与复现口径见
`DOC_ANALYSIS_14_Q2_RIP白区带内信号与配置冲突审查.md`。

**本轮约束修订**：当前阶段不新增逐层 1-bit sidecar。现有 RIP 基本流程已经完成，新增文件会要求
RIP 重新实现输入、缓存、校验和联调。本轮保持单 TIFF 六通道，优先确认以下两条路径：

| 路径 | 说明 | 当前判断 |
|---|---|---|
| **D 真实材料语义（新增·首选）** | 不透明白 `255/255/255/0/255/255`（W 打底）；透明白 `255/255/255/255/255/0`（仅光油）。**零哨兵、零碰撞、零协议改动** | ✅ **推荐首选** |
| A 兼容既有 `WSV=000` | 作为版本化 `rip_bound_intermediate` 私有合同保留；RIP 须在物理量化前拦截，S/V 不得泄漏 | ✅ 可接受（`WSV=000` 已证不可达）|
| B 全 255 表示白 | 白区写 `255/255/255/255/255/255` | ❌ **NO-GO——与背景字节完全相同**，且触发材料闭环缺陷 |
| C RGB 黑哨兵 | 继续使用 `0/0/0/255/255/255` | ❌ **NO-GO**，除非全输入源转义真实黑色 |
| E 纹理区标记 `WSV=000`+RGB 载色 | 白 `255/255/255/0/0/0`、黑 `0/0/0/0/0/0` | ⚠️ 可行但三处代价：S/V 泄漏风险、占用 W 真实语义、需 composer 主动写出当前不可达值 |

**路径 D 为何最优（详见 `DOC_ANALYSIS_14_Q2` §2.2.3）**：

```text
"白"在 RGBWSV 里本来就有物理正解，区别只在【白由什么材料构成】：
  不透明白 = 无彩色墨 + 白墨打底        → 255/255/255/0/255/255
  透明白   = 无彩色墨、无白墨 + 仅光油  → 255/255/255/255/255/0
两者互不相同、不与纯黑纹理碰撞、不与背景碰撞，且每个字节都是【真实材料指令】，
不存在"需要被下游剥离的假值"——这正是哨兵方案的根本风险来源。
```

若切片侧能确定材料构成，直接写 W=0 或 V=0，RIP 无需猜测；若无法确定，统一按不透明白写 `255/255/255/0/255/255`，再由 RIP Profile 决定是否抑制 W 转为透明——**两种做法都不需要哨兵，也不需要 sidecar**。

**Stage 15 项目内验证证据（2026-08-04）**：显式不透明白 Profile 的 W 载体路径已经通过
自动 Gate，但尚未取得外部 RIP 和实物工艺证据。

```text
F-01：真实小马物语模型切片 PASS；纯白载体/W 打印像素均为 150581；
F-04：像素差异仅发生在 W(idx 3)，R/G/B/S/V 差异为 0；
F-02：无严格纯白输入时新旧生产 TIFF 逐层 SHA-256 等价；
项目内 strict Reader：PASS；既有 Golden 28/28 不变；Quick CI：PASS；
Stage 15 未修改本仓库 RIP 源码。
```

这组证据支持路径 D 中的**显式不透明白**分支：切片侧可直接输出
`255/255/255/0/255/255`，项目内 Reader 按普通 W 通道读取即可。请 RIP 侧继续确认目标实现
是否也把它作为普通白墨材料处理。该证据不回答“同一全 RGB Package 能否由 RIP Profile
切换透明/不透明白”，因此原 Q2/Q3 和 12G-TCWS 继续保留。

**🆕 支持路径 A 的新证据（2026-08-03 代码级核实）**：`W/S/V = 0/0/0` 在当前 composer 中**结构性不可达**——

```text
S 通道（base+4）全仓库仅三处写入：
  slicer.cpp:2436  legacy 模型路径 → 显式写 background.value = 255
  slicer.cpp:2839  role=Support   → 写 0，但该 switch case 只写 S 就 return
  slicer.cpp:3125  support 分支   → 位于 else-if 链第三段，只对【非模型像素】生效
且 policy 路径 write_material_pixel()（:2798-2802）写 base+0,1,2,3,5，【完全跳过 base+4】。

⇒ 模型像素要 S=0 只能走 role=Support，而该路径下 W、V 必为 255；
  policy 路径可得 W=0、V=0，但 S 必为 255；
  非模型像素可得 S=0，但 W 必为 255。
⇒ 三者不可能在同一像素同时为 0。
```

即：**既有 RIP 白区信号是"由构造保证安全"，不是碰巧没撞上。** 这与候选值 `0/0/0/255/255/255` 恰好相反（后者是高频合法内容）。

因此我方建议：**保留既有 `WSV=000`，不改协议字节布局**，只补两条保护把隐式约定变成受保护的显式合同：

```text
保护一 Writer 断言：写出前扫描，若出现 W==0 && S==0 && V==0 → fail-closed
        报 PM-SLICER-CONTRACT-0060，不允许发布该包
        （可与既有通道统计扫描合并，零额外遍历开销）
保护二 manifest 显式声明：新增只读字段（不改通道布局、不改像素语义）
        "ripBoundIntermediate": { "whiteRegionSentinel": "WSV=000",
                                  "contractId": "rip_bound_intermediate.1",
                                  "guaranteedUnreachableByComposer": true }
```

完整推导见 `DOC_ANALYSIS_14_Q2_RIP白区带内信号与配置冲突审查.md` §2.1。

**需要答复**：
1. 当前 RIP 实际识别的完整六通道白区字节值是什么？
2. `WSV=000` 的识别发生在 W/S/V 墨滴量化之前还是之后？S=0、V=0 是否可能进入真实支撑/光油？
3. 两个 RIP Profile 对同一白区像素的逐通道输出映射分别是什么？
4. 是否接受 `W=0, S=255, V=255` 作为白区材料信号，由 Profile 决定使用或抑制 W？
5. 若坚持 RGB 黑哨兵，是否接受所有真实纯黑统一转义、manifest 版本化和未知版本 fail-closed？

### Q3【高优先·产品决策】白色的"语义类型"由谁定义、如何传递？

**背景**：表达"这里出白墨"其实已有正解——`W=0`（白墨通道打印）。但据了解，**同一份全 RGB 六通道包，RIP 可以生成"透明白（transparent knockout）"或"不透明白（opaque white）"两种不同结果**。

也就是说白色存在一个**语义类型维度**，而 `p0.rgbwsv.2` 里目前没有地方表达它。

**三条可能的路**：

| 方案 | 做法 | 适用前提 |
|---|---|---|
| ① 由 Profile 决定 | 整个作业统一一种白（RIP 按 Profile 走），切片侧不管 | **同一层内不需要混用两种白** |
| ② 由 manifest 声明 | 切片侧在包级声明本作业的白色类型 | 同上，但归属更清晰 |
| ③ 逐像素区分 | 当前六通道内需保留/转义一个语义值；否则留待后续协议扩展 | **同一层内需要混用两种白** |

**需要答复（此项主要请产品/工艺确认）**：
1. 实际工艺上，**同一层内是否需要同时存在"不透明白"和"透明白"**？（需要 / 不需要）
2. 若不需要 → 采用 ① 或 ②？由谁持有该设置？
3. 若需要 → 请说明区分规则（按材质名？按区域？按纹理内容？）。本轮不新增 sidecar；无法在固定六通道内无歧义表达时，转入独立协议决策。

### Q4【中】RIP 是否支持 PackBits 压缩输入？

**背景**：切片侧已实现可选 TIFF 压缩（`output.tiffCompression.algorithm` = `none` | `packbits`），**默认 `none`**，manifest 中声明 `tiff.compression`，严格 Reader 校验一致性。当前判定为 `NO_GO_DEFAULT`，原因就是目标 RIP 是否支持未确认。

**收益**：若支持，可显著降低包体积与磁盘 I/O（层数多时明显）。

**需要答复**：
1. RIP 读取 TIFF 时是否支持 `Compression = PackBits (32773)`？（支持 / 不支持）
2. 若支持，是否有性能顾虑（解压开销 vs I/O 节省）？
3. 是否希望默认开启，还是保持默认不压缩、按需开启？

### Q5【中】`grayBits` 的请求路径请固化

**背景**：`grayBits`（1 或 2）决定 §1.4 的墨滴上限，因此 **RIP 必须知道它**。但打印软件侧的接口文档中，请求 JSON 示例里没有出现该字段，只在 `profileKeys` 列表中提到 `device.grayBits`。

**需要答复（此项由打印侧与 RIP 侧共同约定即可，不需产品拍板）**：
1. `grayBits` 通过哪个字段路径传给 RIP？（建议 `profile.device.grayBits`）
2. 若请求中未提供该字段，RIP 的行为是？（建议：**fail-closed 报错**，不要默认猜 2）

### Q6【中】RIP 输出能否回写 `dropRange`，并保证取值在按通道上限内？

**背景**：打印软件侧会在 RIP 输出后加一道校验器（S2 校验），其中一条判据是"抽样检查 W/S/V 取值是否在合法范围内"。若 RIP 能在输出 manifest 中声明实际使用的 `dropRange`，校验会更可靠且可自解释。

**需要答复**：
1. RIP 输出的 manifest 中能否包含 `dropRange: { min, max }`（或按通道给出上限）？
2. 能否保证输出的 W/S/V 严格 ≤ §1.4 的按通道上限？
3. RIP 输出的组织形式：每层一个多通道 TIFF（推荐，命名如 `rip_%06d.tif`），还是每层每通道一个文件？（**两种模式不可混用**）

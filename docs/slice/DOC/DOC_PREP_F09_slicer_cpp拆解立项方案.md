## 3. 但有一个必须先补的缺口：**没有字节级 golden**

逐份核过 `tests/golden/expected/` 的 28 个文件：全部是**摘要级或 schema 级**
（输出契约、报告骨架、矩阵期望），唯一带哈希字段的是
`12e_mesh_repair_report_skeleton.json`，而那是网格修复报告，不是切片产物。

也就是说：**一次「必须不改变输出」的重构，目前没有能证明这一点的网。**
250 项回归能告诉你「没有新的失败」，但**不能**告诉你「产出的 TIFF 与重构前逐字节相同」。

这不是可以边做边补的东西——基线必须在**动第一行代码之前**采集，否则就没有对照物。

## 4. 建议的步骤

### 第 0 步（硬前置）：建立字节级基线

在当前 HEAD 上跑一组覆盖主要工艺路径的切片，记录每个产物的 SHA-256：

- 至少覆盖 `closed_mesh_scanline` 与 `relief_heightfield` 两条 `slicingMode`

产出一个可复跑的脚本与一份哈希清单。此后**每一步都对照它**，任何字节差异都必须能解释。

**这一步本身不改 `slicer.cpp`**，可以独立交付与验收。

## 9. 并行可行性（2026-09-16 判定）

### 9.1 F-09 内部：严格串行，不可并行

第 1–6 步**全部编辑同一个文件**。并行抽取不只是文本冲突，更要命的是
**每一步都改变其余步骤所依据的行号与上下文**。这不是加锁能解决的，是任务本身的性质。

第 0 步（建基线）必须**先于**第 1 步完成——它是对照物，不是并行项。

### 9.2 F-09 与 R-10：代码不交叉，但验证交叉，故不能并行

**先更正本文档 §7 早先的说法**（曾写「可并行推进」）。那个判断只看了代码半径，漏了验证层：

| 层面 | 是否交叉 | 说明 |
|---|---|---|
| 代码 | ✗ 不交叉 | R-10 的 29 处钉点在 `contracts/`、`src/slicer_module/`、`apps/`，无一在 `slicer.cpp` |
| **工作树** | ✓ **交叉** | 两者共用同一工作树，R-10 的未提交改动会被编译进 F-09 的构建 |
| **构建目录** | ✓ **交叉** | 同一 `build-slicesoft/main`，ctest 不能并发跑（二进制与 `output/` 都会打架） |

后两条各自足以否定并行。要真并行必须开独立 git worktree + 独立构建目录，
代价是每侧多一次全量构建（约 15 分钟）与一套独立的基线，
而收益只是省下串行的等待——不划算，且引入交叉污染的新风险。

### 9.3 因此：串行，优先级如下

1. **F-09 第 0 步（建字节级基线）** —— 无论后面先做谁，这一步都该最先做：

字节级 PASS 是本步的决定性判据：第 0 步已证实切片可复现（两轮独立运行 738 个产物全等），
因此任何字节差异都只能是搬运引入的。现在全等，等于证明「只移位、不改行为」成立。

**搬运脚本的三道自检**（都真的拦过东西，不是摆设）：

1. 行切分必须可逆（`b"".join(lines) == data`）——该文件 CRLF/LF 混合，做归一化会毁掉它

### 13.1 第一次出现「不能逐字节搬运」

`sample_relief_heightfield_masks`（第 7 步）与 `update_layer_channel_stats`（第 8 步）
都带默认参数。原先只有一个定义、默认值写在定义上；拆成「头声明 + cpp 定义」后
**C++ 不允许两侧都写**（实测 C2572）。

处置：默认值**保留在头声明**（对外仍可用），从 `.cpp` 定义剥离。

反过来（只留在 `.cpp`）也能编译，但默认值对头文件的使用者不可见，
成为看得见却用不了的摆设，下一个调用者会撞上一个没有道理的编译错误。

安全性依据是具体的：第 7 步那个函数的**唯一调用点显式传了全部 6 个参数**，
不依赖任何默认值，重载解析与实参求值完全不变；字节级基线亦为此背书。

**第二次出现时改成了通用能力并先证伪。** 第 7 步是按函数名写死两处字符串替换；
第 8 步同一形状再现，说明不该逐个特判。通用实现只在**签名区**
（定义起点到函数体起始 `{` 的那一行）替换，**绝不碰函数体**——
函数体里的 `x = nullptr` 是赋值语句，误伤就是改行为。

证伪在 6 个函数上跑过：该去的去掉 2 个、不该动的 0 个且字节串与原文全等，
并断言剥离后的文本仍以**原函数体**结尾。

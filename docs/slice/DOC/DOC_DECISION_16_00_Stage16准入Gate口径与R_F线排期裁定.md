## 1. 背景：一句话有两种读法

`TASKS_16` 的启动约束写的是「Stage 14 收口前不得执行任何 Stage 16 代码卡」。
但截至 2026-08-11，Stage 14 的实际状态是
`SLICER PACKAGE READY / INTERFACES FROZEN / EXTERNAL ACCEPTANCE DEFERRED`，
于是「收口」出现两种互斥读法：

```text
读法甲 · Stage 14【切片侧】收口
         14F-05 已 SLICER-SIDE COMPLETE，阶段收口报告已产出
         ⇒ Stage 16 的 16-00 准入复核【现在即可执行】

读法乙 · Stage 14【外部验收】通过
         需 14A_EXTERNAL_ACK 由打印侧书面回签
         ⇒ Stage 16 无限期等待，进度不受我方控制
```

## 2. 用户裁决（2026-08-11）

```text
① Stage 16 的准入 Gate 取【读法甲】—— 以 Stage 14 切片侧收口为准
② 完成 R-F 线涉及的任务后，方可开启 Stage 16 任务处理
③ 本裁定与执行顺序须写入 codex 上下文，由用户在 codex 界面点名启动
```

### 2.1 采读法甲的理由（P）

`16-00-01..04` 四张卡**全部是审计与文档卡，不改一行代码**，出口只是
`baseline_identity.json`、carry-in 判定矩阵与 `GO / DEFER / NO-GO` 结论。
用一个不受我方控制的外部回签去锁一个纯审计动作，代价是把整个 Stage 16 挂在他方进度上，
而收益为零。

### 2.2 Stage 14 Worker/Facade 边界复核

本裁定只解锁 `16-00` 的准入复核与其后按卡片依赖放行的实施卡。
最新 `REPORT_14` v3.61 已确认早期任务表中的内部阻塞均已解除：
`14D-05/06/07/08` 与 `14C-06B` 全部 `COMPLETE`。须在 `16-00-02` 中逐项显式登记：

| 阻塞项 | 性质 | 影响的 Stage 16 卡 |
|---|---|---|
| Stage 14 Worker/Facade 最终边界 | **已满足**：真实 Worker、安全发布、取消、重能力路由与 SPI 生命周期均完成 | `16C-08` 可排期，但其 Preview/I/O 解耦实现仍为 `still_required` |
| `13B` 的 `OPEN INPUT`：设备 buildVolume/origin/axes 与 22 实例生产预算未定 | **产品输入**，切片侧定不了 | `16C-10` —— 出口本就是「只输出实测，状态仍 `INPUT_OPEN`」，**不是一张能关掉的卡** |
| `14A_EXTERNAL_ACK` 未回签 | 外部 | Stage 14 侧的 14F-02..05 外部验收；不阻塞 16-00 |

⇒ 排期时 `16C-01..09` 可推进；`16C-10` 只能输出实测，不能在产品输入缺失时关闭生产 Gate。

## 3. R-F 线的范围界定

「R-F 线」在本裁定中定义为 **RENDER 专项的显示质量线**，含两张卡：

| 卡号 | 任务 | 说明 |
|---|---|---|
| **R-F-01** | 平滑顶点法线 + crease angle 阈值 | 修 `SceneViewMeshBuilder.cpp:35/366/385` 只发面法线导致的刻面 |
| **R-F-02** | R-F-01 的基线重固化与证据刷新 | 法线一变，mesh 字节基线与显示证据全部失效，必须连带处理 |

### 3.1 R-C-00 与 T-A-05B-02 的归属裁定（用户 2026-08-11 授权我方判断）

**① `R-C-00` 并入 `R-F-02`，不单独立卡。**

理由不是"相关"，而是**二者是同一次测量**（P）：

```text
R-F-02 必须在 22 资产聚合场景重跑 mesh 字节基线（法线一改，105.15 B/三角 必然失效）
R-C-00 要的是【同一场景、同一 harness】，只是把统计口径从 mesh 扩到
       mesh / 纹理 / 预览三项 + 上传耗时
⇒ 拆成两张卡 = 跑两次完整 Release 测量周期，纯浪费
```

⇒ `R-F-02` 的验收口径扩展为三项字节构成与上传耗时；`R-C-00` 状态改为
`MERGED INTO R-F-02`，其原定出口（R-C-01 是否值得做受控修订的判据）由 R-F-02 承担。

**② `T-A-05B-02` 延后，且必须与 `T-A-05B-03` 捆绑执行。**

```text
T-A-05B-02 的唯一下游是 T-A-05B-03（删除 Writer），而删除确认尚未给出
⇒ 单独做 05B-02 拿不到任何终局价值，只是把债从 A 挪到 B，
   中间还多养一段「迁移了但没删干净」的中间态
⇒ TIFF 的实际风险已被 T-A-05B-01 关死（fail-closed + 弃用告警 + 无静默回退）
   它现在是【债】，不是【风险】
```

⇒ 触发条件：**用户给出 handwritten Writer 删除确认**后，05B-02 与 05B-03 一次做完。

⇒ 因此 **R-F 线 = R-F-01 + R-F-02（含 R-C-00 口径）**，两张卡完成即打开 Stage 16 准入 Gate。

## 3.5 任务优先级分级（本裁定的核心产物）

### 3.5.1 尽快完成（三张，全部零外部依赖）

| 顺序 | 任务 | 判定理由 |
|---|---|---|
| 1 | **R-F-01** 平滑顶点法线 | 唯一用户可见的质量缺陷；A 级根因已定位；零前置 |
| 2 | **R-F-02** 基线重固化（含 R-C-00 口径） | R-F-01 的必然连带，跳过即留下一批失效基线；顺带一次测完纹理侧 |
| 3 | **16-00-01..04** Stage 16 准入复核 | 纯审计零代码；工作树干净的当下成本最低，越晚做越要先拆账 |

### 3.5.2 可延后（每项均有明确触发条件，不满足不得开工）

| 任务 | 触发条件 | 阻塞归属 |
|---|---|---|
| `T-A-05B-02` + `T-A-05B-03` | 用户给出 handwritten Writer **删除确认** | 用户 |
| `T-A-04` 压缩默认 PackBits | 目标 RIP / 控制软件互操作**书面证据** | 外部 |
| `T-A-06` LZW / Deflate 扩展 | 出现新增算法需求；每种算法各自过 RIP 确认 | 需求侧 |
| `R-C-01` / `R-C-02` 屏幕空间 DTO | R-F-02 数据证明收益足够 **且** 打印侧愿意回签 | 数据 + 外部 |
| `R-D` 组 Qt6 / QRhi | 出现 D3D11 不可用的部署环境，或 Qt 5.15 维护到期 | 无触发迹象 |
| `R-E-01` 性能验收重定标 | `R-D-02` 完成 | 同上 |
| `H-G-01..06` 三维层栈预览 | `DOC_PREP_HOSTFLOW_H_G` §6 的 5 项产品 Gate 输入 | 用户 |
| `CI` `C-A-02`..`C-C-01` | 用户解除暂缓 **且** 定下 runner 形态（甲/乙/丙） | 用户 |
| `16C-08` Preview/IO 解耦 | 16-00 carry-in 审计后按依赖排期；Stage 14 Worker/Facade 前置已满足 | 阶段任务 |
| `16C-10` 22 实例预算 | 13B 设备 buildVolume/origin/axes 与生产预算 | 产品输入 |
| `14F-02..05` 外部验收 | 打印侧书面回签（`14A_EXTERNAL_ACK`） | 外部 |
| `12G-TCWS` | G1–G8 与 RIP 契约冲突解决 | **明确冻结，不得实现** |

> **不在上表、但杠杆最高的非技术动作**：`N-03` —— 书面对齐打印侧要「导入切片产物」
> 还是「内嵌切片器」。见 `DOC_ANALYSIS_能力边界与UI融合_四问核实.md` §3.4 / §5。
> 它的答案决定后续整条 UI 线是否值得投入，但需用户跨项目推动，切片侧做不了。

## 4. 冻结的执行顺序

```text
第 1 步  R-F-01  平滑顶点法线                    ✅ COMPLETE
第 2 步  R-F-02  基线重固化与证据刷新（含 R-C-00）✅ COMPLETE
         ─────────── R-F 线已完成，Stage 16 准入 Gate 已打开 ───────────
第 3 步  16-00-01..04  Stage 16 准入复核          ← 当前主线，纯审计
第 4 步  按 16-00-04 结论放行 Wave 1

⏸ 延后（等触发条件，见 §3.5.2）：T-A-05B-02 + 03 捆绑、T-A-04、R-C-01/02、
   R-D 组、H-G 组、CI 组、16C-10
```

### 4.1 一个与顺序相关的既存事实（A）

`16-00-01` 要求「记录 `git status --short`；区分用户未提交变更与 Stage 16 可用基线」。
2026-08-11 本地提交后**工作树已干净**，是固化 `baseline_identity.json` 的最佳时点。
若在 R-F 线执行期间再次积累未提交改动，该卡需先额外拆账。

### 4.2 🔴 Stage 14 之前的性能基线已整体作废（A）

`T-A-03` 已把默认 Writer 切为 LibTIFF 4.7.1，同机 Release Writer-only p50 相对 handwritten
变化区间为 **+1.086% ~ +48.775%**。因此：

```text
13F-R1-06 记录的「完整写包 6516.322 ms」是 handwritten 时代的数字
12F / 13F 的全部 Release 性能数字同理
⇒ 均【不可与 Stage 16 新基线直接比较】
⇒ 16C-02「Stage 14 后 Release 基线」必须整套重跑，不得复用旧数做 before/after
```

## 5. 边界

```text
✅ 本裁定只改变【准入 Gate 的口径】与【执行顺序】，不改变 Stage 16 的任何任务内容与验收标准

   先语义后性能；不并行改动同一热路径的语义与存储形式

⛔ 本裁定不放宽 Stage 14 任何冻结面：PM_SPI_VERSION、11 个 pm_* 导出、15 项能力、
   12 份合同哈希、p0.rgbwsv.2 协议均不变
```

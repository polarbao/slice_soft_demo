### Current Code Reality

- `rip_module/source.json` 仅支持一个完整的 `sourceDirectory`，固定到 `RIPDLL_20260909`。
- 打包器要求同一目录同时具有 3 个二进制和 8 个 `CmykFiles` 资源。
- `RIPDLL_20260917`、`RIPDLL_20260918` 与 `RIPDLL_20260920` 均只有二进制、头文件和 `rip_cli.c`，没有资源目录。
- 宿主与合同测试对模块版本 `1.2.0` 做 fail-closed 检查。

### Current State

20260909 模块在项目内已完成切片侧验证；20260917/20260920 尚未被受控来源 pin、打包器、宿主版本门和测试接纳。

### Target State

1. 引入 `slicesoft.rip.source.2`，分别固定二进制目录和资源目录。
2. 默认使用 20260920 二进制与 20260909 `CmykFiles`，生成模块版本 `1.3.0`。
3. 保留 source v1 解析兼容；缺任一来源或能力参数时 fail-closed。
4. 自检要求 `--transparent <0-4>`、`--ripmode <0|1>` 和 `--verbose`。
5. 验证默认调用不注入 `--verbose`，中文目录可执行，正常日志不再被逐像素 DEBUG 淹没。
6. 不修改 UI 的“正常 RIP/3 倍墨量 RIP”产品映射；供应方 0/1 的技术含义继续在文档中单独说明。
7. 0917/0918 作为中间版本留存差异与输出证据，运行时只部署最新 0920，不形成多版本选择 UI。

### Historical State

20260909 是首个同时带 `--ripmode` 和新版完整资源的已验收目录；旧 `RIPDLL` 的 `CMYK.icc` 与 `linear.csv` 哈希不同，不能作为新版本资源回退。

### Pending Confirmation

- 供应方尚未提供“20260920 二进制与 20260909 资源”的书面兼容矩阵；本地真实 RIP 只能形成工程证据，不能替代外部确认。
- 外部分发授权、打印软件消费和物理打印验收不在本次本地适配范围。

### Risk Points

- 新目录资源缺失若被静默忽略，会产生混版或运行时失败。
- 二进制与资源来自不同目录，provenance 必须分别记录，禁止仅写一个模糊版本名。
- 0920 的 `ripMode=1` 已观察到相对 0917/0918 的输出变化，必须跑宿主结果合同和两档模式矩阵，不能只做 `--help` 探测。
- 模块版本升级会同时影响宿主准入、合同 fixture 和结果中的模块身份。
- `--verbose` 会产生巨量逐像素日志，宿主默认参数不得启用。
- 现有 S2、输出验证和诊断隔离规则不得因供应方升级而放宽。

## 方案比较

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 把 20260909 的 `CmykFiles` 手工复制进 20260920 | 现有脚本无需改动 | 供应方目录被人工污染，来源不可追溯，后续更新容易漏资源 | 不采用 |
| 继续固定 20260909，只替换部署目录内 EXE/DLL | 改动少 | pin 与实际产物不一致，hash/provenance 失真 | 不采用 |
| source v2 显式组合二进制和资源来源 | 来源清晰、可 fail-closed、便于后续日期版更新 | 需同步脚本/CMake/测试 | 采用 |

## 不变边界

`p0.rgbwsv.2`、R G B W S V 顺序、uint8、`black_is_print`、QProcess 进程外架构、自动 RIP 默认关闭、严格/诊断输出隔离及 `EXTERNAL_VALIDATION_DEFERRED` 均保持不变。

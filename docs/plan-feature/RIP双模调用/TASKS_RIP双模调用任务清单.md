**先做 H-01 / H-02 的理由**：这两项对现有行为是零变化——把今天的 QProcess 路径原样落进
`RipProcessBackend` 即可，不引入新后端。这样做等于把"能不能双模"这个风险
从代码结构里摘出去，后面 RIP 侧无论给不给重编版本，这两项都不白做。

**不先做 H-03 的理由**：没有重编的 `RipSlicer.dll`，写出来的进程内后端**加载就会绑到宿主的
`tiff.dll`**，既跑不起来也测不了，只能变成一段无法验证的代码。

## 6. S0 必须先问清的一件事

**供方是否持有 `RipSlicer.dll` 的源码与可复现构建。**

若答案是否，R-01 与 R-03 都无法交付，**双模在物理上不成立**，整条线退化为"exe 唯一"，
S1 之后的全部条目直接作废。这一问要放在 S0 的第一位，避免两轮往返后才发现。

## 7. 不做的事

| 项 | 理由 |
| --- | --- |
| 先写 `RipLibraryBackend` 占位 | 没有重编 DLL 时它加载即错，写出来也无法验证 |
| 把校验权下放给 RIP | 无论哪种承载形态，输出逐层校验都留在宿主。进程内没有 `exitCode`，**更不能**用"函数返回 `RIP_OK`"替代 |
| 统一两侧 libtiff 版本了事 | 能省掉加载期冲突，但省不掉重编，还会新引入 `TIFFSetErrorHandler` 这类进程级全局的运行期串扰。详见 DECISION-01 |
| 默认切到进程内模式 | S6 明确：默认仍为 `process` |

## 2. 未执行，及各自的理由

### CFG-1 把 T 策略提为单文件 —— **收益最大，但改动面需要单独一轮**

要改加载器、**5 处 CMake/脚本拷贝点**、以及两条硬断言
（`files.size() == 10`、10 份策略一致）。这不是"顺手做掉"的体量，
混进本轮会让一次提交同时承载三件不相干的事。**建议单独立一条任务。**

### CFG-2 删 7 份无执行消费方的 T 副本 —— **依赖 CFG-1 先定**

若 CFG-1 落地，这 7 份自然不再进部署包，无需单独删；
若 CFG-1 不做而先删它们，三处循环断言都要改，且**我未实测删后行为不变**
（推断依据是 10 份策略一致，但推断不是验证）。**顺序上它应在 CFG-1 之后。**

### CFG-3 / CFG-4 合并 UI 预设 —— **会减少用户可见选项，不擅自做**

这两条合的是**用户在下拉里能选到的工艺**：

- CFG-4（G1）涉及 `DefaultPresetId()`，**改默认 id 会波及所有按 id 解析的调用方**；
- CFG-3（G2）合并后 `RgbWhiteVarnish` 失去唯一预设入口，
  且已保存的 workspace 若按 preset id 持久化可能失配（**我未验证**）。

更要紧的是：**"选项太多"是感受，"哪些该合"是产品判断。**
我能给出「它们只差一个枚举」这个事实，但"是否应该让用户少一个选择"不是我该替你定的。

### ~~UX-1 把「导入落位与规则排版」从 tab 4 移到 tab 0~~ —— **2026-09-20 已完成**

原判断是「要先有回归护栏」。已按此顺序执行：

1. **先补护栏** `hostflow_panel_ownership`：把「哪个控件在哪一页」钉死，
   沿父链找被标签组收录的那一级再比对标签**文案**（不比下标——下标会随插入顺序悄悄变）。
   已证伪：改错一条期望即精确变红。
2. **再搬迁**：整组迁到「模型」页紧邻「添加模型」，「变换与排版」更名「变换」。

**测绘指出的最危险一处已规避**：`GroupHostInspectorSections` 在
`groups.size() != titles.size()` 时**静默 return**——不报错、不日志。
搬走一个 group 而不改标题列表，会编译通过、测试全绿、程序照跑，
只是表单换行策略悄悄变了。

**但测绘推荐的改法是错的，实测推翻了它。** 它建议「删除该调用」，
理由是单 group 的页面不需要子标签。照做之后 `hostux_full_ui_scale_*`
三条全红：`PAGE 4 SECTION 0 overflow=14`。

先试了它给的补救（显式设 `WrapLongRows`），**仍然 14px**——说明换行策略不是原因。
换成它标为「保守」的那个选项（保留单页 sections 包装）后立刻归零。

**真实原因**：`sections` 这个 `QTabWidget` 的最小尺寸比它包住的 `QGroupBox` 小。
删掉包装等于把 group 的最小高度直接暴露给 `ConfigureHostInspectorPages` 的滚动区，
于是触发零滚动判据。**「保守」选项不是保守，是必需。**

这一条也说明：`GroupHostInspectorSections` 顺带承担了一个**没有写在名字里**的职责
——给页面一个可压缩的外壳。它的名字只说「分组」。

**顺带修掉一个既有隐患**：`HostModelListPanel::Clear()` 此前只清列表不刷控件，
摘要文案与按钮启用态会停在清空前的值。搬入排版按钮后这一点变得可见。

**一处刻意的判据替换**：排版按钮的启用原本看场景实例数（`SetSceneState` 喂），
改用展示列表计数——排版针对的正是已导入的模型，语义一致，
且省掉把 `SetSceneState` 再接到五个调用点。测试按生产路径先 `AddModel` 再断言。

**另一处实测修正**：整组以 `QFormLayout` 8 行的形态搬进「模型」页会让该页
超出零滚动判据 **316px**——那一页还要放模型列表与预检表。
改成紧凑网格（两个开关并排、原点与排版参数各挤一行）后归零。
**「把一组控件原样搬到另一页」在有布局门禁的地方不成立**，形态要跟着换。

**用户手册同步改了 4 处 + 滚轮规则 1 处**；两处截图已标注失真待重拍。
REPORT / DOC_DECISION / TASKS 里的历史记录**一律不动**。

### UX-5 `scene_admission` 的耗时记进 `gridSetupMs` —— **查下来不值得改**

调研里把它标为"命名错位"。实际查了消费方之后我不这么认为：

`gridSetupMs` 是 **CLI、worker、宿主共用**的键（`CliDiagnosticJson.cpp:65`、
`main.cpp:356`、`WorkerSliceExecutor.cpp:227`、`HostSliceJobPanel.cpp:387` 等），
在 legacy 路径下它名副其实。问题只在**宿主把场景路径的 admission 阶段复用了这一行**。

真修要么新增一个耗时键（波及 CLI 与 worker），要么做场景专属标签。
**为一个显示措辞付这个波及面不划算。** 记录在案，不改。

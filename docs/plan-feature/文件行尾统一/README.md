# 文件行尾统一

本目录记录仓库行尾（CRLF / LF）混杂问题的现状实测、标准选型、实施方案与任务状态。

## 为什么要立专项

盘上**三种状态并存**，且有 176 个文件**单文件内混合**。这不是洁癖问题，它有具体代价：

- 批量改源码时锚点匹配必须行尾感知，写死一种就会 0 命中或静默改错。本专项立项前的
  一场会话里，仅此一项就导致 5 次补丁失败，其中 2 次直接造成构建失败、跑的是旧二进制。
- 单文件内混合时，「按文件主流行尾回填」这条规则本身也会出错——单行锚点没有换行符，
  推导会退化。
- diff 噪声：编辑器或工具无意归一化整个文件时，一处改动显示成全文重写。

## 当前结论

- **问题只在检出这一层**。仓内 blob 普查：LF 3035、CRLF **0**、混合 1（归档聊天导出）。
  仓库从来就是纯 LF 的，`core.autocrlf=true` 一直在提交时做转换，只是没人量过仓内。
- **标准取 LF**，理由不是「占多数」，而是仓内本就如此——选 CRLF 等于反向改 3035 个文件。
- **修复就是一条 `.gitattributes`**：`* text=auto eol=lf`。原文件没有 `text=auto`，
  于是检出行为完全由各人的 `core.autocrlf` 决定，工作树才会与仓内不一致。
- **没有「存量 CRLF 文件要转换」这回事**。初版方案排了六波、估算 2856 个文件，
  那是基于**量错对象**得出的工作量，已取消。

## 一次必须记住的返工

初版普查量的是**工作树字节**（LF 1561 / CRLF 1295 / 混合 176），并据此推断
「存在 `core.autocrlf=false` 的环境往仓里提交过」。改量**仓内 blob** 后，该推断被推翻。

> 「行尾不统一」这句话必须先问**哪一层不统一**。仓内、工作树、检出后，三者可以完全不同。

两版数据都保留在现状实测文档里，因为「量哪个」本身就是本专项最重要的结论。

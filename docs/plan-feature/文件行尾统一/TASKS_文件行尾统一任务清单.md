## 2. 已取得的证据

| 判据 | 结果 |

| 仓内 blob 普查 | LF 3035、CRLF **0**、混合 1（归档聊天导出，不在范围） |
| 109 个文件盘上转 LF 后的仓库改动 | **零**——git 认为等价 |

第三条是最有力的一条：盘上从混合改成纯 LF 而 git 报告「没有变化」，
同时证明了转换只动行尾、且仓内早就是 LF。

## 3. 一次值得记下的返工

初版任务卡排了六波、估算涉及 2856 个文本文件，其中「波 3：转换 380 个纯 CRLF 源码」
这一项**对应的文件在仓内根本不存在**。

原因是初版普查量的是**工作树字节**而非**仓内 blob**。`core.autocrlf=true` 一直在提交时
把 CRLF 转成 LF，仓内从来就是干净的；盘上的 CRLF 是检出时转出来的。

> 教训：「行尾不统一」必须先问**哪一层不统一**。仓内、工作树、检出后，三者可以完全不同。
> 量错一层，整条方案都会建在错的前提上。

## 4. 与并行线的关系

工作树内另有一条线的 **9 个未提交改动**，其中
`apps/slicer_ui_host_sim/HostRipJobController.cpp`（盘上 1344 : 40）与
`tests/rip_integration/RipIntegrationTests.cpp`（934 : 40）是混合最严重的文件之列。

**本专项未转换它们**，因为转换会与对方未提交的改动冲突。对方落盘后，
这些文件会在下次检出时自然收敛，不需要专门处理。

同理，方案 §3 里那条 `git reset --hard` 的刷新办法**在本仓当前不可用**——
它会直接毁掉那 9 个改动。

# PLAN：文件行尾统一实施方案

> 依据：[CONTEXT_行尾现状实测](CONTEXT_行尾现状实测.md)

## 1. 标准选型：LF

| 依据 | 说明 |
| --- | --- |
| 已是多数 | 1561 : 1295，转换面更小 |
| git 的仓内规范形态 | `text=auto` 的默认归一化方向就是 LF，顺着工具走而不是对着走 |
| 工具链无阻碍 | MSVC、CMake、PowerShell、Python 在 Windows 上都接受 LF |
| 中文内容无关 | 编码是 UTF-8，与行尾选择正交 |
| **仓内已有先例** | 现有 `.gitattributes` 那条冻结样本用的就是 `eol=lf`，跟随既有约定而非另立一套 |

### 关于「仓内 LF、盘上 CRLF」这个折中

本机 `core.autocrlf = true`（系统级），其语义正是「仓内 LF、检出 CRLF」。
只写 `* text=auto`（不带 `eol`）就能得到这个效果，且对现有工作树扰动最小。

**仍然不取它**，两条理由：

1. 它把盘上行尾**交给各人的本地配置**。谁的 `autocrlf=false`，谁盘上就是 LF，
   跨人不一致又回来了。要确定就得写 `eol=`，那就等于在选 `lf` 还是 `crlf`。
2. 仓内已有的 `eol=lf` 先例。同一个仓里两种 `eol` 取值，是给后来人埋坑。

**代价要说清**：取 `eol=lf` 后，现有工作树里大批文件会从 CRLF 变成 LF，
各人首次检出时编辑器会显示整文件变化。这是一次性的，但不是零成本。

### 为什么不是 `eol=crlf`

先说清一点：**`eol=crlf` 同样能解决立项的痛点**。痛点是「不统一」而不是「哪一种」，
盘上统一成 CRLF，脚本一样可以按 CRLF 写死，混合态一样消失。本项目又只在 Windows 上
构建，选它不会有工具链问题。

不取它的理由只有两条，都不是「它解决不了」：

1. 仓内已有 `eol=lf` 的先例（那条冻结样本），同一个仓里两种 `eol` 取值是给后来人埋坑。
2. `eol=lf` 下仓内存什么、检出就是什么，少一层转换；出问题时少一个可能的变量。

## 2. 结构性修复先于一次性清理

**先补 `.gitattributes`，再做转换。** 顺序不能反：先转换再补规则，等于把已经理顺的
文件重新交给各人的 `core.autocrlf` 去搞乱，过一段时间原样长回来。

拟定内容（最终以任务卡为准）：

```gitattributes
# 默认：仓内一律 LF，检出也是 LF
* text=auto eol=lf

# 二进制：不做任何行尾转换
*.pdf binary
*.png binary
*.tif binary
*.tiff binary
*.dll binary
*.exe binary
*.lib binary

# 按精确字节校验的冻结样本：单独钉住（沿用既有做法）
samples/configs/3mf/three_mf_texture2d_checker.json text eol=lf
```

模型资产（`.obj` / `.mtl`）是否纳入默认规则，取决于第 4 节的实测结论。

## 3. 波次执行，每波独立可回滚

一把梭全仓转换的问题不是工作量，是**出了问题无从定位**——2856 个文本文件一起变，
字节级基线若红，没法二分。故分波：

| 波次 | 范围 | 文件数（估） | 闸门 |
| --- | --- | --- | --- |
| 波 0 | 补 `.gitattributes`，不转换任何文件 | 1 | 核心档 |
| 波 1 | **176 个混合文件**中的源码与脚本 | ~90 | 核心档 + 字节级基线 |
| 波 2 | 其余混合文件（文档为主） | ~86 | 核心档 |
| 波 3 | 纯 CRLF 的源码、脚本、配置 | ~380 | 全量档 + 字节级基线 |
| 波 4 | 纯 CRLF 的文档 | ~514 | 核心档 |
| 波 5 | 模型资产 `.obj` / `.mtl` | ~216 | **全量档 + 字节级基线**，见 §4 |

波 1 优先，因为混合文件才是实际扎人的那批；做完这一波，补丁脚本的行尾感知逻辑就能退休。

## 4. 模型资产单独裁决

`.obj` / `.mtl` 共 216 个、以 CRLF 为主且零混合，是唯一需要单独论证的类别。

已核查的事实：

- 模型字节进 `sourceHash`，但该哈希运行时重算、不签入仓库；
- `tests/golden/expected/` 与 `samples/configs/scene/` 里的 `sourceHash` 均为占位串；
- 字节级基线的 11 例清单不含任何 64 位十六进制串。

**但这是推理，不是实测。** OBJ / MTL 解析器对行尾是否完全免疫，必须实测：
在波 5 里先只转换**基线用到的那一个** `.obj`（`model/obj/reality/finger_suoguo/03.obj`），
跑字节级基线；逐字节一致才转其余，不一致则该类整体排除并在 `.gitattributes` 里
用 `-text` 钉住现状。

> 这一波放在最后、且单独设闸门，就是因为它是唯一可能真正打破产出的类别。

## 5. 不做的事

| 项 | 理由 |
| --- | --- |
| `git add --renormalize` 一次性全仓 | 见 §3：出问题无从二分 |
| 改 `docs/archive/` 下的历史存档 | 那是归档，不参与构建；它也是混合最严重的（5787 : 21127），转换收益为零 |
| 动 codex 未提交的在制品 | 工作树里有另一条线的 9 个改动，转换会与之冲突；须等对方落盘后再纳入波次 |
| 顺手重排或格式化代码 | 本专项只改行尾。任何其它改动都会让「逐字节一致」这条判据失效 |

## 6. 验证判据

每波结束都要满足：

1. 该波涉及文件的行尾**只有一种**（脚本复核，不靠肉眼）；
2. 未涉及的文件**一个字节都没动**（`git diff --stat` 范围核对）；
3. 对应档位闸门的失败集合等于基线；
4. 涉及源码的波次，字节级基线 11 例 738 产物逐字节一致。

第 2 条容易被忽略：编辑器或脚本很容易顺手改到范围外的文件，而那种改动混在几百个
文件的 diff 里根本看不出来。

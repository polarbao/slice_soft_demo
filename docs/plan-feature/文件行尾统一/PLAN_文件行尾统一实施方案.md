# PLAN：文件行尾统一实施方案

> 依据：[CONTEXT_行尾现状实测](CONTEXT_行尾现状实测.md)
> **本方案于 2026-09-22 被实测大幅缩减**：初版计划六波、涉及 2856 个文本文件；
> 量清楚仓内本就是纯 LF 之后，真正要做的只剩一件事。

## 1. 结论先行：一条 `.gitattributes` 就是完整修复

仓内 blob 已是纯 LF（3035 : 0），问题只在**检出**这一步——
`core.autocrlf=true` 把 LF 转成 CRLF 写到盘上，而脚本直写的是 LF，两者在盘上共存。

补上

```gitattributes
* text=auto eol=lf
```

之后检出也产出 LF，工作树就与仓内一致。**没有「存量 CRLF 文件要转换」这回事**——
那是初版方案基于错误测量得出的工作量。

## 2. 标准选型：LF

| 依据 | 说明 |
| --- | --- |
| **仓内本就是 LF** | 3035 个文件，零例外。选 CRLF 等于把 3035 个文件反向改一遍 |
| 仓内已有先例 | 原 `.gitattributes` 那条冻结样本用的就是 `eol=lf` |
| 工具链无阻碍 | MSVC、CMake、PowerShell、Python 在 Windows 上都接受 LF |
| 中文内容无关 | 编码是 UTF-8，与行尾选择正交 |

`eol=crlf` 其实同样能消除「不统一」这个痛点——痛点是不统一而非哪一种。
不取它只因为上表第一条：那会把仓内 3035 个文件全部反转，代价与收益完全不成比例。

## 3. 实施：两步，第一步已完成

| 步 | 内容 | 状态 |
| --- | --- | --- |
| 一 | 补 `.gitattributes`：`* text=auto eol=lf` + 二进制清单 + 冻结样本保持 | ✅ 已落 |
| 二 | 让现有工作树收敛到 LF | 🟡 见下 |

### 第二步为什么不能一把梭

让工作树立刻全部变 LF 的标准做法是

```bash
git rm --cached -r . && git reset --hard
```

**本仓当前不能这么做**：工作树里有另一条线的 9 个未提交改动，`reset --hard` 会直接毁掉。

可行的三条路：

1. **自然收敛**（推荐）：`.gitattributes` 已生效，此后任何检出、切分支、
   `git checkout -- <file>` 都会把经手的文件写成 LF。不需要额外动作。
2. **脚本直转**：对指定范围把盘上的 CRLF 改成 LF。已对 109 个混合的源码/脚本做过
   （见任务卡），**对仓库零改动**——git 认为转换前后等价，这正是「仓内本就是 LF」
   的直接证据。
3. **各人自行刷新**：工作树干净时执行上面那条命令。这是每个人自己的事，不由本专项代劳。

## 4. 不做的事

| 项 | 理由 |
| --- | --- |
| 批量「转换存量 CRLF 文件」 | 仓内不存在这种文件。初版方案的波 2~5 据此取消 |
| `git reset --hard` 刷新工作树 | 会毁掉并行线的 9 个未提交改动 |
| 动 `docs/archive/` | 仓内唯一的混合文件在那里，但它是归档，不参与构建 |
| 动模型资产 | 仓内已是 LF，无需转换；`.gitattributes` 里用 `-text` 钉住现状即可 |
| 顺手重排或格式化 | 本专项只碰行尾 |

## 5. 验证判据

1. `git check-attr text eol -- <任一源文件>` 返回 `text: auto` / `eol: lf`；
2. 仓内 blob 普查：非归档文本文件零 CRLF、零混合；
3. 盘上转换后**仓库零改动**；
4. 涉及源码时，字节级基线 11 例 738 产物逐字节一致。

第 3 条是本专项最有说服力的判据：如果盘上从混合改成纯 LF 而 git 报告「没有变化」，
那就同时说明了两件事——转换只动了行尾，且仓内早就是 LF。

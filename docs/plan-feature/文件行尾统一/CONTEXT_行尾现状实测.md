# CONTEXT：行尾现状实测

> 采集日期：2026-09-22
> **本文档于当日被自己的实测推翻过一次，见 §1。保留两版数据是因为「量哪个」这件事
> 本身就是本专项最重要的结论。**

## 1. 一次关键更正：量错了对象

初版普查量的是**工作树字节**，得出「纯 LF 1561、纯 CRLF 1295、混合 176」，
并据此推断「存在 `core.autocrlf=false` 的环境往仓里提交过」。

**这个推断是错的。** 改量**仓内 blob** 后：

| 对象 | LF | CRLF | 混合 | 二进制 |
| --- | --- | --- | --- | --- |
| **仓内 blob** | **3035** | **0** | **1** | 190 |
| 工作树字节 | 1561 | 1295 | 176 | 190 |

仓内那唯一一个混合是 `docs/archive/.../chat_exports/` 下的聊天导出，本就不在范围内。

**也就是说：仓库从来就是纯 LF 的。** `core.autocrlf=true`（本机系统级）一直在提交时
把 CRLF 转成 LF，只是没人量过仓内。

> 教训：「行尾不统一」这句话必须先问**哪一层不统一**。仓内、工作树、检出后，
> 三者可以完全不同。量错一层，后面整条方案都会建在错的前提上——初版方案里
> 「波 3 转换 380 个纯 CRLF 源码」这一项，对应的文件在仓内**根本不存在**。

## 2. 真实成因：检出与直写并存

工作树的混合来自两条路径同时写文件：

- **git 检出**：`autocrlf=true` 把仓内的 LF 转成 CRLF 写到盘上；
- **脚本或编辑器直写**：按 `\n` 插入的内容留在盘上就是 LF。

两者叠加，同一个文件里就同时有了 CRLF 和 LF。典型形态是
`RgbwsvPackageWriter.cpp` 的 1771 : 14——1771 行来自检出，14 行来自后来的脚本插入。

这解释了为什么混合最严重的恰恰是**被频繁脚本化修改过**的那批源文件。

## 3. 代价：这不是洁癖问题

立项前的一场会话里，仅「补丁锚点匹配必须行尾感知」这一项就导致 5 次失败，
其中 2 次造成构建失败、跑的是旧二进制而浑然不觉。

更隐蔽的一种：单文件内混合时，「按文件主流行尾回填」这条补救规则**本身也会出错**
——单行锚点没有换行符，推导会退化成默认值，于是往 CRLF 正文里注入裸 LF，
让混合更严重。本会话内这一条踩了 3 次。

## 4. 根因实证：`core.autocrlf = true`

```
core.autocrlf    = true      （系统级，Git for Windows 安装器默认）
core.eol         = (未设置)
```

`autocrlf=true` 的语义是「提交时 CRLF→LF，检出时 LF→CRLF」。前半句解释了仓内为何
干净，后半句解释了工作树为何是 CRLF。

**一条直接证据**：本专项四份文档按 LF 写盘，`git add` 时 git 当场警告

```
warning: in the working copy of '...', LF will be replaced by CRLF the next time Git touches it
```

——「以后新文件都写 LF」这条规矩，没有 `.gitattributes` 根本立不住。

## 5. 为什么原 `.gitattributes` 拦不住

原文件只有三行：`*.pdf binary`、一行注释、一条单文件 `eol=lf`。**没有 `text=auto`**，
于是检出行为完全由各人的 `core.autocrlf` 决定。

补上 `* text=auto eol=lf` 后，检出也产出 LF，工作树才会与仓内一致。

## 6. 字节敏感面

仓内已有按**精确 SHA-256 字节**校验的固定样本——原 `.gitattributes` 那条注释即为先例。
另实测：

- 模型字节会进 `sourceHash`（`ModelFacadeImplementation.cpp:203`），
  但该哈希运行时重算、**不签入仓库**；`tests/golden/expected/` 与
  `samples/configs/scene/` 下出现的 `sourceHash` / `resourceHash` 均为占位串。
- 字节级基线的 11 例清单**不含任何 64 位十六进制串**，即产出清单不嵌模型哈希。

由于仓内本就是 LF，模型资产在仓内也已是 LF，这一节的风险实际上**已经不存在**；
保留它是为了记下核查过程——下次有人想动 `.obj` 时不必重查一遍。

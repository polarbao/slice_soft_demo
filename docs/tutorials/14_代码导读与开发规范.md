# 14 代码导读与开发规范

## 1. 推荐代码阅读顺序

目标：知道有哪些 target、CLI 模式、生产 API 和固定协议。

目标：理解 current production 与 diagnostic candidate 的隔离。

## 2. C++ 规范

- C++20；
- RAII 和值语义优先；
- 避免裸 `new/delete`；
- 单参数构造使用 `explicit`；
- 适合时使用 `constexpr`、`enum class`、`std::optional`、`std::span`、`std::string_view`；
- header 不放宽泛 `using namespace`；
- 浮点几何比较使用容差；
- 长度统一 mm，并在字段名表达单位；
- 大 vector 可预知容量时 reserve；
- 像素循环内避免堆分配和磁盘 I/O。

## 3. Qt 规范

- Qt 只在 `apps/slicer_debug_ui`；
- core 公共 API 不出现 QString/QList/QObject/QWidget；
- 长任务不阻塞 UI 线程；
- 使用函数指针 connect；
- UI 显示稳定错误码和友好中文，不吞掉 CLI exit code；
- report interpreter 与 widget 分离。

## 4. 错误处理

理想边界：

~~~text
低层 parser/algorithm
-> status/result 或稳定异常类型
-> ValidationIssue / blocker code
-> report
-> CLI exit / UI presentation
~~~

错误字符串可以解释，但自动化判断应依赖稳定 code。新增错误码要：

1. 命名稳定；
2. 明确 severity；
3. 指定 production 影响；
4. 有正/负测试；
5. 进入 report/schema；
6. UI 不把 blocker 降级成普通提示。

## 5. 新增模块的判断

满足以下任一条件才值得新增抽象：

- 明确消除多个调用方的真实重复；
- 建立需要测试的跨模块合同；
- 从聚合文件中隔离独立职责；
- 匹配现有 service/policy/report 模式；
- 为可选 backend 提供稳定 interface。

不要为了“看起来架构化”新增只转发一次、没有不变量也没有测试的层。

## 6. 修改 public API

先回答：

- 谁调用；
- 是否跨 apps/core；
- DTO 是否稳定；
- 是否改变单位、ownership、错误语义；
- legacy 与 experimental 是否都受影响；
- ABI 不是当前首要承诺，但源码兼容和测试影响是什么；
- 需要哪些 migration/adapter。

优先加 wrapper/adapter，再迁移调用方，最后删除旧入口。未经授权不要一次性重写。

## 7. 第三方依赖

新增依赖前至少比较两个候选：

| 维度 | 必须分析 |
|---|---|
| 功能 | 是否真正解决核心规则/算法 |
| CMake | imported target、静态/动态、MSVC 兼容 |
| vcpkg | manifest feature、triplet、版本可复现 |
| 许可证 | 商用分发、静态链接、NOTICE |
| 维护 | 活跃度、Windows 支持、上游风险 |
| 数据 | 是否保持 UV/材质/provenance |
| 体积 | 构建时间、runtime DLL、包大小 |
| 回退 | dependency unavailable 时普通构建是否可用 |

OpenVDB 的既有原则是 optional/OFF。Mesh repair 首版决策明确不自动引入第三方库。

## 8. 一个合格改动的结构

~~~text
问题/验收
-> 责任模块
-> 输入输出 DTO
-> 不变量和错误码
-> 最小实现
-> 单元/负向测试
-> report/schema 或 UI（若需要）
-> targeted validation
-> legacy safety validation
-> 状态文档（若改变项目状态）
~~~

## 9. 代码审查重点

1. 是否把目标态冒充当前态；
2. 是否破坏固定协议；
3. 是否出现反向依赖；
4. 是否静默 fallback；
5. 是否丢失 UV/材质/单位/layerIndex；
6. 是否把 diagnostic 当 production；
7. 是否只测 happy path；
8. 是否在像素/体素热路径引入明显二次复杂度或频繁分配；
9. 是否覆盖用户未提交改动；
10. 是否陈述实际验证，而不是推测。

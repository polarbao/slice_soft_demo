# 06 输入模型与场景导入

## 1. 支持的主要输入

| 格式 | 当前能力 | 典型限制 |
|---|---|---|
| STL | ASCII/Binary 基础几何 | 无标准 UV/材质语义 |
| OBJ | 顶点、面、UV、材质引用 | 依赖 MTL/纹理相对路径和资产完整性 |
| MTL | diffuse color、diffuse texture | 不是完整 PBR 材质系统 |
| PNG | 纹理采样 | 需有效 UV 和资源路径 |
| 3MF | stored/deflate、对象、component transform、BaseMaterial、ColorGroup、Texture2DGroup | 使用受限 XML reader，不代表支持全部扩展 |

## 2. 当前领域数据

legacy 输入最终汇总为 `ModelReport`，其中包含：

- 模型路径、格式、STL 编码；
- 顶点/面/三角形/退化三角形数量；
- BBox 与自动朝向信息；
- 三角形数组；
- 每三角形 UV 和材质名；
- 材质统计与贴图资源状态；
- 3MF 专项解析统计、warning 和 error。

正式模块还提供 `SceneModel`、`TriangleMeshData` 和 adapter。不要让 UI 或输出层重新解析外部格式。

## 3. OBJ/MTL/纹理链路

~~~mermaid
flowchart LR
  O["OBJ<br/>v/vt/f/usemtl/mtllib"] --> M["三角形 + UV + materialName"]
  L["MTL<br/>Kd/map_Kd"] --> R["MaterialInfo"]
  P["PNG"] --> R
  M --> S["ModelReport / Scene DTO"]
  R --> S
  S --> T["Texture Runtime / Transfer"]
~~~

关键检查：

1. OBJ 面索引是否合法；
2. 多边形是否可靠三角化；
3. `mtllib` 路径能否解析；
4. `usemtl` 名称是否存在；
5. UV 是否齐全；
6. 纹理文件是否存在且能读取；
7. fallback 策略是 warning 还是 fail fast。

## 4. 3MF 链路

3MF 是 ZIP package。当前实现：

1. 读取 central directory 和 stored/deflate entry；
2. 找 model part；
3. 使用受限字符串 XML reader；
4. 解析对象、网格、components、build；
5. 处理单位和 component transform；
6. 解析 BaseMaterial、ColorGroup、Texture2D/Texture2DGroup；
7. 将内部纹理提取到受控缓存并连接到三角形属性；
8. 把不支持资源和扩展写入报告。

安全重点：

- package 内部路径必须标准化，避免路径穿越；
- entry 数量和解压大小需可审计；
- 引用错误不能静默丢失；
- 3MF 支持矩阵应由 negative tests 和报告证明。

## 5. Transform 与单位

`modelTransform` 包含：

~~~json
{
  "unit": "mm",
  "scale": [1.0, 1.0, 1.0],
  "rotationDeg": [0.0, 0.0, 0.0],
  "translationMm": [0.0, 0.0, 0.0]
}
~~~

长度统一到 mm。新增算法必须明确输入是在原始坐标、标准化坐标、world-space、voxel-space 还是 raster-space。12E 分类到 raster 的一个核心风险正是坐标空间混淆。

## 6. 自动朝向

当前策略名称为 `minimize_height_by_right_angle_rotation`，使用直角候选方向，以最大高度约束和 footprint 等指标选择。它不是连续优化，也不考虑：

- 多模型碰撞；
- 支撑量全局最小；
- 纹理朝向；
- 设备夹具；
- 用户工艺禁区。

## 7. 拓扑为何重要

Scanline、point-in-closed-mesh、SDF 和 global distance 都依赖几何假设。以下问题会造成内部/外部不确定：

- boundary edge；
- non-manifold edge；
- duplicate/opposite duplicate face；
- local winding inconsistency；
- degenerate triangle；
- confirmed self-intersection。

strict production admission 必须阻断关键问题。`warn_and_attempt` 的输出只能诊断。确认自交必须 fail fast。

## 8. Mesh Repair 的当前边界

截至 2026-07-20，R1 contract、eligibility、generated golden 与四 case pre-repair baseline 已完成，正式方向仍是显式 `repair_then_strict`：

~~~text
pre-repair diagnostics + hash
-> eligibility
-> conservative repair
-> operation list + attribute provenance
-> post-repair full strict diagnostics
-> texture/partition/raster/closure/Release gates
~~~

不允许：

- strict 模式中隐式修复；
- 丢 UV/材质后仍标生产通过；
- 用体素重建冒充原始纹理网格；
- 为了赶进度把 `manual_repair_required` 当 PASS。

当前代码已有 `MeshRepairPreflight` 和 `mesh_repair_preflight` CLI，用于只读基线与资格判断；实际 conservative repair、post-repair strict、属性保持与 Release Gate 尚未完成。下一准备任务是 R2-01 Degenerate/Duplicate Cleanup。

只读 preflight 的基本形式：

~~~powershell
.\build\Debug\mesh_repair_preflight.exe --config <config.json> --output <report.json> --source-id <stable-path> --voxel-mm 0.10
~~~

它用于生成修复前证据，不修改源模型，也不写生产 TIFF。

## 9. 新增导入能力的检查表

1. 定义输入范围和明确非目标；
2. 转换到 scene/mesh DTO；
3. 保留单位、材质、UV、资源和 provenance；
4. 给出稳定 error/warning code；
5. 加最小正向 fixture；
6. 加损坏、缺失、越界引用负向 fixture；
7. 更新 model/import report；
8. 不让 importer 写 TIFF；
9. 运行 legacy 回归，确认旧格式不变。

## 1. 工作负载量化（E，全部结论的基础）

选型最容易犯的错是跳过这一步直接比库。本项目实际参数（A）：

```text
幅面        230 × 100 × 60 mm
实例上限    22（13B-03 的 11×2 规则排版）
模型类型    甲片，单个约 20 × 12 mm
```

整板俯视、视口按 1200×800 估（E）：

```text
缩放           ≈ 5.2 px/mm
单甲片占屏     ≈ 104 × 62 px ≈ 6400 像素
22 片总占屏    ≈ 142k 像素  =  视口的【15%】
若单片 50k 三角 → 平均每三角 ≈ 0.13 像素   ← 【严重 sub-pixel】
```

**三条推论：**

| # | 推论 | 依据 |
|---|---|---|
| **P1** | GPU 在此场景优势有限 | sub-pixel 三角每个至少占一个 2×2 quad → 50k 三角产生约 200k 片元着色，有效像素仅 6400，**约 97% 是 quad overdraw**。GPU 擅长的大三角填充用不上 |
| **P2** | 成本大头在纹理，不在几何 | 单张 2048² RGBA = 16 MB。首帧传输、解码、上传延迟与内存峰值才是瓶颈 |
| **P3** | **LOD 策略收益 >> 后端选择收益** | 整板俯视 lod2（10k 面）绰绰有余；只有放大到单片才需要 lod0。这条做对，后端选谁差别都不大 |

### 1.1 关键阈值公式（A + E）

```text
ViewData 每三角字节 = position 36 + normal 36 + texcoord0 24 + index 12 = 108 B
默认 maxBytes = 32 MiB，22 实例
→ 每实例预算 ≈ 1.49 MB  →  约 13.8k 三角/实例
```

> **⚠️ 必须先测的一个数**：甲片模型的实际三角面数。
> **超过约 13.8k，`lod: auto` 在 22 实例场景下就会降级** —— 而降级会触发 §2 的缺陷。
> 这一个数字决定 §2 是 P1 还是 P2。

## 2. 🔴 LOD 是「跳采样」实现的，不是网格简化（A 级代码证据）

`src/slicer_core/api/viewdata/SceneViewMeshBuilder.cpp:143-146`：

```cpp
const std::size_t stride = model.triangles.size() <= triangleLimit
    ? 1U
    : (model.triangles.size() + triangleLimit - 1U) / triangleLimit;
...
for (groupIndex = 0; groupIndex < triangleIndices.size(); groupIndex += stride)
```

`TriangleLimit()`（同文件 :84-99）：`lod1 = 50000`、`lod2 = 10000`。
50k 面模型降 lod2 时 `stride = 5` —— **每 5 个三角只保留 1 个**。

### 2.1 为什么这是问题

| | 真正的网格简化（QEM） | 当前的跳采样 |
|---|---|---|
| 做法 | 合并顶点、折叠边、重建拓扑 | 直接丢弃 4/5 三角面 |
| 结果 | 低面数但**仍然封闭**的网格 | **离散、不相连的三角碎片** |
| 外形 | 保持轮廓 | 轮廓破碎 |

结果不是"粗糙的低模"，而是**一堆散落的三角片** —— 模型看起来满身是洞。

**对甲片这类薄壳模型尤其致命**：薄壳本就只有上下两层面片，丢掉 4/5 后直接看穿，正反面混在一起。

### 2.2 两个次级缺陷（A）

| # | 缺陷 |
|---|---|
| **D1** | `stride` 用 `model.triangles.size()`（全模型）算，但循环在 `triangleIndices`（**单材质组**）上走。多材质模型各组按同一 stride 跳，实际保留总数 ≠ `triangleLimit`。材质越多偏差越大 |
| **D2** | `estimatedTriangles = model.triangles.size() / stride` 的 `reserve` 与实际逐组累加不符。仅性能问题，不影响正确性 |

### 2.3 降级理由措辞过于中性（A）

`TexturedSceneViewDataProvider.cpp:147` 写的是 `"mesh_lod_reduced_for_max_bytes"` ——
**完全看不出网格已经破碎**。宿主收到这个字符串不会知道要报警。

## 3. LOD 判据方向错误（契约层，P）

`DOC_SCHEMA_14` §4 的 `auto` 规则纯粹按字节数降级。但 LOD 的正确判据是**屏幕空间误差**，不是传输字节数。两者在本场景下**方向相反**：

```text
整板俯视（甲片仅 104×62 px，最不需要细节）
  → 预算够就发 lod0 → 传 1.1M 三角，屏幕只需几千   【浪费】

放大看单甲片（最需要细节）
  → 预算紧张 → 降到 lod2 → 恰好在此刻破碎           【错误时机】
```

**两个问题叠加**：用错误的判据（字节）触发一个错误的手段（跳采样），且触发时机与视觉需求相反。

## 5. 两处对我方早前结论的更正

### 5.1 ⚠️ WARP：Windows 自带 D3D11 软件光栅器

我此前建议"随包分发 llvmpipe / SwiftShader 作为无 GPU 回退"。**这在 Windows 上是多余的** ——
Windows **系统内置 WARP**（Windows Advanced Rasterization Platform），是 D3D11 的软件实现，
可通过 `D3D_DRIVER_TYPE_WARP` 或显式请求软件适配器使用，**无需任何额外分发**。

因此："工控机无独显"这条论据**主要针对 OpenGL 而非 D3D11**。选 D3D11 路径时该风险大幅降低。

> ⚠️ 待核实：QRhi 的 D3D11 后端是否会**自动**回退到 WARP，或需显式指定软件适配器。
> 实施时以 Qt 官方文档为准；但"能用 WARP"这一条是 D3D11 的既有能力，不依赖 Qt。

### 5.2 ⚠️ 像素级 UI golden 测试的性价比被我高估了

我此前把"确定性 → 可做像素级 golden 回归"作为 CPU 光栅的核心价值。**重新评估后需要下调**：

```text
成本   自研 CPU 光栅 10–18 人日
收益   仅【测试】受益，生产路径不受益
```

**更划算的替代**：

```text
① FrameDesc 层做确定性断言 —— 输入本身天然确定，零额外成本，能抓住绝大多数回归
   （相机矩阵、实例列表、identity 集合、装饰参数）
② 输出图像用容差比对（SSIM / 感知差异）而非逐字节
③ 合计约 2 人日，取得约 90% 的价值
```

这是 UI 测试的通行做法。**只有在"渲染算法本身"需要回归保护时，逐像素才不可替代** ——
而本项目的渲染是标准贴图着色，不含自研算法。

## 6. 🎯 推荐方案（Qt 6.8+ 长期版本前提）

```text
主推：方案 A（QRhiWidget 单后端）  +  meshoptimizer  +  修 LOD 缺陷
```

**四条理由：**

| # | 理由 |
|---|---|
| 1 | Qt 6.8+ 既已作为长期版本，**QRhiWidget 是零第三方、随 Qt LTS 维护的路径**，无需引入 bgfx 一类库，也不违反"不引入新依赖"的既有约束 |
| 2 | D3D11 + WARP 已覆盖工控机场景（§5.1），CPU 光栅的**主要生产理由消失** |
| 3 | 像素级 golden 的收益可用 ~2 人日的替代方案取得 90%（§5.2），**不值 10–18 人日** |
| 4 | 按 P3，**LOD 与纹理策略的收益远高于后端选择** —— 把预算投到 meshoptimizer 与 LOD 修复上，回报率高得多 |

**保留 `IRenderBackend` 接口不变。** 抽象成本几乎为零，将来若确实需要 CPU 后端（例如出现真正无 D3D11 的部署环境），可以直接加实现而不改 14E 一行代码。

**不推荐方案 D**：Qt 官方方向已转向 QRhi，且 OpenGL 驱动是本场景已知的薄弱环节。

**方案 B 的适用条件**：如果后续出现"必须逐像素复现渲染结果"的硬需求（例如客户要求渲染结果可审计），再补 CPU 后端。届时接口已在，增量实施。
